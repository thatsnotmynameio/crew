# Getting set up

crew is a Go module, `github.com/thatsnotmynameio/crew`. Its binary is `cmd/crew`, and everything else is under `internal/`. [Architecture](/develop/architecture) explains how the packages fit together and how to add an adapter.

You need:

- Go 1.27 or later, as `go.mod` says;
- macOS or Linux, since crew starts its tools in process groups;
- pnpm, for the docs and the Codacy CLIs.

## Commands

Run every command from the repository root.

```sh
go build ./cmd/crew                 # the crew binary, at the root (ignored by git)
go test -race ./...                 # every test
gofmt -l cmd internal tools         # files gofmt would change; prints nothing when clean
go vet ./...
go run github.com/golangci/golangci-lint/v2/cmd/golangci-lint@v2.14.0 run
go run golang.org/x/vuln/cmd/govulncheck@v1.8.0 ./...
```

[Code quality](/develop/quality) lists the coverage checks and Codacy's tools, which also run locally.

Run golangci-lint through `go run` as above, at the version CI uses. A golangci-lint older than v2.13.0 cannot lint a `go 1.27` module, so an older one installed on your machine fails. Its config, `.golangci.yml`, turns on every linter except the ones it lists with a reason, and also enforces the package layering through `depguard`.

To run one package's tests, or one test:

```sh
go test -race ./internal/core
go test -race ./internal/core -run TestName
```

The TUI's views are golden files under `internal/ui/tui/testdata/`. After a deliberate change to the view, rewrite them and review the diff:

```sh
go test ./internal/ui/tui -update
```

CI's `go` job (`.github/workflows/ci.yml`) runs gofmt, `go vet`, golangci-lint, the tests with the race detector and coverage, the two coverage floors, and govulncheck on every pull request and every push to `main`. Its `codacy` job sends the results to Codacy; see [Code quality](/develop/quality).

## Releases

The version is `VERSION`. A pull request that bumps it is a release: once it merges to `main`, the Release workflow (`.github/workflows/release.yml`) publishes the tag `vX.Y.Z` and a GitHub release. The version must be `MAJOR.MINOR.PATCH` and not below the latest release. A version that already has its tag publishes nothing.

GoReleaser builds and publishes the release from `.goreleaser.yaml`. Each release ships crew for darwin and linux on amd64 and arm64, one archive per platform named without the version (`crew_linux_arm64.tar.gz`), and `checksums.txt`. The binaries print the tag for `crew --version`. The notes are GitHub's generated notes, which the workflow asks for at the released commit and hands to GoReleaser.

Nothing is published unless every archive built. The workflow tags the commit locally only, GoReleaser keeps the release a draft while it uploads the assets, and GitHub creates the tag when GoReleaser publishes it. If an upload fails, the draft stays and no tag exists: re-running the workflow finishes that draft. This is the one workflow that does not use [thatsnotmynameio/.github](https://github.com/thatsnotmynameio/.github)'s shared release action to publish; it still uses its check.

Try the configuration without publishing anything; the archives land in `dist/`, which git ignores:

```sh
go run github.com/goreleaser/goreleaser/v2@v2.18.2 check
go run github.com/goreleaser/goreleaser/v2@v2.18.2 release --snapshot --clean
```

Users install a release with the command in the Guide's Install section, or with `go install github.com/thatsnotmynameio/crew/cmd/crew@vX.Y.Z`, which prints `vX.Y.Z` too. A `go build` in a checkout prints the version Go derives from the commit, and `dev` when it records none (`go build -buildvcs=false`).

## Docs

Run `pnpm install` once, then `pnpm docs:check` for broken links and invalid MDX, and `pnpm docs:preview` for a live preview.
