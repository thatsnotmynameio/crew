# crew

crew moves your issues through a workflow you declare in the repository. It polls GitHub for the issues and pull requests you labeled, and for each one it runs the stage's actions in parallel. Each action is a headless Claude Code session in its own git worktree and branch. When every action ends, crew moves the issue on, or to the stage's failure label with a comment saying what failed.

crew runs sessions and moves labels. Opening a pull request, reviewing and merging are your prompts' job and yours. A stage takes issues, or, with `takes: pull_requests`, the pull requests you labeled. crew also writes to the pull requests that close an issue: it gives them the issue's crew label, and comments on them when a stage ends. See [The pull requests](#the-pull-requests).

## Install

On macOS or Linux, on amd64 or arm64, this downloads the latest release for your machine, checks it against the release's `checksums.txt`, and installs `crew` into `/usr/local/bin`. `sudo` asks for your password.

```sh
(
  set -eu
  os=$(uname -s | tr '[:upper:]' '[:lower:]')
  case $(uname -m) in
    x86_64) arch=amd64 ;;
    aarch64 | arm64) arch=arm64 ;;
    *) echo "crew has no build for $(uname -m)" >&2; exit 1 ;;
  esac
  archive="crew_${os}_${arch}.tar.gz"
  url=https://github.com/thatsnotmynameio/crew/releases/latest/download
  tmp=$(mktemp -d)
  trap 'rm -rf "$tmp"' EXIT
  cd "$tmp"
  curl -fsSLO "$url/$archive"
  curl -fsSLO "$url/checksums.txt"
  if command -v sha256sum > /dev/null; then
    grep " $archive\$" checksums.txt | sha256sum -c -
  else
    grep " $archive\$" checksums.txt | shasum -a 256 -c -
  fi
  tar -xzf "$archive" crew
  sudo install -d /usr/local/bin
  sudo install -m 0755 crew /usr/local/bin/crew
  crew --version
)
```

With Go 1.27 or later, you can build a release instead, where `vX.Y.Z` is the release's tag:

```sh
go install github.com/thatsnotmynameio/crew/cmd/crew@vX.Y.Z
```

This puts `crew` in `$(go env GOPATH)/bin`.

## Before you run it

- **macOS or Linux.** crew starts every tool in its own process group, which Windows does not have.
- **A git repository with an `origin` remote on GitHub.** crew branches each action from origin's latest default branch.
- **`gh`, logged in** (`gh auth login`), with permission to edit the repository's issues and labels.
- **`claude` on your `PATH`**, logged in.

crew checks all of this when it starts and stops with a message if something is missing.

## Configure it

crew reads `.crew/config.yaml` at the root of the repository. Commit it. Here is a complete example:

```yaml
config:
  poll_interval_seconds: 300
  max_parallel_issues: 2
  harness: claude
  model: claude-opus-5-5
tracker:
  name: github
workflow:
  - name: implement
    label: ready
    moves_to: in progress
    on_success: ready to review
    on_failure: needs attention
    actions:
      - name: acceptance
        prompt: >-
          Write the acceptance tests for issue {{.Issue.Ref}} ({{.Issue.URL}}).
          Take the acceptance examples from the issue and ask nothing: nobody
          answers questions in this session. Open a pull request with the tests.
      - name: development
        prompt: >-
          Implement issue {{.Issue.Ref}}, "{{.Issue.Title}}" ({{.Issue.URL}}).
          Open a pull request with the change. This session is headless:
          ending your turn ends the session. Never end a turn waiting on a
          background command; run it in the foreground, or wait for it with
          Monitor.
        check: >-
          gh pr list --head "$CREW_BRANCH" --state open --json number --jq length
          | grep -qv '^0$' || { echo "no open pull request from $CREW_BRANCH"; exit 1; }
  - name: review
    label: ready to review
    moves_to: in review
    on_success: ready to merge
    on_failure: needs attention
    actions:
      - name: custom_review
        prompt: "Review the pull requests for issue {{.Issue.Ref}} and leave your review on them."
```

With it, an issue labeled `ready` gets two sessions at once, `acceptance` and `development`, and moves to `in progress`. When both succeed, it moves to `ready to review`, where the `review` stage takes it. When either fails, it moves to `needs attention`. `development` succeeds only when its [check](#checks) finds an open pull request from its branch. Here `on_success: ready to merge` only means "reviewed": crew does not merge anything.

Sessions run with no one to answer them, so tell the agent not to ask. A session that asks a question and stops counts as a success. That is why the `acceptance` prompt tells it to take the examples from the issue.

Ending a turn also ends the session, and nothing resumes it. A session that ends its turn to wait for a background command, such as a test run, is stopped there and counts as a success. That is why the `development` prompt tells it to run commands in the foreground or wait for them with Monitor.

### Keys

Everything but `workflow` is optional. A minimal file is a `workflow` alone.

| Key | Default | What it does |
| --- | --- | --- |
| `config.poll_interval_seconds` | `300` | Seconds between polls. Must be positive. |
| `config.run_time_limit_seconds` | none | How long crew runs, counted from its first poll, before it winds down (see [Run it for a set time](#run-it-for-a-set-time)). Must be positive: `28800` is 8 hours. Without it, crew runs until you stop it. |
| `config.max_parallel_issues` | `2` | How many issues crew works on at once, split into [queues](#queues). It counts issues, not sessions: an issue whose stage has two actions takes one slot. |
| `config.clerk_slots` | `1` | The slots of the `clerk` queue, for bookkeeping stages. At least 1, and below `max_parallel_issues`. See [Queues](#queues). |
| `config.queues` | none | More queues, each a name and its slots, such as `review: 2`. See [Queues](#queues). |
| `config.mate` | none | The default [mate](#act-as-mates): crew's own writes on GitHub act as it, and so does every action that names no mate. |
| `config.usage_in_status` | `false` | Adds each ended action's cost, tokens and pull request to the [status comment](#the-status-comment). |
| `config.harness` | `claude` | The coding agent that runs sessions. `claude` is the only one today. |
| `config.model` | `claude-opus-5-5` | The model every session runs, passed to `claude --model`. |
| `tracker.name` | `github` | Where issues live. `github` is the only one today. |
| `harness` | none | A top-level section for harness-specific settings. `claude` takes none, and the model goes in `config.model`. |
| `extra_labels` | none | Labels for parked work that no stage takes, such as an idea waiting for a brainstorm. See below. |
| `board` | none | The columns of the live view's board, each a name and the labels whose open issues it shows. Without it, the board has one column per stage. See [The board](#the-board). |
| `prompts` | none | Named prompts that a skill runs in your own Claude Code session, such as `brainstorm` for [`/cw-brainstorm`](/guide/create-issue#brainstorm-an-issue). See [Prompts](#prompts). |
| `workflow` | required | The stages, at least one. |

Each stage has:

| Key | What it does |
| --- | --- |
| `name` | The stage's name, unique in the workflow. |
| `label` | The label the stage takes issues from. No two stages take the same label. |
| `moves_to` | The label the issue carries while the actions run. It cannot be any stage's `label`, or that stage would take the issue too. |
| `on_success` | The label the issue moves to when every action succeeded. It cannot be the stage's own `label`. |
| `on_failure` | The label the issue moves to when any action failed, with crew's comment. It cannot be the stage's own `label`, but it can be another stage's: `on_failure: ready` on the `review` stage sends a failed review back to `implement`. |
| `actions` | At least one action, each with a `name` (unique in the stage), a `prompt`, and optionally a `check` (see [Checks](#checks)) and a `mate` that its session and check act as (see [Act as mates](#act-as-mates)). |
| `queue` | Optional. The [queue](#queues) the stage runs in: `clerk`, `default` or one under `config.queues`. Without it, the stage runs in `default`. |
| `takes` | Optional. The kind of item the stage takes: `issues`, the default, or `pull_requests`. A stage takes one kind, never both. See [A pull request as the work](#a-pull-request-as-the-work). |
| `on_board` | Optional. `false` hides the stage from the live view's board: it gets no column, an issue it holds gets no card, and its ends send no notification. Its actions still show in Actions and its events in Events. Stages show by default. With a [`board`](#the-board), the stage still sends no notification, but `on_board` no longer changes the board. See [Run it](#run-it). |
| `description` | Optional. The work the stage takes, in a few words, such as `a bug to reproduce and fix`. crew does not use it: the [`/cw-create-issue`](/guide/create-issue) skill shows it when it lists the types of issue. |
| `issue_template` | Optional. The file name of a Markdown issue template in `.github/ISSUE_TEMPLATE/`, such as `bug.md`. crew does not use it: `/cw-create-issue` fills it for an issue of this stage. |

`label`, `moves_to`, `on_success` and `on_failure` hold the label as it is written on GitHub, such as `in progress`. Any text works. GitHub does not tell labels apart by case, so neither does crew: `Ready` and `ready` are the same label in every rule above, and crew writes a label everywhere as you first wrote it in the file.

A stage whose `on_success` or `on_failure` is its own `moves_to` leaves the issue where it is when it ends. On failure crew still comments.

Each item of `extra_labels` has:

| Key | What it does |
| --- | --- |
| `label` | Required. The label, written as on GitHub. It cannot be a label any stage names in `label`, `moves_to`, `on_success` or `on_failure`, or another extra's label. |
| `description` | Optional, as for a stage. |
| `issue_template` | Optional, as for a stage. |

```yaml
extra_labels:
  - label: waiting brainstorm
    description: an idea to brainstorm later
    issue_template: idea.md
```

The label above is an example. Extra labels, `description` and `issue_template` serve the author's own workflow with [`/cw-create-issue`](/guide/create-issue), so they may still change.

crew's labels are the ones your stages name in `label`, `moves_to`, `on_success` and `on_failure`, plus the extra labels, and no others. Every other label on an issue is yours: crew ignores it and never removes it.

An extra label parks an issue that no stage takes, such as an idea that waits for a brainstorm. No stage takes an issue whose only crew label is an extra. To start work on it, add a stage's `label`: that stage takes the issue at the next poll with a free slot, even with the extra still on it. Every move crew makes removes the extras an issue carries, together with its other crew labels, so the issue leaves the extra behind when a stage takes it.

So declare as an extra only a label you keep for crew. If you declare a label you already use, such as `bug`, crew removes it from every issue it moves.

### The board

By default the live view's board has one column per stage and shows only the issues crew has in play. `board` sets its columns yourself, to see the issues you care about while crew runs, such as parked ideas, open bugs and finished work:

```yaml
board:
  - name: ideas
    labels: [crew:brainstorm:ready]
  - name: bugs
    labels: [bug]
  - name: done
    labels: [crew:brainstorm:done, crew:triage:done]
```

Each column has:

| Key | What it does |
| --- | --- |
| `name` | Required. The column's title, unique on the board. |
| `labels` | Required. One or more labels, written as on GitHub. Any label works, crew's own or not. crew does not check that it exists on GitHub, so a label no issue carries gives an empty column. |

The columns are drawn left to right in the file's order. A column holds a card for each open issue that carries at least one of its labels, opened by the boss or a mate, the same issues crew takes. An issue with the labels of several columns has a card in each, and an issue with none of them has no card, even while crew works on it: its work still shows in Actions. Pull requests never get a card. With `board` set, the stages no longer shape the board: they add, hide and order no column, whatever their `on_board`. Labels compare ignoring case, as GitHub compares them, and a label that is also a stage's or an extra's takes the spelling the workflow or the extra gives it.

### Queues

`max_parallel_issues` is split into queues, and each stage runs in one of them. A queue's slots are only for its own stages: a long development session can never take the slot of a quick bookkeeping stage, such as a triage that finds an issue's blockers. Two queues are always there:

- `clerk`, for bookkeeping. It has `config.clerk_slots` slots, 1 unless you set it.
- `default`, which gets the slots the other queues leave: `max_parallel_issues` minus `clerk_slots` minus the slots of every queue under `config.queues`. A stage that names no `queue` runs here.

You can declare more under `config.queues`, each with its slots:

```yaml
config:
  max_parallel_issues: 5
  clerk_slots: 1
  queues:
    review: 2
workflow:
  - name: triage
    queue: clerk
    # ...
  - name: review
    queue: review
    # ...
  - name: implement
    # ...
```

Here `triage` has 1 slot, `review` 2, and `implement` runs in `default`, which has the 2 slots left.

A queue never lends a slot it does not use. While `default` is full, a `clerk` slot stays free for the next triage, even with development issues waiting. So a slot is guaranteed only by the size of a stage's queue, and the total never goes over `max_parallel_issues`. A queue that no stage names, such as `clerk` in a config that names no queue, keeps its slots idle: with only `max_parallel_issues: 2`, `clerk` has 1 slot and every stage shares the other 1. The [live view](#run-it) shows each queue a stage runs in, with its busy and free slots.

`default` may have 0 slots, when the other queues take them all. Its stages then never run, and crew does not warn you. crew refuses to start when:

- `clerk_slots` is below 1, or not below `max_parallel_issues`. With `max_parallel_issues: 1`, the 1-slot `clerk` leaves no room, so raise the limit to at least 2.
- `default` would have fewer than 0 slots.
- a queue under `config.queues` has fewer than 1 slot, or is named `clerk` or `default`, in any case.
- a stage names a queue that does not exist.

### Prompts

A prompt is a Go template over the item the stage took: an issue, or a pull request when the stage has `takes: pull_requests`:

| Field | On GitHub |
| --- | --- |
| `{{.Issue.Ref}}` | `#42` |
| `{{.Issue.Key}}` | `42` |
| `{{.Issue.Title}}` | the issue's or pull request's title |
| `{{.Issue.URL}}` | the issue's or pull request's web address |

Any other field is an error when crew starts. Quote the prompt or use a block (`>-`) as in the example: in YAML, a value that starts with `{` is not a string.

A session on a pull request still starts in a new worktree branched from the default branch. A prompt that works on the pull request's own branch checks it out itself, detached, and pushes to that branch by name:

```yaml
prompt: >-
  Run `gh pr checkout {{.Issue.Key}} --detach`, then answer the review
  comments on pull request {{.Issue.Ref}} and push your fixes with
  `git push origin HEAD:$(gh pr view {{.Issue.Key}} --json headRefName --jq .headRefName)`.
```

Keep `--detach`. git checks out a branch in one worktree only, and a pull request crew opened keeps its branch checked out in the worktree of the session that opened it, which crew never removes. A plain `gh pr checkout` fails there.

The top-level `prompts` maps a name to a prompt that a skill runs, not crew. Some work needs you at the keyboard, such as a brainstorm, so it cannot be an unattended action. [`/cw-brainstorm`](/guide/create-issue#brainstorm-an-issue) fills `prompts.brainstorm` with an issue and runs it in your session:

```yaml
prompts:
  brainstorm: |-
    /compound-engineering:ce-brainstorm {{.Issue.Ref}}
```

[`/cw-update-issue-plan`](/guide/create-issue#put-a-plan-in-an-existing-issue), run without a label, runs `prompts.update_issue_plan` the same way once it has put the plan in the issue, for example to move the issue to the label that always comes next.

crew checks these prompts as it checks an action's, with the same fields, and then ignores them. `prompts` serves the author's own workflow, so it may still change.

### Checks

An action's `check` is a shell command crew runs after the action's session succeeded, to see that the work exists:

```yaml
      - name: development
        prompt: "Implement {{.Issue.Ref}} and open a pull request that closes it."
        check: >-
          gh pr list --head "$CREW_BRANCH" --state open --json number --jq length
          | grep -qv '^0$' || { echo "no open pull request from $CREW_BRANCH"; exit 1; }
```

- **Where it runs:** with `sh -c`, in the action's worktree, once its session has ended. A session that failed runs no check.
- **What it gets:** your environment, plus `CREW_ISSUE_REF` (`#42`), `CREW_ISSUE_KEY` (`42`), `CREW_ISSUE_URL`, `CREW_BRANCH` (the worktree's branch, such as `crew/issue-42-development`), and `CREW_BOSS` and `CREW_MATES` (see [Who the boss is](#who-the-boss-is)). It acts on GitHub as its action's session does, as its [mate](#act-as-mates) when it has one. The check is not a template: write `$CREW_ISSUE_REF`, not `{{.Issue.Ref}}`. No issue text, such as the title, ever becomes part of the command.
- **How it passes:** it exits with 0. It fails when it exits with anything else, cannot start, or runs for more than 10 minutes, a limit you cannot change. A failed check fails the action, as a failed session does: the issue moves to `on_failure`, and crew does not run the action again.
- **Its output:** stdout and stderr go to the action's log, after the session's. The reason crew gives is `the check failed:` followed by the last line the check printed, from stdout or stderr. That line goes into the issue's [status comment](#the-status-comment), which may be public. So keep your tools' output out of the last line, and end a failing check by echoing its own one-line reason, as above. A check that runs out of time or cannot start says so instead.
- **What it trusts:** the check runs in the worktree the session wrote. A check that calls a script from the repository runs the session's copy of it. The check catches a session that stopped early, not one that tries to fool it.

When you stop crew, a running check is ended too, and its action counts as stopped. When the run time is up, a running check runs to its end.

### What "succeeded" means

An action succeeded when its session ended cleanly, Claude Code's last result is not an error and `claude` exited with 0, and its check, if it has one, passed. Without a check, crew does not look for a pull request or any other evidence of the work. The labels and comments crew writes to [pull requests](#the-pull-requests) never decide whether an action succeeded.

So a session without a check can succeed without doing its work. For example, `--permission-mode auto` denies a tool, and the agent gives up politely, or the session ends its turn while a command runs in the background. Give such actions a check that looks for the work, write prompts that say what done looks like, and read the last message crew prints for every action that ends, successes included.

To make an early end less likely, crew starts `claude` with a Bash timeout of 10 minutes by default and 30 at most (`BASH_DEFAULT_TIMEOUT_MS` and `BASH_MAX_TIMEOUT_MS`), instead of Claude Code's 2 and 10. A Bash command that outlives its timeout moves to the background, so a full test run now stays in the foreground. They win over the same variables in the environment you start crew in.

### When crew refuses to start

Before its first poll, crew checks the whole file and its tools. It stops, exiting with 2, when:

- a key is unknown, or a value has the wrong type (the message names the key and its line);
- `config.harness` or `tracker.name` names an adapter that does not exist;
- a stage lacks `label`, `moves_to`, `on_success` or `on_failure`;
- the workflow would loop or take an issue twice (the `label`, `moves_to`, `on_success` and `on_failure` rules above);
- an extra label is a label a stage names, or another extra's label, ignoring case;
- `board` is an empty list, a column has no `name`, no label or an empty label, or two columns share a name (the message names the column);
- `board` is set and the tracker cannot list issues by any label;
- a `description` is empty, or an `issue_template` is not a file name ending in `.md` (it holds a `/` or `\`, for example). crew does not check that the template file exists;
- a prompt, in an action or under `prompts`, is empty, does not parse, or uses a field that does not exist;
- an action's `check` is present but empty;
- a stage's `takes` is neither `issues` nor `pull_requests`;
- an action names a `mate` while `config.mate` names none, or a mate's name is not lowercase letters, digits and hyphens;
- CODEOWNERS cannot be read, or its `*` rule names a team crew cannot list (see [Who the boss is](#who-the-boss-is));
- a [queue](#queues) rule is broken: `clerk_slots`, `default`'s slots, a queue's slots or name, or a stage's `queue`;
- `gh` is missing or not logged in, `claude` is not on your `PATH`, or the repository has no `origin`;
- the checks take more than 10 minutes, or you stop crew during them.

crew stops at the first check that fails, and prints its error after the [boot log](#run-it), whose last line names the check that failed. A second broken tool shows on the next start.

At the same check, crew creates the labels your workflow names and the extra labels that the repository does not have yet, each `on_failure` label included, and no other.

## Act as mates

Without mates, crew, its sessions and its checks act on GitHub as your `gh` login. GitHub does not notify you about your own activity, so a failure report rarely reaches you, and it does not let you approve a pull request you opened. A [mate](/guide/mates) is a GitHub identity of crew's own. Name mates in the config, and crew acts as them:

```yaml
config:
  mate: ops
workflow:
  - name: implement
    label: ready
    moves_to: in progress
    on_success: ready to review
    on_failure: needs attention
    actions:
      - name: development
        prompt: "Implement {{.Issue.Ref}} and open a pull request that closes it."
        mate: developer
      - name: acceptance
        prompt: "Write the acceptance tests for {{.Issue.Ref}}."
```

- **`config.mate`** is the default mate. crew's own writes on GitHub act as it: the labels it creates, its label moves, the status comment, the failure report, the stop comment and the labels it mirrors on pull requests. So does every action that names no mate, `acceptance` above.
- **An action's `mate`** acts for that action's session and its check, `developer` for `development` above. Two actions of one stage can act as different mates, such as a developer and a reviewer: a mate cannot approve a pull request it opened.
- **An action can name a mate only with a default.** An action's `mate` without `config.mate` stops crew at startup.
- **A name is a mate on this machine.** crew finds it among the mates stored on this machine for the owner of the repository, so the same config works in every repository of that owner where the mate is installed.
- **Without a mate,** crew, its sessions and its checks act as your `gh` login, as before.

### What acts as whom

- **crew's reads,** such as the poll and the labels and comments it lists, go as your `gh` login, so a mate's missing organization permissions cannot break the poll. `gh` must stay logged in as you.
- **crew's writes** go as the default mate. When GitHub refuses the mate's token, crew renews it and tries once more. When the mate is still refused, lacks a permission, or lost access to the repository, crew makes the write again as you, and every later write of the run too, until crew restarts. The live view and the event lines then warn that crew writes as you, with the fix.
- **A session and its check** act as the action's mate in every `gh` call, for as long as they run: crew renews each token before its hour is up. They get a token limited to this repository, never the mate's key, and act as the mate even when your shell exports `GH_TOKEN` or `GITHUB_TOKEN`. A pull request a session opens has the mate as its author, so you can approve it.
- **Commits stay yours:** authored by you and pushed with your own git credentials. Every commit made in a workspace acting as a mate ends with the mate as co-author, whatever makes it, a skill's own `git commit` included:

  ```text
  Co-authored-by: crew-developer[bot] <123+crew-developer[bot]@users.noreply.github.com>
  ```

  The trailer comes from a `commit-msg` hook crew sets through git's environment, which needs git 2.54 or newer. Your own hooks still run.

crew never puts a token or a key in a prompt or a log, and it redacts GitHub tokens and private keys from what a session or a check says before that reaches a comment, the live view or the event lines.

### Who the boss is

crew takes the issues and pull requests that the boss or a configured mate opened, even a mate that cannot act this run. A mate whose key is not on this machine has no login crew knows, so its issues wait until you create it here. The boss is every user the `*` rule of the repository's CODEOWNERS names, on its default branch. crew reads the first of `.github/CODEOWNERS`, `CODEOWNERS` and `docs/CODEOWNERS` that exists, and its last `*` line, as GitHub does. A team, such as `@org/devs`, counts as its members, which `gh` lists only with the `read:org` scope: run `gh auth refresh -s read:org` when crew says it cannot. Email owners are skipped. Without CODEOWNERS, or with a `*` rule that names no user, the boss is your `gh` login. This holds whether or not the config names a mate. crew reads CODEOWNERS when it starts.

Sessions and checks get the logins in two variables, each a list separated by spaces: `CREW_BOSS`, the boss's, and `CREW_MATES`, those of the configured mates stored on this machine, each as `<slug>[bot]`, including a mate that cannot act this run. In a session acting as a mate, `@me` is the mate, so a prompt that lists the issues crew takes uses them instead:

```sh
for login in $CREW_BOSS $CREW_MATES; do gh issue list --state open --author "$login"; done
```

### When a mate cannot act

crew still starts when a mate it names cannot act, and acts as your `gh` login wherever that mate would. It warns at the top of the live view, and in the first lines of `--plain` output, naming the mate, what is wrong and the fix:

- **No key on this machine:** run `crew mates create <name>` in this repository.
- **Not installed on the repository:** run `crew mates create <name>` in this repository to install it.
- **GitHub rejected its key,** as after you deleted the app or revoked its key: delete the mate's file and run `crew mates create <name>` again.
- **It could not get a token,** as when GitHub fails, or the token grants other permissions than every mate asks for: crew acts as you this run, and a restart tries again.
- **Its commits carry no co-author,** with git older than 2.54, or when GitHub did not give the bot's user id. The mate still acts. Update git, or restart crew.

A mate that cannot act at startup is not tried again until crew restarts. Its row in the [live view](#run-it)'s Mates section reads `cannot act` with a short reason, such as `no key`, `bad key file`, `not installed`, `key rejected` or `no token`, and its stages and actions act as you.

A mate can also stop acting while crew runs. crew then adds a warning under the header, with the reason and the fix, changes the mate's row, and prints an event, which `--plain` prints too:

- **crew's writes go back to you:** GitHub refused the default mate's credentials, a permission, or access to the repository, so crew writes as you until it restarts. The row reads `writes as you`, and the warning stays for the rest of the run.
- **A token did not renew:** crew renews each token about ten minutes before it expires, and a renewal failed. The row reads `token not renewed` at once, while the old token still works, and the sessions and checks acting as the mate fail once it expires. crew tries again every minute: when a renewal succeeds, the row reads `acting` again, the warning goes, and an event says the mate acts again.

### Before you name a mate

- **Log `gh` in** with `gh auth login`. A login that exists only as an exported `GH_TOKEN` gives a session acting as a mate no way to push.
- **Pushes keep your credentials.** When your git config runs `gh auth git-credential` as the credential helper for github.com, as `gh auth setup-git` sets it, crew points that helper at your own `gh` config in a session acting as a mate, so `git push` pushes as you. Other helpers and SSH remotes are left alone.
- **Push before `gh pr create`.** `gh pr create` pushing a branch itself pushes as the mate, which cannot push code. Have prompts push with `git push` first.
- **Don't export `GH_TOKEN` in a profile the session's shell loads.** crew removes it from a session's environment, but a profile that sets it again makes the session's `gh` act as you.
- **A commit made with `--no-verify`** skips the hook and carries no co-author.

crew keeps the run's tokens in a private directory only your OS user can read, under `$XDG_RUNTIME_DIR` or else the system's temporary directory, never inside the repository, and removes it when it exits. After a crash or SIGKILL the tokens stay there until they expire, within the hour. A session runs as your OS user, so it could read a mate's key file: see [the key's risk](/guide/mates#the-keys-risk).

## What crew does on each poll

While every queue a stage runs in is full, a poll lists no issues, since it could take none. It still updates the running issues' status comments and retries what is owed, and says so in a line such as `poll: skipped, 2 of 2 slots busy`, which counts only the slots of the queues your stages run in. When crew lets go of an issue after such a poll, it lists at once instead of waiting for the next poll. Otherwise, a poll goes like this:

1. It lists the open issues and pull requests that [the boss](#who-the-boss-is) or a configured [mate](#act-as-mates) opened and that carry a stage's `label`. Those other people opened are ignored, whatever their labels, and so are those whose only crew label is an extra.
2. It skips an issue that carries two crew labels, such as `ready` and `needs attention`, and says so. Remove one, and a later poll takes it. Extra labels do not count, and neither do labels no stage names: an issue labeled `paused` and `ready` is taken when no stage names `paused`, and so is one labeled `waiting brainstorm` and `ready` when `waiting brainstorm` is an extra.
3. It leaves alone an item whose stage takes the other kind: a pull request carrying the `label` of a stage that takes issues, or an issue carrying the `label` of a stage with `takes: pull_requests`. crew does not move it or comment on it, and says so once, in a line such as `left #90 alone: it is a pull request, and ready is the label of implement, which takes issues`. It says so again only after a poll found the item without that label, or after crew restarts.
4. It skips an issue that an open issue blocks, as GitHub records it under the issue's relationships ("blocked by"). A pull request is never blocked. The issue keeps its label, and a later poll takes it once every issue blocking it is closed. crew writes no status comment for it while it is blocked.
5. It takes each issue whose stage's [queue](#queues) has a free slot, and passes over the others, so a full queue does not hold back the stages of another queue. It goes through them in this order: the highest priority first; then, at the same priority, later stages first, so reviews are not starved behind new work; then the oldest issue first. The priority is the issue's GitHub issue field `Priority`, which your organization defines, ranked by the order of the field's options: with Urgent, High, Medium and Low, Urgent goes first. An issue without a priority, and every pull request, goes after every issue that has one. A repository without issue fields, such as one you own as a user, or an organization without a single select field named `Priority`, works as before: no issue has a priority. crew writes nothing on the issues left waiting: they keep their label, and a later poll with a free slot in their queue takes them.
6. Taking an issue moves it to the stage's `moves_to`. A move removes every other crew label, extras included, and adds the new one, and leaves your other labels alone. Every move crew makes is then mirrored on the issue's open [pull requests](#the-pull-requests).
7. For each action, crew creates a worktree and a branch from origin's latest default branch, and starts a session there with the action's prompt. When the last run of that action, in that stage, on that issue failed, crew [resumes it](#resume-a-failed-action) in that run's worktree instead.
8. While the actions run, crew updates the issue's status comment at every poll.
9. When every action of the issue has ended, its check included, crew judges it. If all succeeded, the issue moves to `on_success`. Otherwise it moves to `on_failure`, and crew comments on the issue. Either way, crew then comments on the issue's open pull requests that the stage ended.

This failure report is a new comment, apart from the status comment, so GitHub notifies you of it. It names each failed action and its log, relative to the repository:

```markdown
crew: 1 action failed on #42.

**`development`** failed. Its log is `.crew/logs/issue-42-development.log`.
```

The comment carries nothing the session said: no last message, no commands, no output. Why an action failed is in its log, in crew's output and, in crew's own words, in the status comment. An action whose worktree could not be created has no log, and the comment says it failed before it had a log.

A move or comment that fails, for example because GitHub is down, is retried at every poll and once more when crew stops. So is a label or comment on a pull request, which never holds back or undoes the issue's move. One that cannot work, because the issue was closed or relabeled meanwhile or GitHub refused it, is dropped and reported. A status comment that says an issue is running is not retried: the next poll writes it again.

To retry a failed issue, swap its `on_failure` label, such as `needs attention`, for the stage's `label`, such as `ready`. Each failed action then resumes where it stopped, and each action that succeeded starts over.

### Resume a failed action

When a stage takes an issue, crew looks at the last run of each of its actions on that issue. When that run failed, the action resumes: crew runs a new session in the failed run's worktree, on its branch, with the commits and uncommitted files it left. crew does not fetch, merge or rebase the default branch into it. A run counts as failed when its action failed for any reason: the session failed, its check failed, crew stopped it, it failed to start, or crew crashed or was killed while it ran. A run that succeeded is never resumed, and an action of another stage never resumes it, even when the two actions share a name.

The new session gets the action's usual prompt followed by a paragraph from crew. It says that the session continues an earlier session's work in this worktree, on its branch, quotes why that run failed, gives the run's log (`.crew/logs/issue-42-development.log` in the main checkout, `../../logs/issue-42-development.log` from the worktree), and tells the session to check the worktree's state with `git` before going on. The new session's output goes into the same log, after this line:

```json
{"type":"crew","subtype":"resumed","time":"2026-10-02T21:05:00Z"}
```

The event lines, the live view and the status comment say that the action resumed and name its worktree. A resumed run is judged like any other. When it fails, the next relabel resumes it again; there is no limit.

To start over instead, remove the worktree before you relabel the issue:

```sh
git worktree remove --force .crew/worktrees/issue-42-development
```

crew then creates a new worktree, `issue-42-development-2` while the old branch exists, and says so in its output. The old branch, and any pull request from it, are yours to clean up.

crew knows how runs ended from its run journal, `.crew/logs/runs.jsonl`, so a resume works after a restart. Runs that ended before your crew version had the journal are not in it, so their actions start over. Renaming a stage or an action in the config starts its actions over too.

If crew was killed, for example with SIGKILL, its sessions can outlive it. Make sure none still runs in the worktree before you relabel the issue, or two sessions will work in it.

### The status comment

Each issue crew takes gets one status comment, created when crew takes it. It keeps one entry per stage run, oldest first: a stage run starts when a stage takes the issue, and ends when the next one starts. crew edits only the latest entry, and earlier entries keep the text they had when their stage ended, across restarts. An entry shows where the issue stands:

- **Running:** the stage, each action as running, succeeded or failed, how long each running action has run, the last thing its session said, and when crew updated the entry. An action that [resumed](#resume-a-failed-action) names its worktree, as in "**`development`** resumed in worktree `issue-42-development` and has been running for 5 minutes." crew updates it at every poll. An action whose check runs, or whose pull request crew is looking up, is still running.
- **Ended:** each action's final state, and where the issue went: the stage's `on_success` or its `on_failure`, including when you stopped crew. Each failed action says why in crew's words, with its log: its session failed, crew stopped it, its workspace could not be created, its session could not start, or its prompt did not render. A failed check shows its reason, as in the example below.
- **With `config.usage_in_status: true`:** each ended action whose session started also shows its cost and tokens, as the [run journal](#where-things-go) records them, and its pull request, linked, as in "**`development`** succeeded. Usage: $12.40, 48.4M tokens. Pull request: #45." A value the harness did not report says so, and a sum that misses one is marked partial. Without the setting, the comment shows none of this.

````markdown
<!-- crew:entry run=20261002T130112.000000000Z.1 kind=ended stage=implement -->
crew: `implement` ended on #42.

**`acceptance`** succeeded.

**`development`** failed: `the check failed: no open pull request from crew/issue-42-development`. Its log is `.crew/logs/issue-42-development.log`.

#42 moved to `needs attention`.

Updated 2026-10-02 13:58 UTC.

---

<!-- crew:entry run=20261002T140112.000000000Z.2 kind=running stage=implement -->
crew: `implement` is running on #42.

**`acceptance`** succeeded.

**`development`** has been running for 42 minutes. It last said:

```text
U1 committed: 168 tests pass. Starting U2.
```

Updated 2026-10-02 14:43 UTC.

<!-- crew:status -->
````

The hidden lines mark the entries and the comment. The session's words have your repository's path written as `.` and your home directory as `~`, and sit in a code block, so nothing in them renders or mentions anyone. Editing a comment notifies no one; the failure report is what notifies you.

crew finds its comment again after a restart by the hidden last line, among the comments of your `gh` login and of the configured mates, and keeps what it holds. An entry left running by a crew that crashed or was killed says that crew stopped following that stage once the next stage run starts. A comment written before crew kept entries becomes the first entry. A queued entry that an earlier crew version wrote, while the issue waited for a free slot, becomes the running entry when crew takes the issue for that stage. Edits you make by hand inside the comment are not kept.

A comment that would grow past GitHub's limit of 65,536 characters is left as it is, and crew continues in a new status comment that says so. So does a comment another login wrote, such as yours before you named a default mate: crew does not edit it and continues as the login it now writes as. From then on, crew writes only to the new one. If you delete the comment, crew creates a new one at its next update. An issue crew handled before it had status comments gets none until crew takes it again. crew does not touch the comment of an issue it does not take, so a queued entry an earlier version left there stays as it is.

### The pull requests

crew does not open, review or merge pull requests. A stage with `takes: pull_requests` takes a pull request that carries its label, as a stage takes an issue: see [A pull request as the work](#a-pull-request-as-the-work). crew also writes to the pull requests that belong to an issue, so the pull request list shows where crew holds the work and whether anyone still watches it.

- **Which:** the open pull requests in the repository that GitHub links as closing the issue, whoever opened them. That is the `Closes #42` line in the pull request's body, so keep it in the prompts that open pull requests. Merged and closed pull requests, and pull requests in other repositories, are left alone. An issue without such a pull request gets nothing.
- **The label:** each time crew moves the issue, it gives each of those pull requests the issue's new crew label and removes every other crew label, extras included, as on the issue. Your other labels stay. The mirror goes one way: a crew label you put on a pull request by hand is replaced at the issue's next move.
- **The stop comment:** when a stage ends, after the issue moved, crew posts a new comment on each of those pull requests, so GitHub notifies you. In a crew session the session's watch over the pull request has ended with the session, so the comment says nobody watches it any more:

```markdown
crew: `development` failed on #42, which moved to `crew:failed`, as did this pull request.

**`lfg`** failed: crew stopped it. Its log is `.crew/logs/issue-42-lfg.log`.

Nobody watches this pull request any more: new review comments and CI failures need a person.

#42's [status comment](https://github.com/you/repo/issues/42#issuecomment-123) has the details.
```

A stage that succeeded says `succeeded` and lists no action. Like the failure report, the comment carries nothing a session said. A rerun of the stage posts a new comment when it ends.

A pull request opened while a stage runs gets its label at the issue's next move, usually the stage's end. A merged pull request keeps the last label it got, such as `ready to review`. crew does not clean it up. A pull request that closes several issues carries the label of the issue crew moved last.

#### A pull request as the work

A stage with `takes: pull_requests` takes an open pull request that the boss or a mate opened and that carries its `label`, as a stage that takes issues takes an issue. A stage without `takes` takes issues only: crew leaves a pull request carrying its `label` alone, and says so (step 3 of [each poll](#what-crew-does-on-each-poll)). crew moves the pull request through the stage's labels, runs the stage's actions on it, and keeps a status comment and, when the stage fails, a failure report on it. Its [prompt fields](#prompts) are the pull request's. A pull request has no priority and is never blocked.

- **Swap the label, don't add one:** a pull request that closes an issue crew moved already carries that issue's crew label, and a pull request with two crew labels is skipped. Replace the mirrored label with the `label` of a stage that takes pull requests.
- **Nothing is mirrored from it:** moving a pull request gives no other pull request a label and posts no stop comment, since a pull request closes no issue.
- **The issue's moves still reach it:** when the issue it closes moves, the mirror replaces the label crew gave the pull request with the issue's. And when an issue moves to a stage's `label`, such as `on_success: ready to review` in the example, its pull requests get that label too. A stage that takes issues, like `review` there, takes the issue and leaves each pull request alone with a notice. A stage with `takes: pull_requests` takes the pull requests, and the issue, which keeps that label, gets the notice. Keep the labels your issues move to apart from stage labels unless you want that.

### Where things go

For action `development` on issue #42:

| What | Where |
| --- | --- |
| Worktree | `.crew/worktrees/issue-42-development` |
| Branch | `crew/issue-42-development`, not pushed by crew |
| Session log | `.crew/logs/issue-42-development.log` |
| Run journal | `.crew/logs/runs.jsonl`, for every run |

The name is the issue's key and the action's name, lowercased, with anything outside `a-z`, `0-9` and `-` turned into `-`. When a name is taken, crew adds `-2`, `-3` and so on. A resumed action keeps its worktree, branch and log. crew never removes worktrees: they are your evidence when an issue needs attention, and a failed action resumes in its own. Remove them with `git worktree remove` when you are done.

The run journal has one JSON line when a run's worktree is ready and one when its action ends, whatever its outcome. crew only appends to it, and never rewrites or trims it, so it holds every run of every crew process in this repository. For example:

```json
{"v":1,"event":"started","time":"2026-10-02T20:08:28Z","run":"2026-10-02T20:08:20.344209367Z","issue":"42","ref":"#42","stage":"implement","action":"development","workspace":"issue-42-development","branch":"crew/issue-42-development","log":".crew/logs/issue-42-development.log"}
{"v":1,"event":"ended","time":"2026-10-02T21:05:00Z","run":"2026-10-02T20:08:20.344209367Z","issue":"42","ref":"#42","stage":"implement","action":"development","workspace":"issue-42-development","branch":"crew/issue-42-development","log":".crew/logs/issue-42-development.log","succeeded":true,"reason":"done","duration_ms":3390000,"cost_usd":12.4,"input_tokens":450,"output_tokens":184862,"cache_read_tokens":46816709,"cache_write_tokens":1364924,"turns":64,"models":["claude-opus-5-5","claude-sonnet-5-5"],"pull_request":"#45","pull_request_url":"https://github.com/you/repo/pull/45","pull_request_lookup":"found"}
```

| Key | What it holds |
| --- | --- |
| `run` | The crew process the line belongs to: when it started, in UTC. Every line of one run of `crew` has the same value. |
| `succeeded`, `reason` | The action's outcome and its one-line reason, with your repository's path written as `.` and your home directory as `~`. |
| `duration_ms` | Milliseconds from the session's start to the action's end, its check included. Left out when no session started, as when its worktree could not be created. |
| `cost_usd` | The session's cost in US dollars, exactly as the harness reports it. With `claude` it is Claude Code's `total_cost_usd` at API prices, an estimate on a subscription. |
| `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_write_tokens` | The session's tokens by kind, its subagents included. |
| `turns` | The session's turns. With `claude`, the main session's turns, not its subagents'. |
| `models` | The models the session used. |
| `pull_request`, `pull_request_url` | The pull request crew found from the action's branch. |
| `pull_request_lookup` | `found`, `none` when the branch has no pull request, or `not looked up` when the tracker cannot look or the lookup failed. |

A key the harness did not report is left out of the line, never written as zero. A session crew stopped, or one that was killed or crashed before its final result, reports none of them. An action that never got a worktree has an `ended` line with no `workspace`.

crew finds the pull request with `gh pr list --head <branch>`, once the action's session ends, for up to 15 seconds: an open one from your repository first, otherwise the newest closed or merged one created since the worktree was made. A pull request opened from another branch than the action's is not found. A missing pull request changes nothing about the action's outcome; a [check](#checks) is how you fail it.

crew computes no totals across runs. Read the journal with your own tools, for example the cost of each ended action as CSV:

```sh
jq -r 'select(.event == "ended") | [.time, .run, .ref, .stage, .action, .succeeded, .cost_usd, .output_tokens, .pull_request] | @csv' .crew/logs/runs.jsonl
```

A run with a `started` line and no `ended` line was cut short by a crash or a kill, including a second ctrl+c. crew stops before polling when it cannot read the journal, and says in its output when it cannot write to it.

Add crew's local files to `.gitignore`, and keep `.crew/config.yaml` committed:

```text
.crew/logs/
.crew/worktrees/
```

## Run it

Run `crew` anywhere inside the repository's main checkout. In one of crew's worktrees, it would take that worktree for the repository.

```sh

```

While crew loads `.crew/config.yaml` and runs its [checks](#when-crew-refuses-to-start), it prints a boot log: one line as each step starts, before anything else. A step done once per item, a mate or a missing label, gets a line for each, and a step that does not run, such as making mates act when the config names none, gets no line.

```text
14:22:41 crew: loading .crew/config.yaml
14:22:41 crew: resolving the repository for the mates
14:22:42 crew: checking git for the mates
14:22:42 crew: making a private directory for the mates' tokens
14:22:42 crew: making mate developer act
14:22:43 crew: checking the gh login
14:22:44 crew: finding the boss
14:22:44 crew: reading the repository's labels
14:22:45 crew: creating the label "crew:triage:ready"
14:22:45 crew: looking for claude on PATH
14:22:45 crew: checking the git checkout and its origin
14:22:45 crew: resolving origin's default branch
14:22:46 crew: reading the run journal
```

crew prints the boot log on every start, with the live view and with `--plain` alike. Its last line names what crew is waiting on, so a slow start never looks like a hung one. When the checks pass, the live view or the event lines take over; the live view does not repeat the boot log.

The header shows the repository, how long crew has been up and, with `config.run_time_limit_seconds`, how much run time is left, then the cost and tokens of every session that ended since crew started. Startup warnings stay under it for as long as crew runs, and so does a warning about a [mate that stopped acting](#when-a-mate-cannot-act) while it does. Each section opens with its title and a rule that ends in a short summary. Colours follow the terminal's background, light or dark; with `NO_COLOR`, or on a terminal without colour, the titles, icons and labels still tell everything apart. Issue and pull request numbers link to their page in terminals that support links.

Mates has two rows for each mate the config names, the default mate first, then a row for you, labelled with the `gh` login crew acts as when it acts as you. The section shows even when the config names no mate, with your row alone, and its summary counts the mates that act and those that do not. A mate's first row shows its state, `acting`, `cannot act` with a short reason, `writes as you` or `token not renewed`, then what its actions that ended since crew started cost: how many, their cost and their tokens, in the same words as Handled. An action counts on the identity it acted as, so the actions of a mate that cannot act count on your row. The second row lists the stages and actions that act as it, as `stage/action`, starts with `crew's writes` on the row crew's own writes go as, and ends, after `▸`, with the actions running as it now, from the start of their session until they end, their check included. A row that does not fit the window ends in `…`. No key acts on a mate: `crew mates create` creates or fixes one.

Workflow has one column per stage of your workflow, in the order of `.crew/config.yaml`, and a card for each issue crew has in play. A card shows the issue's number and title, and how crew holds it: `⠋ running`, `◌ taking`, `⠋ judging`, `! owed` while a move waits for a retry, or `■ stopping`. When a stage ends and moves the issue to another stage's `label`, the card stays in its column with `→` and that label until the next stage takes the issue, then slides to the new column. It leaves the board when the issue moves to a label no stage takes, such as a failed or waiting-review label, when crew gave the move up, or when the issue is closed or relabelled outside crew. Issues crew has not taken, such as those waiting in a `label`, are not on the board: GitHub shows them. A stage with [`on_board: false`](#keys) has no column and its issues no card. When the columns do not fit the window, the empty ones drop and the summary says how many; when the rest still do not fit, the board scrolls sideways with `←` and `→`.

With [`board`](#the-board) in the config, Workflow shows your columns instead, in the file's order, and a card for each open issue with a column's labels, oldest first. crew reads them from GitHub at each poll, even when it is too busy to take an issue. A move crew makes shows at once; a label changed on GitHub, or an issue closed there, shows after the next poll. A card shows the issue's number and title, and how crew holds it while it does; a card of an issue crew does not hold shows its number and title alone. No card waits with `→`: a card sits wherever the issue's labels put it, and slides when they move it to another column. A column with more cards than fit ends in `+N more`, hiding the newest. The summary counts the issues with a card, and says `board not read` while the last read from GitHub failed; the board then keeps what it last read. Empty columns drop and the board scrolls as above.

Actions lists every action that has not ended: its issue, its stage and action, the [queue](#queues) its issue holds a slot in, its state with the elapsed time, and its branch. A running session shows the last thing it said on the line under it, with tokens and keys redacted, as in the [status comment](#the-status-comment). Queues shows each queue's busy slots `■` and free slots `□`. A slot is busy from the moment crew takes an issue for a stage in that queue until it lets go of the issue, whether the issue's actions have started or not, which is the count crew uses to decide whether the queue can take another issue.

Handled lists each issue whose stage ended: a label saying how it ended, its number and title, the stage and how long it took, the cost and tokens of the stage's sessions, and the pull request of a stage with one action. The issues that need you come first: `NEEDS ATTENTION` for a stage that failed, with one line per failed action and its reason after `×`, and `GIVEN UP` for a move crew gave up because the issue was closed or moved meanwhile or GitHub refused it. Any other ending shows the last part of the label the issue moved to, such as `WAITING REVIEW`. A stage with several actions shows each action's pull request on a line of its own. An issue shows once, with its latest stage, and stays there while a stage holds it again, with `now in` and that stage after its details. While a stage holds it again, a failed entry shows the last part of its label, such as `FAILED`, instead of `NEEDS ATTENTION`, and no longer counts as needing you: you already sent it back. A stage with [`on_board: false`](#keys) that ends well keeps the entry it found when that one ended well too, so a promote stage does not replace the stage before it. The header still counts what every stage cost. The status comment on each issue keeps the detail. Handled covers this run only: it starts empty each time crew starts, and nothing of it is saved.

The cost is the harness's figure, shown as it reports it and always next to the tokens, which add up all four kinds the [run journal](#where-things-go) keeps apart. A stage where some session reported no cost shows the known cost marked `(partial)`, and one where none did says `cost not reported`. A running action shows no cost: its numbers appear once it ends. An action that never had a session adds nothing and shows no pull request.

Events shows the latest 100 events, the newest at the bottom.

Events and Handled each take five rows, however many they have, so the view holds still while crew works. Their rows fill from the top, with blank rows below until there are five. Past five, the section scrolls, and its title says `↑↓ scroll`. Events follows the newest event until you scroll up.

The view fits the window. When rows run out, Events and then Handled give up rows, as many as the window needs and down to two each. Then the session lines under Actions go, then each board column shows fewer cards with `+N more`, then each Mates row drops its second line, and only then is the view cut, with a line saying how many lines were cut. The keys:

| Key | What it does |
| --- | --- |
| `q`, Ctrl-C | Stop crew; a second press forces the exit. See [Stop it](#stop-it). |
| `tab`, `shift+tab` | Move the focus between Handled and Events. The focused section's title has a `▸`. |
| `↑` `↓` or `k` `j`, `pgup` `pgdown`, `home` `end` | Scroll the focused section. Events follows the newest event until you scroll up, and again from `end`. |
| `←` `→` or `h` `l` | Scroll the board sideways. |
| `?` | Show the keys, and hide them again. |

No key acts on an issue, a pull request, a workspace or a log.

crew also tells the terminal what it is doing, where the terminal supports it. The tab title reads like `crew · 2 running · 1 waiting · 1 needs attention`, or `crew · idle`, `crew · stopping` or `crew · winding down`. The tab's progress indicator shows activity while actions run, and an error while an issue in Handled needs you. A failed issue that a stage holds again does not count in either. While the terminal is not focused, each stage that ends sends a desktop notification saying how it ended. Stages with `on_board: false` send none, and nothing is sent once you asked crew to stop. Notifications use OSC 9, which terminals such as iTerm2, WezTerm, Ghostty and Windows Terminal show, and tmux does not pass on. crew knows the terminal is not focused only when the terminal reports focus, so a terminal that never does gets no notification.

With `--plain`, or when the output is not a terminal, crew prints one line per event instead, after the boot log and any startup warnings:

```text
14:22:58 crew: implement took #42 "Add login form" (ready -> in progress)
14:22:58 crew: poll: listed 1 issue, took 1
14:22:59 crew: #42 moved from ready to in progress
14:23:04 crew: #42 implement/acceptance started on branch crew/issue-42-acceptance, log .crew/logs/issue-42-acceptance.log
```

When a mate stops acting while crew runs, a line names it with the warning the live view shows under its header, such as `mate developer stopped acting: mate developer could not renew its token: …`, and `mate developer acts again: its token renewed` when it recovers.

`crew --version` prints the version: the release's tag for a downloaded release or a `go install …@vX.Y.Z` build, and `dev` for a build that records no version.

### Stop it

Press Ctrl-C (or `q` in the live view), or send SIGTERM or SIGHUP. Closing the terminal crew runs in sends SIGHUP. crew stops cleanly:

1. It starts nothing new.
2. Issues whose actions have all ended are judged as usual.
3. Running sessions and checks get 10 seconds to stop before they are killed. Their issues move to their stage's `on_failure`, with a comment saying crew stopped them, and their status comments show the move. Their open pull requests get the `on_failure` label and a comment saying the stage failed because crew stopped it. When `on_failure` is another stage's `label`, such as `ready`, that stage takes the issue again at the next poll.
4. Moves and comments still owed, on issues and pull requests, get one last try.

This can take a while if GitHub is slow: every `gh` and `git` call has up to 10 minutes. Press Ctrl-C (or `q`) again, or send a second SIGTERM or SIGHUP, to force the exit. crew kills every process it started and exits at once, so the issues it was working on stay in their `moves_to` state until you relabel them.

If crew's output goes to a pipe that closes, for example `crew | head`, crew stops cleanly the same way and exits with 1.

The checks crew runs when it starts have the same 10 minutes. Past them, or on Ctrl-C, SIGTERM or SIGHUP meanwhile, crew kills every process it started and exits with 2, before its first poll.

### Run it for a set time

Set `config.run_time_limit_seconds` to start crew for a set time, such as overnight. The time counts from the first poll, so the checks crew runs when it starts do not use it up. When the time is up, crew winds down:

1. It takes no new issue, even one that is `ready`.
2. Sessions and checks already running go on until they end, and their issues are judged as usual. No issue goes to its stage's `on_failure` because of the limit.
3. Moves and comments still owed get their last try, as when you stop crew.
4. crew exits with 0.

crew says it is winding down, in the live view and with `--plain`:

```text
06:22:58 crew: run time of 8h0m0s is up: taking no new issues, winding down
```

A session that runs long keeps crew running past the limit, and so does a move that keeps failing while crew takes an issue, until GitHub answers. Press Ctrl-C (or `q`), or send SIGTERM or SIGHUP, to stop it the usual way: running sessions get 10 seconds to stop, and their issues move to their stage's `on_failure`. A second one forces the exit.

### Exit codes

| Code | When |
| --- | --- |
| `0` | crew stopped cleanly, or wound down after its run time. |
| `1` | crew failed while running, or you forced the exit. |
| `2` | The config, a flag or the environment is wrong; nothing was polled. |

`crew mates create`, which gives crew GitHub identities of its own, has its own exit codes: see [Mates](/guide/mates#exit-codes).

## Limits

- **CODEOWNERS is read at startup.** A change to who the boss is takes effect when crew restarts.
- **One crew per repository.** Two crews in one repository take the same issues. Nothing stops you from starting a second one.
- **No recovery after a crash on its own.** An issue left in a `moves_to` state, such as `in progress`, by a crash or a forced exit stays there until you relabel it, and its status comment keeps saying its actions run until its next stage run starts. Relabeling it with its stage's `label` resumes its actions in their worktrees.
- **No time limit on a session.** A session runs until it ends or you stop crew. `config.run_time_limit_seconds` limits crew, not its sessions: it does not cut a running session short.
- **No retries on its own.** crew never runs a failed action, or one whose check failed, again by itself. Relabeling the issue is the retry, and it resumes the failed action. Two stages whose `on_failure` is each other's `label` would hand an issue back and forth with no one relabeling it, resuming each time.
- **Only `github` and `claude`.** Other trackers and coding agents are not built yet.
- **Not built yet from the old dispatcher:** pausing and resuming on usage limits, promoting to `ready to merge` when pull requests pass their checks, and per-stage progress.
- **At most 100 issues per poll**, the oldest first. With more waiting, a newer issue of high priority is not seen until older ones leave the list.
- **At most 100 issues per author on the [board](#the-board)**, the oldest first. With more open issues on its labels, the newest do not show.
- **Priority decides only the next free slot.** It never stops a running session to make room for a higher-priority issue, and it never moves an issue into another queue's free slot.
- **Sessions are headless.** They cannot ask you anything or talk to each other. The [acceptance tester](/guide/acceptance-tester) agent is interactive, so do not point an action at it.
