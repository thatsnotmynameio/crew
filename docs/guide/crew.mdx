# crew

crew moves your issues through a workflow you declare in the repository. It polls GitHub for the issues you labeled, and for each one it runs the stage's actions in parallel. Each action is a headless Claude Code session in its own git worktree and branch. When every action ends, crew moves the issue on, or to the stage's failure label with a comment saying what failed.

crew only runs sessions and moves labels. Opening a pull request, reviewing and merging are your prompts' job and yours.

## Install

You need Go 1.27 or later:

```sh
go install github.com/thatsnotmynameio/crew/cmd/crew@main
```

This puts `crew` in `$(go env GOPATH)/bin`. Install from `@main` for now: the only release, `v0.1.0`, predates crew's Go code. From the next release on, `@vX.Y.Z` works too.

## Before you run it

- **macOS or Linux.** crew starts every tool in its own process group, which Windows does not have.
- **A git repository with an `origin` remote on GitHub.** crew branches each action from origin's latest default branch.
- **`gh`, logged in** (`gh auth login`), with permission to edit the repository's issues and labels.
- **`claude` on your `PATH`**, logged in.

crew checks all of this when it starts and stops with a message if something is missing.

## Configure it

crew reads `.crew/config.yaml` at the root of the repository. Commit it. Here is a complete example:

```yaml
config:
  poll_interval_seconds: 300
  max_parallel_issues: 2
  harness: claude
  model: claude-opus-5-5
tracker:
  name: github
workflow:
  - name: implement
    label: ready
    moves_to: in progress
    on_success: ready to review
    on_failure: needs attention
    actions:
      - name: acceptance
        prompt: >-
          Write the acceptance tests for issue {{.Issue.Ref}} ({{.Issue.URL}}).
          Take the acceptance examples from the issue and ask nothing: nobody
          answers questions in this session. Open a pull request with the tests.
      - name: development
        prompt: >-
          Implement issue {{.Issue.Ref}}, "{{.Issue.Title}}" ({{.Issue.URL}}).
          Open a pull request with the change. This session is headless:
          ending your turn ends the session. Never end a turn waiting on a
          background command; run it in the foreground, or wait for it with
          Monitor.
        check: >-
          gh pr list --head "$CREW_BRANCH" --state open --json number --jq length
          | grep -qv '^0$' || { echo "no open pull request from $CREW_BRANCH"; exit 1; }
  - name: review
    label: ready to review
    moves_to: in review
    on_success: ready to merge
    on_failure: needs attention
    actions:
      - name: custom_review
        prompt: "Review the pull requests for issue {{.Issue.Ref}} and leave your review on them."
```

With it, an issue labeled `ready` gets two sessions at once, `acceptance` and `development`, and moves to `in progress`. When both succeed, it moves to `ready to review`, where the `review` stage takes it. When either fails, it moves to `needs attention`. `development` succeeds only when its [check](#checks) finds an open pull request from its branch. Here `on_success: ready to merge` only means "reviewed": crew does not merge anything.

Sessions run with no one to answer them, so tell the agent not to ask. A session that asks a question and stops counts as a success. That is why the `acceptance` prompt tells it to take the examples from the issue.

Ending a turn also ends the session, and nothing resumes it. A session that ends its turn to wait for a background command, such as a test run, is stopped there and counts as a success. That is why the `development` prompt tells it to run commands in the foreground or wait for them with Monitor.

### Keys

Everything but `workflow` is optional. A minimal file is a `workflow` alone.

| Key | Default | What it does |
| --- | --- | --- |
| `config.poll_interval_seconds` | `300` | Seconds between polls. Must be positive. |
| `config.run_time_limit_seconds` | none | How long crew runs, counted from its first poll, before it winds down (see [Run it for a set time](#run-it-for-a-set-time)). Must be positive: `28800` is 8 hours. Without it, crew runs until you stop it. |
| `config.max_parallel_issues` | `2` | How many issues crew works on at once. It counts issues, not sessions: an issue whose stage has two actions takes one slot. |
| `config.usage_in_status` | `false` | Adds each ended action's cost, tokens and pull request to the [status comment](#the-status-comment). |
| `config.harness` | `claude` | The coding agent that runs sessions. `claude` is the only one today. |
| `config.model` | `claude-opus-5-5` | The model every session runs, passed to `claude --model`. |
| `tracker.name` | `github` | Where issues live. `github` is the only one today. |
| `harness` | none | A top-level section for harness-specific settings. `claude` takes none, and the model goes in `config.model`. |
| `extra_labels` | none | Labels for parked work that no stage takes, such as an idea waiting for a brainstorm. See below. |
| `prompts` | none | Named prompts that a skill runs in your own Claude Code session, such as `brainstorm` for [`/cw-brainstorm`](/guide/create-issue#brainstorm-an-issue). See [Prompts](#prompts). |
| `workflow` | required | The stages, at least one. |

Each stage has:

| Key | What it does |
| --- | --- |
| `name` | The stage's name, unique in the workflow. |
| `label` | The label the stage takes issues from. No two stages take the same label. |
| `moves_to` | The label the issue carries while the actions run. It cannot be any stage's `label`, or that stage would take the issue too. |
| `on_success` | The label the issue moves to when every action succeeded. It cannot be the stage's own `label`. |
| `on_failure` | The label the issue moves to when any action failed, with crew's comment. It cannot be the stage's own `label`, but it can be another stage's: `on_failure: ready` on the `review` stage sends a failed review back to `implement`. |
| `actions` | At least one action, each with a `name` (unique in the stage), a `prompt`, and optionally a `check` (see [Checks](#checks)). |
| `description` | Optional. The work the stage takes, in a few words, such as `a bug to reproduce and fix`. crew does not use it: the [`/cw-create-issue`](/guide/create-issue) skill shows it when it lists the types of issue. |
| `issue_template` | Optional. The file name of a Markdown issue template in `.github/ISSUE_TEMPLATE/`, such as `bug.md`. crew does not use it: `/cw-create-issue` fills it for an issue of this stage. |

`label`, `moves_to`, `on_success` and `on_failure` hold the label as it is written on GitHub, such as `in progress`. Any text works. GitHub does not tell labels apart by case, so neither does crew: `Ready` and `ready` are the same label in every rule above, and crew writes a label everywhere as you first wrote it in the file.

A stage whose `on_success` or `on_failure` is its own `moves_to` leaves the issue where it is when it ends. On failure crew still comments.

Each item of `extra_labels` has:

| Key | What it does |
| --- | --- |
| `label` | Required. The label, written as on GitHub. It cannot be a label any stage names in `label`, `moves_to`, `on_success` or `on_failure`, or another extra's label. |
| `description` | Optional, as for a stage. |
| `issue_template` | Optional, as for a stage. |

```yaml
extra_labels:
  - label: waiting brainstorm
    description: an idea to brainstorm later
    issue_template: idea.md
```

The label above is an example. Extra labels, `description` and `issue_template` serve the author's own workflow with [`/cw-create-issue`](/guide/create-issue), so they may still change.

crew's labels are the ones your stages name in `label`, `moves_to`, `on_success` and `on_failure`, plus the extra labels, and no others. Every other label on an issue is yours: crew ignores it and never removes it.

An extra label parks an issue that no stage takes, such as an idea that waits for a brainstorm. No stage takes an issue whose only crew label is an extra. To start work on it, add a stage's `label`: that stage takes the issue at the next poll, even with the extra still on it. Every move crew makes removes the extras an issue carries, together with its other crew labels, so the issue leaves the extra behind when a stage takes it.

So declare as an extra only a label you keep for crew. If you declare a label you already use, such as `bug`, crew removes it from every issue it moves.

### Prompts

A prompt is a Go template over the issue:

| Field | On GitHub |
| --- | --- |
| `{{.Issue.Ref}}` | `#42` |
| `{{.Issue.Key}}` | `42` |
| `{{.Issue.Title}}` | the issue's title |
| `{{.Issue.URL}}` | the issue's web address |

Any other field is an error when crew starts. Quote the prompt or use a block (`>-`) as in the example: in YAML, a value that starts with `{` is not a string.

The top-level `prompts` maps a name to a prompt that a skill runs, not crew. Some work needs you at the keyboard, such as a brainstorm, so it cannot be an unattended action. [`/cw-brainstorm`](/guide/create-issue#brainstorm-an-issue) fills `prompts.brainstorm` with an issue and runs it in your session:

```yaml
prompts:
  brainstorm: |-
    /compound-engineering:ce-brainstorm {{.Issue.Ref}}
```

[`/cw-update-issue-plan`](/guide/create-issue#put-a-plan-in-an-existing-issue), run without a label, runs `prompts.update_issue_plan` the same way once it has put the plan in the issue, for example to move the issue to the label that always comes next.

crew checks these prompts as it checks an action's, with the same fields, and then ignores them. `prompts` serves the author's own workflow, so it may still change.

### Checks

An action's `check` is a shell command crew runs after the action's session succeeded, to see that the work exists:

```yaml
      - name: development
        prompt: "Implement {{.Issue.Ref}} and open a pull request that closes it."
        check: >-
          gh pr list --head "$CREW_BRANCH" --state open --json number --jq length
          | grep -qv '^0$' || { echo "no open pull request from $CREW_BRANCH"; exit 1; }
```

- **Where it runs:** with `sh -c`, in the action's worktree, once its session has ended. A session that failed runs no check.
- **What it gets:** your environment, plus `CREW_ISSUE_REF` (`#42`), `CREW_ISSUE_KEY` (`42`), `CREW_ISSUE_URL` and `CREW_BRANCH` (the worktree's branch, such as `crew/issue-42-development`). The check is not a template: write `$CREW_ISSUE_REF`, not `{{.Issue.Ref}}`. No issue text, such as the title, ever becomes part of the command.
- **How it passes:** it exits with 0. It fails when it exits with anything else, cannot start, or runs for more than 10 minutes, a limit you cannot change. A failed check fails the action, as a failed session does: the issue moves to `on_failure`, and crew does not run the action again.
- **Its output:** stdout and stderr go to the action's log, after the session's. The reason crew gives is `the check failed:` followed by the last line the check printed, from stdout or stderr. That line goes into the issue's [status comment](#the-status-comment), which may be public. So keep your tools' output out of the last line, and end a failing check by echoing its own one-line reason, as above. A check that runs out of time or cannot start says so instead.
- **What it trusts:** the check runs in the worktree the session wrote. A check that calls a script from the repository runs the session's copy of it. The check catches a session that stopped early, not one that tries to fool it.

When you stop crew, a running check is ended too, and its action counts as stopped. When the run time is up, a running check runs to its end.

### What "succeeded" means

An action succeeded when its session ended cleanly, Claude Code's last result is not an error and `claude` exited with 0, and its check, if it has one, passed. Without a check, crew does not look for a pull request or any other evidence of the work.

So a session without a check can succeed without doing its work. For example, `--permission-mode auto` denies a tool, and the agent gives up politely, or the session ends its turn while a command runs in the background. Give such actions a check that looks for the work, write prompts that say what done looks like, and read the last message crew prints for every action that ends, successes included.

To make an early end less likely, crew starts `claude` with a Bash timeout of 10 minutes by default and 30 at most (`BASH_DEFAULT_TIMEOUT_MS` and `BASH_MAX_TIMEOUT_MS`), instead of Claude Code's 2 and 10. A Bash command that outlives its timeout moves to the background, so a full test run now stays in the foreground. They win over the same variables in the environment you start crew in.

### When crew refuses to start

Before its first poll, crew checks the whole file and its tools. It stops, exiting with 2, when:

- a key is unknown, or a value has the wrong type (the message names the key and its line);
- `config.harness` or `tracker.name` names an adapter that does not exist;
- a stage lacks `label`, `moves_to`, `on_success` or `on_failure`;
- the workflow would loop or take an issue twice (the `label`, `moves_to`, `on_success` and `on_failure` rules above);
- an extra label is a label a stage names, or another extra's label, ignoring case;
- a `description` is empty, or an `issue_template` is not a file name ending in `.md` (it holds a `/` or `\`, for example). crew does not check that the template file exists;
- a prompt, in an action or under `prompts`, is empty, does not parse, or uses a field that does not exist;
- an action's `check` is present but empty;
- `gh` is missing or not logged in, `claude` is not on your `PATH`, or the repository has no `origin`;
- the checks take more than 10 minutes, or you stop crew during them.

At the same check, crew creates the labels your workflow names and the extra labels that the repository does not have yet, each `on_failure` label included, and no other.

## What crew does on each poll

1. It lists the open issues **you** opened that carry a stage's `label`. Issues other people opened are ignored, whatever their labels, and so are issues whose only crew label is an extra.
2. It skips an issue that carries two crew labels, such as `ready` and `needs attention`, and says so. Remove one, and a later poll takes it. Extra labels do not count, and neither do labels no stage names: an issue labeled `paused` and `ready` is taken when no stage names `paused`, and so is one labeled `waiting brainstorm` and `ready` when `waiting brainstorm` is an extra.
3. It skips an issue that an open issue blocks, as GitHub records it under the issue's relationships ("blocked by"). The issue keeps its label, and a later poll takes it once every issue blocking it is closed. crew writes no status comment for it while it is blocked; one queued before it became blocked keeps its last status comment.
4. It takes issues while slots are free: later stages first, so reviews are not starved behind new work, then the oldest issue first. An issue left waiting gets a [status comment](#the-status-comment) saying it is queued for its stage.
5. Taking an issue moves it to the stage's `moves_to`. A move removes every other crew label, extras included, and adds the new one, and leaves your other labels alone.
6. For each action, crew creates a worktree and a branch from origin's latest default branch, and starts a session there with the action's prompt. When the last run of that action, in that stage, on that issue failed, crew [resumes it](#resume-a-failed-action) in that run's worktree instead.
7. While the actions run, crew updates the issue's status comment at every poll.
8. When every action of the issue has ended, its check included, crew judges it. If all succeeded, the issue moves to `on_success`. Otherwise it moves to `on_failure`, and crew comments on the issue.

This failure report is a new comment, apart from the status comment, so GitHub notifies you of it. It names each failed action and its log, relative to the repository:

```markdown
crew: 1 action failed on #42.

**`development`** failed. Its log is `.crew/logs/issue-42-development.log`.
```

The comment carries nothing the session said: no last message, no commands, no output. Why an action failed is in its log, in crew's output and, in crew's own words, in the status comment. An action whose worktree could not be created has no log, and the comment says it failed before it had a log.

A move or comment that fails, for example because GitHub is down, is retried at every poll and once more when crew stops. One that cannot work, because the issue was closed or relabeled meanwhile, is dropped and reported. A status comment that says an issue is queued or running is not retried: the next poll writes it again.

To retry a failed issue, swap its `on_failure` label, such as `needs attention`, for the stage's `label`, such as `ready`. Each failed action then resumes where it stopped, and each action that succeeded starts over.

### Resume a failed action

When a stage takes an issue, crew looks at the last run of each of its actions on that issue. When that run failed, the action resumes: crew runs a new session in the failed run's worktree, on its branch, with the commits and uncommitted files it left. crew does not fetch, merge or rebase the default branch into it. A run counts as failed when its action failed for any reason: the session failed, its check failed, crew stopped it, it failed to start, or crew crashed or was killed while it ran. A run that succeeded is never resumed, and an action of another stage never resumes it, even when the two actions share a name.

The new session gets the action's usual prompt followed by a paragraph from crew. It says that the session continues an earlier session's work in this worktree, on its branch, quotes why that run failed, gives the run's log (`.crew/logs/issue-42-development.log` in the main checkout, `../../logs/issue-42-development.log` from the worktree), and tells the session to check the worktree's state with `git` before going on. The new session's output goes into the same log, after this line:

```json
{"type":"crew","subtype":"resumed","time":"2026-10-02T21:05:00Z"}
```

The event lines, the live view and the status comment say that the action resumed and name its worktree. A resumed run is judged like any other. When it fails, the next relabel resumes it again; there is no limit.

To start over instead, remove the worktree before you relabel the issue:

```sh
git worktree remove --force .crew/worktrees/issue-42-development
```

crew then creates a new worktree, `issue-42-development-2` while the old branch exists, and says so in its output. The old branch, and any pull request from it, are yours to clean up.

crew knows how runs ended from its run journal, `.crew/logs/runs.jsonl`, so a resume works after a restart. Runs that ended before your crew version had the journal are not in it, so their actions start over. Renaming a stage or an action in the config starts its actions over too.

If crew was killed, for example with SIGKILL, its sessions can outlive it. Make sure none still runs in the worktree before you relabel the issue, or two sessions will work in it.

### The status comment

Each issue crew queues or takes gets one status comment. It keeps one entry per stage run, oldest first: a stage run starts when crew queues the issue for a stage or takes it, and ends when the next one starts. crew edits only the latest entry, and earlier entries keep the text they had when their stage ended, across restarts. An entry shows where the issue stands:

- **Queued:** the stage it waits for, and that it waits for a free slot (`max_parallel_issues`). crew edits it only when that changes.
- **Running:** the stage, each action as running, succeeded or failed, how long each running action has run, the last thing its session said, and when crew updated the entry. An action that [resumed](#resume-a-failed-action) names its worktree, as in "**`development`** resumed in worktree `issue-42-development` and has been running for 5 minutes." crew updates it at every poll. An action whose check runs, or whose pull request crew is looking up, is still running.
- **Ended:** each action's final state, and where the issue went: the stage's `on_success` or its `on_failure`, including when you stopped crew. Each failed action says why in crew's words, with its log: its session failed, crew stopped it, its workspace could not be created, its session could not start, or its prompt did not render. A failed check shows its reason, as in the example below.
- **With `config.usage_in_status: true`:** each ended action whose session started also shows its cost and tokens, as the [run journal](#where-things-go) records them, and its pull request, linked, as in "**`development`** succeeded. Usage: $12.40, 48.4M tokens. Pull request: #45." A value the harness did not report says so, and a sum that misses one is marked partial. Without the setting, the comment shows none of this.

````markdown
<!-- crew:entry run=20261002T130112.000000000Z.1 kind=ended stage=implement -->
crew: `implement` ended on #42.

**`acceptance`** succeeded.

**`development`** failed: `the check failed: no open pull request from crew/issue-42-development`. Its log is `.crew/logs/issue-42-development.log`.

#42 moved to `needs attention`.

Updated 2026-10-02 13:58 UTC.

---

<!-- crew:entry run=20261002T140112.000000000Z.2 kind=running stage=implement -->
crew: `implement` is running on #42.

**`acceptance`** succeeded.

**`development`** has been running for 42 minutes. It last said:

```text
U1 committed: 168 tests pass. Starting U2.
```

Updated 2026-10-02 14:43 UTC.

<!-- crew:status -->
````

The hidden lines mark the entries and the comment. The session's words have your repository's path written as `.` and your home directory as `~`, and sit in a code block, so nothing in them renders or mentions anyone. Editing a comment notifies no one; the failure report is what notifies you.

crew finds its comment again after a restart by the hidden last line, among the comments of the `gh` user it runs as, and keeps what it holds. An entry left running by a crew that crashed or was killed says that crew stopped following that stage once the next stage run starts. A comment written before crew kept entries becomes the first entry. Edits you make by hand inside the comment are not kept.

A comment that would grow past GitHub's limit of 65,536 characters is left as it is, and crew continues in a new status comment that says so. From then on, crew writes only to the new one. If you delete the comment, crew creates a new one at its next update. An issue crew handled before it had status comments gets none until crew queues or takes it again, and an issue whose label you remove while it is queued keeps its last status comment.

### Where things go

For action `development` on issue #42:

| What | Where |
| --- | --- |
| Worktree | `.crew/worktrees/issue-42-development` |
| Branch | `crew/issue-42-development`, not pushed by crew |
| Session log | `.crew/logs/issue-42-development.log` |
| Run journal | `.crew/logs/runs.jsonl`, for every run |

The name is the issue's key and the action's name, lowercased, with anything outside `a-z`, `0-9` and `-` turned into `-`. When a name is taken, crew adds `-2`, `-3` and so on. A resumed action keeps its worktree, branch and log. crew never removes worktrees: they are your evidence when an issue needs attention, and a failed action resumes in its own. Remove them with `git worktree remove` when you are done.

The run journal has one JSON line when a run's worktree is ready and one when its action ends, whatever its outcome. crew only appends to it, and never rewrites or trims it, so it holds every run of every crew process in this repository. For example:

```json
{"v":1,"event":"started","time":"2026-10-02T20:08:28Z","run":"2026-10-02T20:08:20.344209367Z","issue":"42","ref":"#42","stage":"implement","action":"development","workspace":"issue-42-development","branch":"crew/issue-42-development","log":".crew/logs/issue-42-development.log"}
{"v":1,"event":"ended","time":"2026-10-02T21:05:00Z","run":"2026-10-02T20:08:20.344209367Z","issue":"42","ref":"#42","stage":"implement","action":"development","workspace":"issue-42-development","branch":"crew/issue-42-development","log":".crew/logs/issue-42-development.log","succeeded":true,"reason":"done","duration_ms":3390000,"cost_usd":12.4,"input_tokens":450,"output_tokens":184862,"cache_read_tokens":46816709,"cache_write_tokens":1364924,"turns":64,"models":["claude-opus-5-5","claude-sonnet-5-5"],"pull_request":"#45","pull_request_url":"https://github.com/you/repo/pull/45","pull_request_lookup":"found"}
```

| Key | What it holds |
| --- | --- |
| `run` | The crew process the line belongs to: when it started, in UTC. Every line of one run of `crew` has the same value. |
| `succeeded`, `reason` | The action's outcome and its one-line reason, with your repository's path written as `.` and your home directory as `~`. |
| `duration_ms` | Milliseconds from the session's start to the action's end, its check included. Left out when no session started, as when its worktree could not be created. |
| `cost_usd` | The session's cost in US dollars, exactly as the harness reports it. With `claude` it is Claude Code's `total_cost_usd` at API prices, an estimate on a subscription. |
| `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_write_tokens` | The session's tokens by kind, its subagents included. |
| `turns` | The session's turns. With `claude`, the main session's turns, not its subagents'. |
| `models` | The models the session used. |
| `pull_request`, `pull_request_url` | The pull request crew found from the action's branch. |
| `pull_request_lookup` | `found`, `none` when the branch has no pull request, or `not looked up` when the tracker cannot look or the lookup failed. |

A key the harness did not report is left out of the line, never written as zero. A session crew stopped, or one that was killed or crashed before its final result, reports none of them. An action that never got a worktree has an `ended` line with no `workspace`.

crew finds the pull request with `gh pr list --head <branch>`, once the action's session ends, for up to 15 seconds: an open one from your repository first, otherwise the newest closed or merged one created since the worktree was made. A pull request opened from another branch than the action's is not found. A missing pull request changes nothing about the action's outcome; a [check](#checks) is how you fail it.

crew computes no totals across runs. Read the journal with your own tools, for example the cost of each ended action as CSV:

```sh
jq -r 'select(.event == "ended") | [.time, .run, .ref, .stage, .action, .succeeded, .cost_usd, .output_tokens, .pull_request] | @csv' .crew/logs/runs.jsonl
```

A run with a `started` line and no `ended` line was cut short by a crash or a kill, including a second ctrl+c. crew stops before polling when it cannot read the journal, and says in its output when it cannot write to it.

Add crew's local files to `.gitignore`, and keep `.crew/config.yaml` committed:

```text
.crew/logs/
.crew/worktrees/
```

## Run it

Run `crew` anywhere inside the repository's main checkout. In one of crew's worktrees, it would take that worktree for the repository.

```sh
crew
```

On a terminal, crew shows a live view: the issues it holds by stage, the running actions with their elapsed time, the issues it handled since it started, and the latest events. The view only displays. You act on issues through their labels on GitHub.

The top line says how many issues crew holds and how long it has been up, and, with `config.run_time_limit_seconds`, how much run time is left. The line under it counts the issues crew handled, with the cost and tokens of every session that ended since crew started, then the issues by the state each went to, as your workflow names it:

```text
crew: 2 issues held, up 3h12m, 48m left (q or ctrl+c stops)
handled 10 ($70.05, 138.1M tokens): 2 crew:failed, 8 crew:waiting review
```

Handled lists each issue whose stage ended, on one line: the state it went to, its number, the stage and how long it took, the cost and tokens of the stage's sessions, the pull request of a stage with one action, and its title. An issue shows once, with its latest stage, and leaves Handled while a stage holds it again; the line above still counts what its earlier stages cost. The issues that need you come first: a stage that failed, with one line per failed action and its reason, and a move crew gave up, because the issue was closed or moved meanwhile or GitHub refused it. A given-up move shows `move given up` where the state would be, and is counted on its own. A stage with several actions shows each action's pull request on a line of its own. The status comment on each issue keeps the detail.

```text
Handled
  crew:failed          #28  development 41m10s  $6.89, 12.7M tokens  no pull request  Parse the config once
    lfg failed: exited 1: tests fail on Go 1.27
  crew:waiting review  #36  development 8m12s   $8.21, 18.4M tokens  #45              Log the poll interval

```

The cost is the harness's figure, shown as it reports it and always next to the tokens, which add up all four kinds the [run journal](#where-things-go) keeps apart. A stage where some session reported no cost shows the known cost marked `(partial)`, and one where none did says `cost not reported`. A running action shows no cost: its numbers appear once it ends. An action that never had a session adds nothing and shows no pull request.

The view fits the window. When rows run out, the latest events go first. Then the oldest handled issues that do not need you collapse into one line per state. The issues that need you never collapse; if even they do not fit, the view is cut at the bottom with a line saying how many lines were cut. Handled covers this run only: it starts empty each time crew starts, and nothing of it is saved.

With `--plain`, or when the output is not a terminal, crew prints one line per event instead:

```text
14:22:58 crew: implement took #42 "Add login form" (ready -> in progress)
14:22:58 crew: poll: listed 1 issue, took 1
14:22:59 crew: #42 moved from ready to in progress
14:23:04 crew: #42 implement/acceptance started on branch crew/issue-42-acceptance, log .crew/logs/issue-42-acceptance.log
```

`crew --version` prints the version, which is `dev` for a `go install` build.

### Stop it

Press Ctrl-C (or `q` in the live view), or send SIGTERM or SIGHUP. Closing the terminal crew runs in sends SIGHUP. crew stops cleanly:

1. It starts nothing new.
2. Issues whose actions have all ended are judged as usual.
3. Running sessions and checks get 10 seconds to stop before they are killed. Their issues move to their stage's `on_failure`, with a comment saying crew stopped them, and their status comments show the move. When `on_failure` is another stage's `label`, such as `ready`, that stage takes the issue again at the next poll.
4. Moves and comments still owed get one last try.

This can take a while if GitHub is slow: every `gh` and `git` call has up to 10 minutes. Press Ctrl-C (or `q`) again, or send a second SIGTERM or SIGHUP, to force the exit. crew kills every process it started and exits at once, so the issues it was working on stay in their `moves_to` state until you relabel them.

If crew's output goes to a pipe that closes, for example `crew | head`, crew stops cleanly the same way and exits with 1.

The checks crew runs when it starts have the same 10 minutes. Past them, or on Ctrl-C, SIGTERM or SIGHUP meanwhile, crew kills every process it started and exits with 2, before its first poll.

### Run it for a set time

Set `config.run_time_limit_seconds` to start crew for a set time, such as overnight. The time counts from the first poll, so the checks crew runs when it starts do not use it up. When the time is up, crew winds down:

1. It takes no new issue, even one that is `ready`.
2. Sessions and checks already running go on until they end, and their issues are judged as usual. No issue goes to its stage's `on_failure` because of the limit.
3. Moves and comments still owed get their last try, as when you stop crew.
4. crew exits with 0.

crew says it is winding down, in the live view and with `--plain`:

```text
06:22:58 crew: run time of 8h0m0s is up: taking no new issues, winding down
```

A session that runs long keeps crew running past the limit, and so does a move that keeps failing while crew takes an issue, until GitHub answers. Press Ctrl-C (or `q`), or send SIGTERM or SIGHUP, to stop it the usual way: running sessions get 10 seconds to stop, and their issues move to their stage's `on_failure`. A second one forces the exit.

### Exit codes

| Code | When |
| --- | --- |
| `0` | crew stopped cleanly, or wound down after its run time. |
| `1` | crew failed while running, or you forced the exit. |
| `2` | The config, a flag or the environment is wrong; nothing was polled. |

## Limits

- **One crew per repository.** Two crews in one repository take the same issues. Nothing stops you from starting a second one.
- **No recovery after a crash on its own.** An issue left in a `moves_to` state, such as `in progress`, by a crash or a forced exit stays there until you relabel it, and its status comment keeps saying its actions run until its next stage run starts. Relabeling it with its stage's `label` resumes its actions in their worktrees.
- **No time limit on a session.** A session runs until it ends or you stop crew. `config.run_time_limit_seconds` limits crew, not its sessions: it does not cut a running session short.
- **No retries on its own.** crew never runs a failed action, or one whose check failed, again by itself. Relabeling the issue is the retry, and it resumes the failed action. Two stages whose `on_failure` is each other's `label` would hand an issue back and forth with no one relabeling it, resuming each time.
- **Only `github` and `claude`.** Other trackers and coding agents are not built yet.
- **Not built yet from the old dispatcher:** pausing and resuming on usage limits, promoting to `ready to merge` when pull requests pass their checks, and per-stage progress.
- **At most 100 issues per poll**, the oldest first.
- **Sessions are headless.** They cannot ask you anything or talk to each other. The [acceptance tester](/guide/acceptance-tester) agent is interactive, so do not point an action at it.
