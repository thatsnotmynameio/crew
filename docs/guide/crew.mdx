# crew

crew moves your issues through rules you declare in the repository. Each rule reacts to one label. crew polls GitHub for the issues and pull requests that carry a rule's label, and for each one it runs the rule's actions in parallel. Each action is a headless coding-agent session, Claude Code today, in its own git worktree and branch. When every action ends, crew moves the issue to the rule's success label, or to its failure label with a comment saying what failed.

crew runs sessions and moves labels. Opening a pull request, reviewing and merging are your prompts' job and yours. A rule takes issues, or, with `takes: pull_requests`, the pull requests you labeled. crew also writes to the pull requests that close an issue: it gives them the issue's label, and comments on them when a rule ends. See [The pull requests](#the-pull-requests).

## Install

On macOS or Linux, on amd64 or arm64, this downloads the latest release for your machine, checks it against the release's `checksums.txt`, and installs `crew` into `/usr/local/bin`. `sudo` asks for your password.

```sh
(
  set -eu
  os=$(uname -s | tr '[:upper:]' '[:lower:]')
  case $(uname -m) in
    x86_64) arch=amd64 ;;
    aarch64 | arm64) arch=arm64 ;;
    *) echo "crew has no build for $(uname -m)" >&2; exit 1 ;;
  esac
  archive="crew_${os}_${arch}.tar.gz"
  url=https://github.com/thatsnotmynameio/crew/releases/latest/download
  tmp=$(mktemp -d)
  trap 'rm -rf "$tmp"' EXIT
  cd "$tmp"
  curl -fsSLO "$url/$archive"
  curl -fsSLO "$url/checksums.txt"
  if command -v sha256sum > /dev/null; then
    grep " $archive\$" checksums.txt | sha256sum -c -
  else
    grep " $archive\$" checksums.txt | shasum -a 256 -c -
  fi
  tar -xzf "$archive" crew
  sudo install -d /usr/local/bin
  sudo install -m 0755 crew /usr/local/bin/crew
  crew --version
)
```

With Go 1.27 or later, you can build a release instead, where `vX.Y.Z` is the release's tag:

```sh
go install github.com/thatsnotmynameio/crew/cmd/crew@vX.Y.Z
```

This puts `crew` in `$(go env GOPATH)/bin`.

## Before you run it

- **macOS or Linux.** crew starts every tool in its own process group, which Windows does not have.
- **A git repository with an `origin` remote on GitHub.** crew branches each action from origin's latest default branch.
- **`gh`, logged in** (`gh auth login`), with permission to edit the repository's issues and labels.
- **The harness of each agent your actions name on your `PATH`, logged in.** `claude` is the one crew ships.

crew checks all of this when it starts and stops with a message if something is missing.

## Configure it

crew reads `.crew/config.yaml` at the root of the repository. Commit it. Here is a complete example:

```yaml
# yaml-language-server: $schema=https://raw.githubusercontent.com/thatsnotmynameio/crew/main/schema/config.schema.json
poll_interval_seconds: 300
max_parallel_issues: 2
tracker:
  name: github
agents:
  developer:
    harness:
      name: claude
      model: claude-opus-5-5
checks:
  open-pull-request: >-
    gh pr list --head "$CREW_BRANCH" --state open --json number --jq length
    | grep -qv '^0$' || { echo "no open pull request from $CREW_BRANCH"; exit 1; }
rules:
  implement:
    labels:
      ready: ready
      running: in progress
      success: ready to review
      failure: needs attention
    actions:
      acceptance:
        prompt: >-
          Write the acceptance tests for issue {{.Issue.Ref}} ({{.Issue.URL}}).
          Take the acceptance examples from the issue and ask nothing: nobody
          answers questions in this session. Open a pull request with the tests.
      development:
        check: open-pull-request
        prompt: >-
          Implement issue {{.Issue.Ref}}, "{{.Issue.Title}}" ({{.Issue.URL}}).
          Open a pull request with the change. This session is headless:
          ending your turn ends the session. Never end a turn waiting on a
          background command; run it in the foreground, or wait for it with
          Monitor.
  review:
    labels:
      ready: ready to review
      running: in review
      success: ready to merge
      failure: needs attention
    actions:
      custom_review:
        prompt: "Review the pull requests for issue {{.Issue.Ref}} and leave your review on them."
```

With it, an issue labeled `ready` gets two sessions at once, `acceptance` and `development`, and moves to `in progress`. When both succeed, it moves to `ready to review`, where the `review` rule takes it. When either fails, it moves to `needs attention`. `development` succeeds only when its [check](#checks), `open-pull-request`, finds an open pull request from its branch. Here `success: ready to merge` only means "reviewed": crew does not merge anything. The file declares one agent, `developer`, so no action needs to name it.

The rules form no sequence. Each rule reacts to its `ready` label alone, and `review` follows `implement` only because `implement`'s `success` is `review`'s `ready`. You chain the labels, and you can move an issue to any rule's `ready` label by hand.

Sessions run with no one to answer them, so tell the agent not to ask. A session that asks a question and stops counts as a success. That is why the `acceptance` prompt tells it to take the examples from the issue.

Ending a turn also ends the session, and nothing resumes it. A session that ends its turn to wait for a background command, such as a test run, is stopped there and counts as a success. That is why the `development` prompt tells it to run commands in the foreground or wait for them with Monitor.

The first line is optional. It points editors that use [yaml-language-server](https://github.com/redhat-developer/yaml-language-server), such as VS Code with the YAML extension, at crew's JSON Schema, `schema/config.schema.json` in the crew repository, so they complete and explain every key as you type.

### Keys

These are the keys of the file's top level. Only `rules` is required, and `agents` as soon as a rule has actions. Names you choose, such as a rule's, an agent's or a check's, are keys of a mapping, so a name written twice is refused with both lines.

| Key | Default | What it does |
| --- | --- | --- |
| `poll_interval_seconds` | `300` | Seconds between polls. Must be positive. |
| `max_parallel_issues` | `2` | How many issues crew works on at once, split into [queues](#queues). It counts issues, not sessions: an issue whose rule has two actions takes one slot. Must be positive. |
| `run_time_limit_seconds` | none | How long crew runs, counted from its first poll, before it winds down (see [Run it for a set time](#run-it-for-a-set-time)). Must be positive: `28800` is 8 hours. Without it, crew runs until you stop it. |
| `usage_in_status` | `false` | Adds each ended action's cost, tokens and pull request to the [status comment](#the-status-comment). |
| `queues` | none | Queues by name, each with its slots. See [Queues](#queues). |
| `tracker` | `name: github` | Where issues live, and the bot crew's own writes act as. See [Tracker](#tracker). |
| `agents` | none | Agents by name: the harness that runs a session, its model and its bot. See [Agents](#agents). |
| `checks` | none | Checks by name, each a shell script that decides whether an action succeeded. See [Checks](#checks). |
| `board` | none | The columns of the live view's board. See [The board](#the-board). |
| `rules` | required | Rules by name, at least one. See [Rules](#rules). |

### Queues

`max_parallel_issues` is split into queues, and each rule runs in one of them. A queue's slots are only for its own rules: a long development session can never take the slot of a quick bookkeeping rule, such as a triage that finds an issue's blockers.

`queues` maps a queue's name to its slots, a positive number. crew always has one more queue, `default`, which gets the slots the others leave: `max_parallel_issues` minus the slots of every queue under `queues`. A rule that names no `queue` runs in `default`.

```yaml
max_parallel_issues: 5
queues:
  clerk: 1
  review: 2
rules:
  triage:
    queue: clerk
    # ...
  review:
    queue: review
    # ...
  implement:
    # ...
```

Here `triage` has 1 slot, `review` 2, and `implement` runs in `default`, which has the 2 slots left. Without `queues`, every rule shares `default`, which has all of `max_parallel_issues`.

A queue never lends a slot it does not use. While `default` is full, a `clerk` slot stays free for the next triage, even with development issues waiting. So a slot is guaranteed only by the size of a rule's queue, and the total never goes over `max_parallel_issues`. A queue that no rule names keeps its slots idle. The [live view](#run-it) shows each queue a rule runs in, with its busy and free slots.

`default` may have 0 slots, when the other queues take them all. Its rules then never run, and crew does not warn you. crew refuses to start when:

- `default` would have fewer than 0 slots;
- a queue under `queues` has fewer than 1 slot, or is named `default`, in any case;
- a rule's `queue` is empty or names a queue that does not exist.

### Tracker

`tracker` says where issues live:

| Key | Default | What it does |
| --- | --- | --- |
| `name` | `github` | The tracker adapter. `github` is the only one today, and it takes no other key. |
| `bot` | none | The [bot](#act-as-bots) crew's own writes act as, and the bot of every agent that names none. Without it, they act as your `gh` login. |

### Agents

`agents` maps an agent's name to the harness that runs its sessions and the bot they act as. An action names its agent with `agent`.

```yaml
agents:
  developer:
    harness:
      name: claude
      model: claude-opus-5-5
    bot: developer
  reviewer:
    harness:
      name: claude
      model: claude-sonnet-5-5
    bot: reviewer
```

| Key | What it does |
| --- | --- |
| `harness.name` | Required. The harness adapter that runs the agent's sessions. `claude` is the only one today. |
| `harness.model` | Optional. The model the harness runs, passed to `claude --model`. Without it, the adapter's default, `claude-opus-5-5` for `claude`. |
| `harness`'s other keys | The harness adapter's own settings. `claude` takes only `model`, and refuses any other key. |
| `bot` | Optional. The [bot](#act-as-bots) the agent's sessions and checks act as. Without it, they act as `tracker.bot`, and as your `gh` login when that is not set either. |

Each action runs on its own agent's harness, so one crew can run sessions on different harnesses, or different models, at the same time. crew checks every agent's harness name against the harnesses it knows, even an agent no action names. It builds, checks and makes act only the agents some action names: an unused agent never starts a session, its tool need not be installed, and its bot does not act.

### Checks

`checks` maps a check's name to a shell script that crew runs after an action's session succeeded, to see that the work exists. An action names its check with `check`, and several actions can share one:

```yaml
checks:
  open-pull-request: >-
    gh pr list --head "$CREW_BRANCH" --state open --json number --jq length
    | grep -qv '^0$' || { echo "no open pull request from $CREW_BRANCH"; exit 1; }
rules:
  implement:
    # ...
    actions:
      development:
        check: open-pull-request
        prompt: "Implement {{.Issue.Ref}} and open a pull request that closes it."
```

- **Where it runs:** with `sh -c`, in the action's worktree, once its session has ended. A session that failed runs no check.
- **What it gets:** the [environment](#the-environment-of-sessions-and-checks) of a check, with the issue's ref, key and URL and the worktree's branch. It acts on GitHub as its action's session does, as its [bot](#act-as-bots) when it has one. The check is not a template: write `$CREW_ISSUE_REF`, not `{{.Issue.Ref}}`. No issue text, such as the title, ever becomes part of the command.
- **How it passes:** it exits with 0. It fails when it exits with anything else, cannot start, or runs for more than 10 minutes, a limit you cannot change. A failed check fails the action, as a failed session does: the issue moves to the rule's `failure` label, and crew does not run the action again.
- **Its output:** stdout and stderr go to the action's log, after the session's. The reason crew gives is `the check failed:` followed by the last line the check printed, from stdout or stderr. That line goes into the issue's [status comment](#the-status-comment), which may be public. So keep your tools' output out of the last line, and end a failing check by echoing its own one-line reason, as above. A check that runs out of time or cannot start says so instead.
- **What it trusts:** the check runs in the worktree the session wrote. A check that calls a script from the repository runs the session's copy of it. The check catches a session that stopped early, not one that tries to fool it.

When you stop crew, a running check is ended too, and its action counts as stopped. When the run time is up, a running check runs to its end.

An empty script is refused, and so is an action whose `check` names a check that `checks` does not have. A check no action names is allowed.

### Rules

`rules` maps a rule's name to the rule. A rule takes the items of its kind that carry its `ready` label, moves each to its `running` label, runs its actions, and moves the item to its `success` label when every action succeeded, or to its `failure` label when any failed.

| Key | What it does |
| --- | --- |
| `labels` | Required. The rule's labels, by state: see below. |
| `actions` | Optional. The rule's actions by name, each a session of its own, all started together: see below. A rule without actions only moves the label: see [Rules without actions](#rules-without-actions). |
| `queue` | Optional. The [queue](#queues) the rule runs in: one under `queues`, or `default`, the default. |
| `takes` | Optional. The kind of item the rule takes: `issues`, the default, or `pull_requests`. A rule takes one kind, never both. See [A pull request as the work](#a-pull-request-as-the-work). |
| `notify` | Optional. Whether crew sends a desktop notification when the rule ends. On by default for a rule with actions, off for a rule without. See [Notifications](#notifications). |

`labels` has:

| Key | What it does |
| --- | --- |
| `ready` | Required. The label the rule takes items from. No two rules take the same label. |
| `running` | Required. The label the item carries while the rule works on it. It cannot be any rule's `ready`, or that rule would take the item too. |
| `success` | Required. The label the item moves to when every action succeeded. It cannot be the rule's own `ready`. |
| `failure` | Required on a rule with actions; a rule without actions never fails. The label the item moves to when any action failed, with crew's comment. It cannot be the rule's own `ready`, but it can be another rule's: `failure: ready` on the `review` rule sends a failed review back to `implement`. |

Each action of `actions` has:

| Key | What it does |
| --- | --- |
| `prompt` | Required. What the session is told, a template over the item: see [Prompts](#prompts). |
| `agent` | The [agent](#agents) that runs the session. It can be left out only when `agents` declares exactly one agent. |
| `check` | Optional. The [check](#checks) that decides whether the action succeeded. Without it, the session's own outcome decides. |

The labels hold the label as it is written on GitHub, such as `in progress`. Any text works. GitHub does not tell labels apart by case, so neither does crew: `Ready` and `ready` are the same label in every rule above, and crew writes a label everywhere as you first wrote it in the file.

A rule whose `success` or `failure` is its own `running` leaves the issue where it is when it ends. On failure crew still comments.

crew's labels are the ones your rules name, and no others. Every other label on an issue is yours: crew never adds, removes or creates it, and an issue whose only labels are yours is not crew's to take. So you can park an issue in a label no rule names, such as an idea waiting for a brainstorm, and start work on it by moving it to a rule's `ready` label. When crew moves the issue, it removes every other label your rules name and keeps every label they do not, the parked one included.

#### Rules without actions

A rule with no `actions` only moves the label. crew takes the item, moves it to `running`, and moves it on to `success` at once, without a worktree or a session, so the rule spends no tokens and no money. Use it to hand an issue from one rule to the next, as the crew repository does:

```yaml
rules:
  promote triage:
    queue: clerk
    labels:
      ready: "crew:triage:done"
      running: "crew:triage:promoting"
      success: "crew:development:ready"
```

Such a rule is a rule like any other in what it takes and when: it waits for a free slot in its queue and holds it for its two moves, so give it a small queue of its own, such as `clerk` above, to keep it from waiting behind long sessions. It never fails, so it needs no `failure` label. It writes an entry in the issue's [status comment](#the-status-comment), with no action in it, and gives the issue's [pull requests](#the-pull-requests) its labels, but posts no stop comment: nobody stopped watching anything. It sends no notification unless its `notify` is `true`, has no column on the default [board](#the-board), and keeps the issue's earlier entry in the live view's Handled section when both ended well. When you stop crew while such a rule is taking an item, the rule still moves it on to `success`.

#### Notifications

While the terminal is not focused, each rule that ends sends a desktop notification saying how it ended, unless its `notify` is `false`. `notify` is on by default for a rule with actions and off for a rule without. A rule with `notify: false` sends none, on failure too. A rule without actions that keeps an earlier Handled entry sends nothing, even with `notify: true`, since it leaves no entry of its own. See [Run it](#run-it) for which terminals show them.

### Prompts

A prompt is a Go template over the item the rule took: an issue, or a pull request when the rule has `takes: pull_requests`:

| Field | On GitHub |
| --- | --- |
| `{{.Issue.Ref}}` | `#42` |
| `{{.Issue.Key}}` | `42` |
| `{{.Issue.Title}}` | the issue's or pull request's title |
| `{{.Issue.URL}}` | the issue's or pull request's web address |

Any other field is an error when crew starts. Quote the prompt or use a block (`>-` or `|-`) as in the example: in YAML, a value that starts with `{` is not a string.

A session on a pull request still starts in a new worktree branched from the default branch. A prompt that works on the pull request's own branch checks it out itself, detached, and pushes to that branch by name:

```yaml
prompt: >-
  Run `gh pr checkout {{.Issue.Key}} --detach`, then answer the review
  comments on pull request {{.Issue.Ref}} and push your fixes with
  `git push origin HEAD:$(gh pr view {{.Issue.Key}} --json headRefName --jq .headRefName)`.
```

Keep `--detach`. git checks out a branch in one worktree only, and a pull request crew opened keeps its branch checked out in the worktree of the session that opened it, which crew never removes. A plain `gh pr checkout` fails there.

### The environment of sessions and checks

A session gets your environment, plus:

- `CREW_CODE_OWNERS`: the [code owners](#code-owners)' logins, separated by spaces.
- `CREW_BOTS`: the logins of the configured bots stored on this machine, each as `<slug>[bot]`, separated by spaces, including a bot that cannot act this run.
- `BASH_DEFAULT_TIMEOUT_MS` and `BASH_MAX_TIMEOUT_MS`, for `claude`: see [What "succeeded" means](#what-succeeded-means).

A check gets your environment, `CREW_CODE_OWNERS` and `CREW_BOTS`, plus:

- `CREW_ISSUE_REF` (`#42`), `CREW_ISSUE_KEY` (`42`) and `CREW_ISSUE_URL`: the item the rule took.
- `CREW_BRANCH`: the worktree's branch, such as `crew/issue-42-development`.

A session or check that acts as a [bot](#act-as-bots) also gets the bot's `gh` configuration, and loses `GH_TOKEN`, `GITHUB_TOKEN`, `GH_ENTERPRISE_TOKEN`, `GITHUB_ENTERPRISE_TOKEN` and `GH_HOST`, which would win over it.

In a session acting as a bot, `@me` is the bot, so a prompt that lists the issues crew takes uses the two lists instead:

```sh
for login in $CREW_CODE_OWNERS $CREW_BOTS; do gh issue list --state open --author "$login"; done
```

Earlier versions of crew named these variables `CREW_BOSS` and `CREW_MATES`, and no longer set them. crew refuses a prompt or a check that still names either, and says which variable replaced it. It reads only the prompt and the check's own script: a script that the check calls, such as `./scripts/check.sh`, is not seen, so one that still reads `$CREW_BOSS` or `$CREW_MATES` gets nothing. Search your scripts for both names when you upgrade.

### The board

The live view's board shows where issues stand, one column per label or group of labels. Without `board`, it has one column per rule that has actions, in the file's order, named after the rule. Each holds the items of the rule's kind, issues or pull requests, that carry its `ready` or `running` label. A rule without actions has no column.

`board` sets the columns yourself, to see the issues you care about while crew runs, such as parked ideas, open bugs and finished work. It maps a column's name to its label, or to a list of one or more labels:

```yaml
board:
  ideas: crew:brainstorm:ready
  bugs: bug
  done: [crew:brainstorm:done, crew:triage:done]
```

Any label works, crew's own or not. crew does not check that it exists on GitHub, so a label no issue carries gives an empty column. The columns are drawn left to right in the file's order. A column of `board` holds a card for each open issue that carries at least one of its labels, opened by a code owner or a configured bot, the same issues crew takes. Pull requests never get a card on a written board. Labels compare ignoring case, as GitHub compares them, and a label that is also a rule's takes the spelling the rule gives it.

On either board, an issue sits in every column whose labels it carries, and nowhere else, even while crew works on it: its work still shows in Actions. No card waits in a column for the next rule. See [Run it](#run-it) for how the board draws and refreshes.

crew refuses a `board` that names no column, a column with no label or an empty one, and a `board` when the tracker cannot list issues by any label. `github` can.

### What "succeeded" means

An action succeeded when its session ended cleanly, Claude Code's last result is not an error and `claude` exited with 0, and its check, if it has one, passed. Without a check, crew does not look for a pull request or any other evidence of the work. The labels and comments crew writes to [pull requests](#the-pull-requests) never decide whether an action succeeded.

So a session without a check can succeed without doing its work. For example, `--permission-mode auto` denies a tool, and the agent gives up politely, or the session ends its turn while a command runs in the background. Give such actions a check that looks for the work, write prompts that say what done looks like, and read the last message crew prints for every action that ends, successes included.

To make an early end less likely, crew starts `claude` with a Bash timeout of 10 minutes by default and 30 at most (`BASH_DEFAULT_TIMEOUT_MS` and `BASH_MAX_TIMEOUT_MS`), instead of Claude Code's 2 and 10. A Bash command that outlives its timeout moves to the background, so a full test run now stays in the foreground. They win over the same variables in the environment you start crew in.

### Upgrade from the old keys

Earlier versions of crew read other keys: a `config:` section, a `workflow` of stages, mates and a boss. crew refuses a file that still uses any of them. Before it checks anything else, it lists every old key it finds, each with its line and what replaced it, and exits with 2:

```text
crew: /home/you/repo/.crew/config.yaml: config.poll_interval_seconds (line 2): now poll_interval_seconds
config.mate (line 5): now tracker.bot
workflow (line 7): now rules, which maps each rule's name to the rule
workflow[0].name (line 8): gone; a rule's name is its key under rules
workflow[0].label (line 9): now labels.ready of the rule
workflow[0].moves_to (line 10): now labels.running of the rule
```

| Old key | Now |
| --- | --- |
| `config` | Gone: its keys are now at the top level. |
| `config.poll_interval_seconds`, `config.max_parallel_issues`, `config.run_time_limit_seconds`, `config.usage_in_status`, `config.queues` | The same key at the top level. |
| `config.clerk_slots` | Gone: crew has no `clerk` queue of its own. Declare one under `queues` and name it in its rules' `queue`. |
| `config.harness` | `agents.<name>.harness.name`. |
| `config.model` | `agents.<name>.harness.model`. |
| `config.mate` | `tracker.bot`. |
| `harness`, the top-level section | `agents.<name>.harness`, beside the harness's name. |
| `workflow` | `rules`, which maps each rule's name to the rule. |
| `extra_labels` | Gone: crew acts only on its rules' labels and leaves every other label alone. |
| `prompts` | Gone: crew never ran them, so keep them in the skills that do. |
| A stage's `name` | Gone: a rule's name is its key under `rules`. |
| A stage's `label` | `labels.ready` of the rule. |
| A stage's `moves_to` | `labels.running` of the rule. |
| A stage's `on_success` | `labels.success` of the rule. |
| A stage's `on_failure` | `labels.failure` of the rule. |
| A stage's `on_board` | Gone: `board` lists the board's columns, and `notify` says whether the rule sends notifications. |
| A stage's `description` and `issue_template` | Gone: crew does not read them. |
| An action's `name` | Gone: an action's name is its key under its rule's `actions`. |
| An action's `mate` | `agents.<name>.bot` of the action's agent. |

crew reports these keys wherever they are, in an old `workflow` or written into a new rule or action. Fix them all, and crew then checks the rest as usual. Three more changes are not old keys, so crew reports them as ordinary errors:

- **An action's `check`** now names a check under `checks` instead of holding the script. Move each script under `checks`, under a name, and put the name in the action. A script left in the action is refused as a check that does not exist.
- **`queue: clerk`** needs a `clerk` queue under `queues`, since crew no longer has one of its own. Without it, crew says the queue does not exist and lists the queues. A config that named no queue now gives `default` every slot: with `max_parallel_issues: 2`, `default` had 1 slot before, beside `clerk`'s, and has 2 now.
- **`$CREW_BOSS` and `$CREW_MATES`** are now `$CREW_CODE_OWNERS` and `$CREW_BOTS`: see [The environment of sessions and checks](#the-environment-of-sessions-and-checks).

`crew mates create` is now `crew bots create`, and bots created before keep acting without being created again: see [Bots](/guide/bots#bots-an-older-crew-created).

For example, this stage:

```yaml
config:
  mate: ops
workflow:
  - name: implement
    label: ready
    moves_to: in progress
    on_success: ready to review
    on_failure: needs attention
    actions:
      - name: development
        mate: developer
        prompt: "Implement {{.Issue.Ref}} and open a pull request that closes it."
```

becomes this rule:

```yaml
tracker:
  name: github
  bot: ops
agents:
  developer:
    harness:
      name: claude
    bot: developer
rules:
  implement:
    labels:
      ready: ready
      running: in progress
      success: ready to review
      failure: needs attention
    actions:
      development:
        prompt: "Implement {{.Issue.Ref}} and open a pull request that closes it."
```

A rule's and an action's names are kept in the run journal, so give them the names the stage and action had, and a failed action still [resumes](#resume-a-failed-action).

### When crew refuses to start

Before its first poll, crew checks the whole file and its tools. It stops, exiting with 2, when:

- the file uses an old key (see [Upgrade from the old keys](#upgrade-from-the-old-keys)), which crew reports before anything else;
- a key is unknown, written twice, or has a value of the wrong type, or a name is empty (the message names the key and its line);
- `tracker.name` or an agent's `harness.name` names an adapter that does not exist, even for an agent no action names (the message lists the adapters crew has);
- `rules` is missing or empty, a rule lacks `labels` or one of `ready`, `running` and `success`, or a rule with actions lacks `failure`;
- the rules would take an item twice or take back what they moved (the `ready`, `running`, `success` and `failure` rules above);
- a rule's `takes` is neither `issues` nor `pull_requests`;
- a rule has actions and `agents` declares none, an action leaves out `agent` while `agents` declares more than one, or names an agent that does not exist, or an agent lacks `harness` or `harness.name`;
- an action names a check that `checks` does not have, or a check is empty;
- a prompt is empty, does not parse, or uses a field that does not exist;
- a prompt or a check names `CREW_BOSS` or `CREW_MATES`;
- `board` names no column, a column has no label or an empty one, or `board` is set and the tracker cannot list issues by any label;
- a [queue](#queues) rule is broken: `default`'s slots, a queue's slots or name, or a rule's `queue`;
- a bot's name is not 1 to 29 lowercase letters, digits and single hyphens;
- CODEOWNERS cannot be read, or its `*` rule names a team crew cannot list (see [Code owners](#code-owners));
- `gh` is missing or not logged in, the harness of an agent in use is not on your `PATH`, or the repository has no `origin`;
- the checks take more than 10 minutes, or you stop crew during them.

crew reports every error it finds in the file at once. Past the file, it stops at the first check that fails, and prints its error after the [boot log](#run-it), whose last line names the check that failed. A second broken tool shows on the next start.

At the same check, crew creates the labels your rules name that the repository does not have yet, each `failure` label included, and no other.

## Act as bots

Without bots, crew, its sessions and its checks act on GitHub as your `gh` login. GitHub does not notify you about your own activity, so a failure report rarely reaches you, and it does not let you approve a pull request you opened. A [bot](/guide/bots) is a GitHub identity of crew's own. Name bots in the config, and crew acts as them:

```yaml
tracker:
  name: github
  bot: ops
agents:
  developer:
    harness:
      name: claude
    bot: developer
  tester:
    harness:
      name: claude
rules:
  implement:
    labels:
      ready: ready
      running: in progress
      success: ready to review
      failure: needs attention
    actions:
      development:
        agent: developer
        prompt: "Implement {{.Issue.Ref}} and open a pull request that closes it."
      acceptance:
        agent: tester
        prompt: "Write the acceptance tests for {{.Issue.Ref}}."
```

- **`tracker.bot`** is the bot crew's own writes on GitHub act as: the labels it creates, its label moves, the status comment, the failure report, the stop comment and the labels it mirrors on pull requests. It is also the bot of every agent that names none, `tester` above.
- **An agent's `bot`** acts for the sessions of the actions that name the agent, and their checks: `developer` for `development` above. Two actions of one rule can act as different bots through different agents, such as a developer and a reviewer: a bot cannot approve a pull request it opened.
- **Either works alone.** An agent's `bot` needs no `tracker.bot`: without it, crew's own writes, and the actions of agents with no bot, act as your `gh` login.
- **A name is a bot on this machine.** crew finds it among the bots stored on this machine for the owner of the repository, so the same config works in every repository of that owner where the bot is installed.
- **Without a bot,** crew, its sessions and its checks act as your `gh` login.

crew makes act `tracker.bot` and the bots of the agents some action names, each once. A bot named only by an unused agent does not act.

### What acts as whom

- **crew's reads,** such as the poll and the labels and comments it lists, go as your `gh` login, so a bot's missing organization permissions cannot break the poll. `gh` must stay logged in as you.
- **crew's writes** go as `tracker.bot`. When GitHub refuses the bot's token, crew renews it and tries once more. When the bot is still refused, lacks a permission, or lost access to the repository, crew makes the write again as you, and every later write of the run too, until crew restarts. The live view and the event lines then warn that crew writes as you, with the fix.
- **A session and its check** act as the action's bot in every `gh` call, for as long as they run: crew renews each token before its hour is up. They get a token limited to this repository, never the bot's key, and act as the bot even when your shell exports `GH_TOKEN` or `GITHUB_TOKEN`. A pull request a session opens has the bot as its author, so you can approve it.
- **Commits stay yours:** authored by you and pushed with your own git credentials. Every commit made in a workspace acting as a bot ends with the bot as co-author, whatever makes it, a skill's own `git commit` included:

  ```text
  Co-authored-by: crew-developer[bot] <123+crew-developer[bot]@users.noreply.github.com>
  ```

  The trailer comes from a `commit-msg` hook crew sets through git's environment, which needs git 2.54 or newer. Your own hooks still run.

crew never puts a token or a key in a prompt or a log, and it redacts GitHub tokens and private keys from what a session or a check says before that reaches a comment, the live view or the event lines.

### Code owners

crew takes the issues and pull requests that a code owner or a configured bot opened, even a bot that cannot act this run. A bot whose key is not on this machine has no login crew knows, so its issues wait until you create it here. The code owners are every user the `*` rule of the repository's CODEOWNERS names, on its default branch. crew reads the first of `.github/CODEOWNERS`, `CODEOWNERS` and `docs/CODEOWNERS` that exists, and its last `*` line, as GitHub does. A team, such as `@org/devs`, counts as its members, which `gh` lists only with the `read:org` scope: run `gh auth refresh -s read:org` when crew says it cannot. Email owners are skipped. Without CODEOWNERS, or with a `*` rule that names no user, the code owner is your `gh` login. This holds whether or not the config names a bot. crew reads CODEOWNERS when it starts, and gives the logins to sessions and checks as `CREW_CODE_OWNERS` (see [The environment of sessions and checks](#the-environment-of-sessions-and-checks)).

### When a bot cannot act

crew still starts when a bot it names cannot act, and acts as your `gh` login wherever that bot would. It warns at the top of the live view, and in the first lines of `--plain` output, naming the bot, what is wrong and the fix:

- **No key on this machine:** run `crew bots create <name>` in this repository.
- **Not installed on the repository:** run `crew bots create <name>` in this repository to install it.
- **GitHub rejected its key,** as after you deleted the app or revoked its key: delete the bot's file, which the warning names, and run `crew bots create <name>` again.
- **It could not get a token,** as when GitHub fails, or the token grants other permissions than every bot asks for: crew acts as you this run, and a restart tries again.
- **Its commits carry no co-author,** with git older than 2.54, or when GitHub did not give the bot's user id. The bot still acts. Update git, or restart crew.

A bot that cannot act at startup is not tried again until crew restarts. Its row in the [live view](#run-it)'s Bots section reads `cannot act` with a short reason, such as `no key`, `bad key file`, `not installed`, `key rejected` or `no token`, and its rules' actions act as you.

A bot can also stop acting while crew runs. crew then adds a warning under the header, with the reason and the fix, changes the bot's row, and prints an event, which `--plain` prints too:

- **crew's writes go back to you:** GitHub refused `tracker.bot`'s credentials, a permission, or access to the repository, so crew writes as you until it restarts. The row reads `writes as you`, and the warning stays for the rest of the run.
- **A token did not renew:** crew renews each token about ten minutes before it expires, and a renewal failed. The row reads `token not renewed` at once, while the old token still works, and the sessions and checks acting as the bot fail once it expires. crew tries again every minute: when a renewal succeeds, the row reads `acting` again, the warning goes, and an event says the bot acts again.

### Before you name a bot

- **Log `gh` in** with `gh auth login`. A login that exists only as an exported `GH_TOKEN` gives a session acting as a bot no way to push.
- **Pushes keep your credentials.** When your git config runs `gh auth git-credential` as the credential helper for github.com, as `gh auth setup-git` sets it, crew points that helper at your own `gh` config in a session acting as a bot, so `git push` pushes as you. Other helpers and SSH remotes are left alone.
- **Push before `gh pr create`.** `gh pr create` pushing a branch itself pushes as the bot, which cannot push code. Have prompts push with `git push` first.
- **Don't export `GH_TOKEN` in a profile the session's shell loads.** crew removes it from a session's environment, but a profile that sets it again makes the session's `gh` act as you.
- **A commit made with `--no-verify`** skips the hook and carries no co-author.

crew keeps the run's tokens in a private directory only your OS user can read, under `$XDG_RUNTIME_DIR` or else the system's temporary directory, never inside the repository, and removes it when it exits. After a crash or SIGKILL the tokens stay there until they expire, within the hour. A session runs as your OS user, so it could read a bot's key file: see [the key's risk](/guide/bots#the-keys-risk).

## What crew does on each poll

While every queue a rule runs in is full, a poll lists no issues, since it could take none. It still updates the running issues' status comments and retries what is owed, and says so in a line such as `poll: skipped, 2 of 2 slots busy`, which counts only the slots of the queues your rules run in. When crew lets go of an issue after such a poll, it lists at once instead of waiting for the next poll. Otherwise, a poll goes like this:

1. It lists the open issues and pull requests that a [code owner](#code-owners) or a configured [bot](#act-as-bots) opened and that carry a rule's `ready` or `running` label. Those other people opened are ignored, whatever their labels. crew takes only from `ready` labels: it lists the `running` labels for the default [board](#the-board), so an item left in a `running` label that crew does not hold, as after a crash, shows on the board but is never taken.
2. It skips an issue that carries two of your rules' labels, such as `ready` and `needs attention`, and says so. Remove one, and a later poll takes it. Labels no rule names do not count: an issue labeled `paused` and `ready` is taken when no rule names `paused`.
3. It leaves alone an item whose rule takes the other kind: a pull request carrying the `ready` label of a rule that takes issues, or an issue carrying the `ready` label of a rule with `takes: pull_requests`. crew does not move it or comment on it, and says so once, in a line such as `left #90 alone: it is a pull request, and ready is the label of implement, which takes issues`. It says so again only after a poll found the item without that label, or after crew restarts.
4. It skips an issue that an open issue blocks, as GitHub records it under the issue's relationships ("blocked by"). A pull request is never blocked. The issue keeps its label, and a later poll takes it once every issue blocking it is closed. crew writes no status comment for it while it is blocked.
5. It takes each issue whose rule's [queue](#queues) has a free slot, and passes over the others, so a full queue does not hold back the rules of another queue. It goes through them in this order: the highest priority first; then, at the same priority, the rule written later in the file first, so reviews are not starved behind new work; then the oldest issue first. The priority is the issue's GitHub issue field `Priority`, which your organization defines, ranked by the order of the field's options: with Urgent, High, Medium and Low, Urgent goes first. An issue without a priority, and every pull request, goes after every issue that has one. A repository without issue fields, such as one you own as a user, or an organization without a single select field named `Priority`, works as before: no issue has a priority. crew writes nothing on the issues left waiting: they keep their label, and a later poll with a free slot in their queue takes them.
6. Taking an issue moves it to the rule's `running` label. A move removes every other label your rules name, adds the new one, and leaves your other labels alone. Every move crew makes is then mirrored on the issue's open [pull requests](#the-pull-requests).
7. For each action, crew creates a worktree and a branch from origin's latest default branch, and starts a session there with the action's prompt, on its agent's harness. When the last run of that action, in that rule, on that issue failed, crew [resumes it](#resume-a-failed-action) in that run's worktree instead. A rule without actions skips this and the next step, and is judged at once.
8. While the actions run, crew updates the issue's status comment at every poll.
9. When every action of the issue has ended, its check included, crew judges it. If all succeeded, the issue moves to the rule's `success` label. Otherwise it moves to its `failure` label, and crew comments on the issue. Either way, crew then comments on the issue's open pull requests that the rule ended.

This failure report is a new comment, apart from the status comment, so GitHub notifies you of it. It names each failed action and its log, relative to the repository:

```markdown
crew: 1 action failed on #42.

**`development`** failed. Its log is `.crew/logs/issue-42-development.log`.
```

The comment carries nothing the session said: no last message, no commands, no output. Why an action failed is in its log, in crew's output and, in crew's own words, in the status comment. An action whose worktree could not be created has no log, and the comment says it failed before it had a log.

A move or comment that fails, for example because GitHub is down, is retried at every poll and once more when crew stops. So is a label or comment on a pull request, which never holds back or undoes the issue's move. One that cannot work, because the issue was closed or relabeled meanwhile or GitHub refused it, is dropped and reported. A status comment that says an issue is running is not retried: the next poll writes it again.

To retry a failed issue, swap its `failure` label, such as `needs attention`, for the rule's `ready` label, such as `ready`. Each failed action then resumes where it stopped, and each action that succeeded starts over.

### Resume a failed action

When a rule takes an issue, crew looks at the last run of each of its actions on that issue. When that run failed, the action resumes: crew runs a new session in the failed run's worktree, on its branch, with the commits and uncommitted files it left. crew does not fetch, merge or rebase the default branch into it. A run counts as failed when its action failed for any reason: the session failed, its check failed, crew stopped it, it failed to start, or crew crashed or was killed while it ran. A run that succeeded is never resumed, and an action of another rule never resumes it, even when the two actions share a name.

The new session gets the action's usual prompt followed by a paragraph from crew. It says that the session continues an earlier session's work in this worktree, on its branch, quotes why that run failed, gives the run's log (`.crew/logs/issue-42-development.log` in the main checkout, `../../logs/issue-42-development.log` from the worktree), and tells the session to check the worktree's state with `git` before going on. The new session's output goes into the same log, after this line:

```json
{"type":"crew","subtype":"resumed","time":"2026-10-02T21:05:00Z"}
```

The event lines, the live view and the status comment say that the action resumed and name its worktree. A resumed run is judged like any other. When it fails, the next relabel resumes it again; there is no limit.

To start over instead, remove the worktree before you relabel the issue:

```sh
git worktree remove --force .crew/worktrees/issue-42-development
```

crew then creates a new worktree, `issue-42-development-2` while the old branch exists, and says so in its output. The old branch, and any pull request from it, are yours to clean up.

crew knows how runs ended from its run journal, `.crew/logs/runs.jsonl`, so a resume works after a restart. Runs that ended before your crew version had the journal are not in it, so their actions start over. Renaming a rule or an action in the config starts its actions over too.

If crew was killed, for example with SIGKILL, its sessions can outlive it. Make sure none still runs in the worktree before you relabel the issue, or two sessions will work in it.

### The status comment

Each issue crew takes gets one status comment, created when crew takes it. It keeps one entry per rule run, oldest first: a rule run starts when a rule takes the issue, and ends when the next one starts. crew edits only the latest entry, and earlier entries keep the text they had when their rule ended, across restarts. An entry shows where the issue stands:

- **Running:** the rule, each action as running, succeeded or failed, how long each running action has run, the last thing its session said, and when crew updated the entry. An action that [resumed](#resume-a-failed-action) names its worktree, as in "**`development`** resumed in worktree `issue-42-development` and has been running for 5 minutes." crew updates it at every poll. An action whose check runs, or whose pull request crew is looking up, is still running.
- **Ended:** each action's final state, and where the issue went: the rule's `success` or its `failure` label, including when you stopped crew. Each failed action says why in crew's words, with its log: its session failed, crew stopped it, its workspace could not be created, its session could not start, or its prompt did not render. A failed check shows its reason, as in the example below. A [rule without actions](#rules-without-actions) lists no action.
- **With `usage_in_status: true`:** each ended action whose session started also shows its cost and tokens, as the [run journal](#where-things-go) records them, and its pull request, linked, as in "**`development`** succeeded. Usage: $12.40, 48.4M tokens. Pull request: #45." A value the harness did not report says so, and a sum that misses one is marked partial. Without the setting, the comment shows none of this.

````markdown
<!-- crew:entry run=20261002T130112.000000000Z.1 kind=ended stage=implement -->
crew: `implement` ended on #42.

**`acceptance`** succeeded.

**`development`** failed: `the check failed: no open pull request from crew/issue-42-development`. Its log is `.crew/logs/issue-42-development.log`.

#42 moved to `needs attention`.

Updated 2026-10-02 13:58 UTC.

---

<!-- crew:entry run=20261002T140112.000000000Z.2 kind=running stage=implement -->
crew: `implement` is running on #42.

**`acceptance`** succeeded.

**`development`** has been running for 42 minutes. It last said:

```text
U1 committed: 168 tests pass. Starting U2.
```

Updated 2026-10-02 14:43 UTC.

<!-- crew:status -->
````

The hidden lines mark the entries and the comment. Their `stage=` holds the rule's name: it keeps the name earlier versions of crew wrote, so their comments still parse. The session's words have your repository's path written as `.` and your home directory as `~`, and sit in a code block, so nothing in them renders or mentions anyone. Editing a comment notifies no one; the failure report is what notifies you.

crew finds its comment again after a restart by the hidden last line, among the comments of your `gh` login and of the configured bots, and keeps what it holds. An entry left running by a crew that crashed or was killed says that crew stopped following that rule once the next rule run starts. A comment written before crew kept entries becomes the first entry. A queued entry that an earlier crew version wrote, while the issue waited for a free slot, becomes the running entry when crew takes the issue for that rule. Edits you make by hand inside the comment are not kept.

A comment that would grow past GitHub's limit of 65,536 characters is left as it is, and crew continues in a new status comment that says so. So does a comment another login wrote, such as yours before you set `tracker.bot`: crew does not edit it and continues as the login it now writes as. From then on, crew writes only to the new one. If you delete the comment, crew creates a new one at its next update. An issue crew handled before it had status comments gets none until crew takes it again. crew does not touch the comment of an issue it does not take, so a queued entry an earlier version left there stays as it is.

### The pull requests

crew does not open, review or merge pull requests. A rule with `takes: pull_requests` takes a pull request that carries its `ready` label, as a rule takes an issue: see [A pull request as the work](#a-pull-request-as-the-work). crew also writes to the pull requests that belong to an issue, so the pull request list shows where crew holds the work and whether anyone still watches it.

- **Which:** the open pull requests in the repository that GitHub links as closing the issue, whoever opened them. That is the `Closes #42` line in the pull request's body, so keep it in the prompts that open pull requests. Merged and closed pull requests, and pull requests in other repositories, are left alone. An issue without such a pull request gets nothing.
- **The label:** each time crew moves the issue, it gives each of those pull requests the issue's new label and removes every other label your rules name, as on the issue. Your other labels stay. The mirror goes one way: a rule's label you put on a pull request by hand is replaced at the issue's next move.
- **The stop comment:** when a rule with actions ends, after the issue moved, crew posts a new comment on each of those pull requests, so GitHub notifies you. In a crew session the session's watch over the pull request has ended with the session, so the comment says nobody watches it any more:

```markdown
crew: `development` failed on #42, which moved to `crew:failed`, as did this pull request.

**`lfg`** failed: crew stopped it. Its log is `.crew/logs/issue-42-lfg.log`.

Nobody watches this pull request any more: new review comments and CI failures need a person.

#42's [status comment](https://github.com/you/repo/issues/42#issuecomment-123) has the details.
```

A rule that succeeded says `succeeded` and lists no action. Like the failure report, the comment carries nothing a session said. A rerun of the rule posts a new comment when it ends. A rule without actions moves the pull requests' labels but posts no stop comment.

A pull request opened while a rule runs gets its label at the issue's next move, usually the rule's end. A merged pull request keeps the last label it got, such as `ready to review`. crew does not clean it up. A pull request that closes several issues carries the label of the issue crew moved last.

#### A pull request as the work

A rule with `takes: pull_requests` takes an open pull request that a code owner or a bot opened and that carries its `ready` label, as a rule that takes issues takes an issue. A rule without `takes` takes issues only: crew leaves a pull request carrying its `ready` label alone, and says so (step 3 of [each poll](#what-crew-does-on-each-poll)). crew moves the pull request through the rule's labels, runs the rule's actions on it, and keeps a status comment and, when the rule fails, a failure report on it. Its [prompt fields](#prompts) are the pull request's. A pull request has no priority and is never blocked.

- **Swap the label, don't add one:** a pull request that closes an issue crew moved already carries that issue's label, and a pull request with two of your rules' labels is skipped. Replace the mirrored label with the `ready` label of a rule that takes pull requests.
- **Nothing is mirrored from it:** moving a pull request gives no other pull request a label and posts no stop comment, since a pull request closes no issue.
- **The issue's moves still reach it:** when the issue it closes moves, the mirror replaces the label crew gave the pull request with the issue's. And when an issue moves to a rule's `ready` label, such as `success: ready to review` in the example, its pull requests get that label too. A rule that takes issues, like `review` there, takes the issue and leaves each pull request alone with a notice. A rule with `takes: pull_requests` takes the pull requests, and the issue, which keeps that label, gets the notice. Keep the labels your issues move to apart from the `ready` labels of rules that take the other kind unless you want that.

### Where things go

For action `development` on issue #42:

| What | Where |
| --- | --- |
| Worktree | `.crew/worktrees/issue-42-development` |
| Branch | `crew/issue-42-development`, not pushed by crew |
| Session log | `.crew/logs/issue-42-development.log` |
| Run journal | `.crew/logs/runs.jsonl`, for every run |

The name is the issue's key and the action's name, lowercased, with anything outside `a-z`, `0-9` and `-` turned into `-`. When a name is taken, crew adds `-2`, `-3` and so on. A resumed action keeps its worktree, branch and log. crew never removes worktrees: they are your evidence when an issue needs attention, and a failed action resumes in its own. Remove them with `git worktree remove` when you are done.

The run journal has one JSON line when a run's worktree is ready and one when its action ends, whatever its outcome. A rule without actions has no run, so it writes none. crew only appends to the journal, and never rewrites or trims it, so it holds every run of every crew process in this repository. For example:

```json
{"v":1,"event":"started","time":"2026-10-02T20:08:28Z","run":"2026-10-02T20:08:20.344209367Z","issue":"42","ref":"#42","stage":"implement","action":"development","workspace":"issue-42-development","branch":"crew/issue-42-development","log":".crew/logs/issue-42-development.log"}
{"v":1,"event":"ended","time":"2026-10-02T21:05:00Z","run":"2026-10-02T20:08:20.344209367Z","issue":"42","ref":"#42","stage":"implement","action":"development","workspace":"issue-42-development","branch":"crew/issue-42-development","log":".crew/logs/issue-42-development.log","succeeded":true,"reason":"done","duration_ms":3390000,"cost_usd":12.4,"input_tokens":450,"output_tokens":184862,"cache_read_tokens":46816709,"cache_write_tokens":1364924,"turns":64,"models":["claude-opus-5-5","claude-sonnet-5-5"],"pull_request":"#45","pull_request_url":"https://github.com/you/repo/pull/45","pull_request_lookup":"found"}
```

| Key | What it holds |
| --- | --- |
| `run` | The crew process the line belongs to: when it started, in UTC. Every line of one run of `crew` has the same value. |
| `stage`, `action` | The rule's name and the action's. The rule's key keeps the name `stage` that earlier versions of crew wrote, so their journals still resume failed actions, and your tools that read it keep working. |
| `succeeded`, `reason` | The action's outcome and its one-line reason, with your repository's path written as `.` and your home directory as `~`. |
| `duration_ms` | Milliseconds from the session's start to the action's end, its check included. Left out when no session started, as when its worktree could not be created. |
| `cost_usd` | The session's cost in US dollars, exactly as the harness reports it. With `claude` it is Claude Code's `total_cost_usd` at API prices, an estimate on a subscription. |
| `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_write_tokens` | The session's tokens by kind, its subagents included. |
| `turns` | The session's turns. With `claude`, the main session's turns, not its subagents'. |
| `models` | The models the session used. |
| `pull_request`, `pull_request_url` | The pull request crew found from the action's branch. |
| `pull_request_lookup` | `found`, `none` when the branch has no pull request, or `not looked up` when the tracker cannot look or the lookup failed. |

A key the harness did not report is left out of the line, never written as zero. A session crew stopped, or one that was killed or crashed before its final result, reports none of them. An action that never got a worktree has an `ended` line with no `workspace`.

crew finds the pull request with `gh pr list --head <branch>`, once the action's session ends, for up to 15 seconds: an open one from your repository first, otherwise the newest closed or merged one created since the worktree was made. A pull request opened from another branch than the action's is not found. A missing pull request changes nothing about the action's outcome; a [check](#checks) is how you fail it.

crew computes no totals across runs. Read the journal with your own tools, for example the cost of each ended action as CSV:

```sh
jq -r 'select(.event == "ended") | [.time, .run, .ref, .stage, .action, .succeeded, .cost_usd, .output_tokens, .pull_request] | @csv' .crew/logs/runs.jsonl
```

A run with a `started` line and no `ended` line was cut short by a crash or a kill, including a second ctrl+c. crew stops before polling when it cannot read the journal, and says in its output when it cannot write to it.

Add crew's local files to `.gitignore`, and keep `.crew/config.yaml` committed:

```text
.crew/logs/
.crew/worktrees/
```

## Run it

Run `crew` anywhere inside the repository's main checkout. In one of crew's worktrees, it would take that worktree for the repository.

```sh
crew
```

While crew loads `.crew/config.yaml` and runs its [checks](#when-crew-refuses-to-start), it prints a boot log: one line as each step starts, before anything else. A step done once per item, a bot, an agent's harness or a missing label, gets a line for each, and a step that does not run, such as making bots act when the config names none, gets no line.

```text

14:22:42 crew: checking git for the bots
14:22:42 crew: making a private directory for the bots' tokens

14:22:45 crew: creating the label "crew:triage:ready"

14:22:45 crew: checking the git checkout and its origin
14:22:45 crew: resolving origin's default branch
14:22:46 crew: reading the run journal
```

crew prints the boot log on every start, with the live view and with `--plain` alike. Its last line names what crew is waiting on, so a slow start never looks like a hung one. When the checks pass, the live view or the event lines take over; the live view does not repeat the boot log.

The header shows the repository, how long crew has been up and, with `run_time_limit_seconds`, how much run time is left, then the cost and tokens of every session that ended since crew started. Startup warnings stay under it for as long as crew runs, and so does a warning about a [bot that stopped acting](#when-a-bot-cannot-act) while it does. Each section opens with its title and a rule that ends in a short summary. Colours follow the terminal's background, light or dark; with `NO_COLOR`, or on a terminal without colour, the titles, icons and labels still tell everything apart. Issue and pull request numbers link to their page in terminals that support links.

Bots has two rows for each bot crew makes act, `tracker.bot` first, then the bots of the agents in use, in the order of the rules, then a row for you, labelled with the `gh` login crew acts as when it acts as you. The section shows even when the config names no bot, with your row alone, and its summary counts the bots that act and those that do not, or says `no bots`. A bot's first row shows its state, `acting`, `cannot act` with a short reason, `writes as you` or `token not renewed`, then what its actions that ended since crew started cost: how many, their cost and their tokens, in the same words as Handled. An action counts on the identity it acted as, so the actions of a bot that cannot act count on your row. The second row lists the rules and actions that act as it, as `rule/action`, starts with `crew's writes` on the row crew's own writes go as, yours when there is no `tracker.bot`, and ends, after `▸`, with the actions running as it now, from the start of their session until they end, their check included. When a row does not fit the window, its rules and actions are cut with `…` first, so the actions running now stay visible. No key acts on a bot: `crew bots create` creates or fixes one.

Board draws the [board](#the-board): its columns, in the file's order, each with a card for each item that carries one of the column's labels, oldest first. A card shows the item's number and title, and how crew holds it: `⠋ running`, `◌ taking`, `⠋ judging`, `! owed` while a move waits for a retry, or `■ stopping`. A card of an item crew does not hold shows `○ idle` instead, whatever label it waits in: an issue waiting for a free slot, or one left in a `running` label that crew does not hold. A card sits wherever the item's labels put it, slides when a move puts it in another column, and leaves the board when the item carries none of the board's labels any more, such as after a move to a `success` or `failure` label no column shows. A move crew makes shows at once. A label changed on GitHub, or an item closed there, shows after crew next reads the board:

- **Without `board`,** crew fills the board from the listing of each poll, which already asks for every rule's `ready` and `running` labels, so the board costs no extra query. While every slot is busy, a poll lists nothing, so a change made on GitHub meanwhile shows at the next listing.
- **With `board`,** crew reads the columns' issues from GitHub at each poll, even when it is too busy to take an issue.

A column with more cards than fit ends in `+N more`, hiding the newest. The summary counts the items with a card, and says `board not read` while the last read or listing from GitHub failed; the board then keeps what it last read. When the columns do not fit the window, the empty ones drop and the summary says how many; when the rest still do not fit, the board scrolls sideways with `←` and `→`.

Actions lists every action that has not ended: its issue, its rule and action, the [queue](#queues) its issue holds a slot in, its state with the elapsed time, and its branch. A running session shows the last thing it said on the line under it, with tokens and keys redacted, as in the [status comment](#the-status-comment). Queues shows each queue's busy slots `■` and free slots `□`. A slot is busy from the moment crew takes an issue for a rule in that queue until it lets go of the issue, whether the issue's actions have started or not, which is the count crew uses to decide whether the queue can take another issue.

Handled lists each issue whose rule ended: a label saying how it ended, its number and title, the rule and how long it took, the cost and tokens of the rule's sessions, and the pull request of a rule with one action. The issues that need you come first: `NEEDS ATTENTION` for a rule that failed, with one line per failed action and its reason after `×`, and `GIVEN UP` for a move crew gave up because the issue was closed or moved meanwhile or GitHub refused it. Any other ending shows the last part of the label the issue moved to, such as `WAITING REVIEW`. A rule with several actions shows each action's pull request on a line of its own. An issue shows once, with its latest rule, and stays there while a rule holds it again, with `now in` and that rule after its details. While a rule holds it again, a failed entry shows the last part of its label, such as `FAILED`, instead of `NEEDS ATTENTION`, and no longer counts as needing you: you already sent it back. A [rule without actions](#rules-without-actions) that ends well keeps the entry it found when that one ended well too, so a promote rule does not replace the rule before it; without such an entry, it leaves its own. The header still counts what every rule cost. The status comment on each issue keeps the detail. Handled covers this run only: it starts empty each time crew starts, and nothing of it is saved.

The cost is the harness's figure, shown as it reports it and always next to the tokens, which add up all four kinds the [run journal](#where-things-go) keeps apart. A rule where some session reported no cost shows the known cost marked `(partial)`, and one where none did says `cost not reported`. A running action shows no cost: its numbers appear once it ends. An action that never had a session adds nothing and shows no pull request.

Events shows the latest 100 events, the newest at the bottom.

Events and Handled each take five rows, however many they have, so the view holds still while crew works. Their rows fill from the top, with blank rows below until there are five. Past five, the section scrolls, and its title says `↑↓ scroll`. Events follows the newest event until you scroll up.

The view fits the window. When rows run out, Events and then Handled give up rows, as many as the window needs and down to two each. Then the session lines under Actions go, then each board column shows fewer cards with `+N more`, then each Bots row drops its second line, and only then is the view cut, with a line saying how many lines were cut. The keys:

| Key | What it does |
| --- | --- |
| `q`, Ctrl-C | Stop crew; a second press forces the exit. See [Stop it](#stop-it). |
| `tab`, `shift+tab` | Move the focus between Handled and Events. The focused section's title has a `▸`. |
| `↑` `↓` or `k` `j`, `pgup` `pgdown`, `home` `end` | Scroll the focused section. Events follows the newest event until you scroll up, and again from `end`. |
| `←` `→` or `h` `l` | Scroll the board sideways. |
| `?` | Show the keys, and hide them again. |

No key acts on an issue, a pull request, a workspace or a log.

crew also tells the terminal what it is doing, where the terminal supports it. The tab title reads like `crew · 2 running · 1 waiting · 1 needs attention`, or `crew · idle`, `crew · stopping` or `crew · winding down`. The tab's progress indicator shows activity while actions run, and an error while an issue in Handled needs you. A failed issue that a rule holds again does not count in either. While the terminal is not focused, each rule that ends sends a desktop notification saying how it ended, as its [`notify`](#notifications) says, and nothing is sent once you asked crew to stop. Notifications use OSC 9, which terminals such as iTerm2, WezTerm, Ghostty and Windows Terminal show, and tmux does not pass on. crew knows the terminal is not focused only when the terminal reports focus, so a terminal that never does gets no notification.

With `--plain`, or when the output is not a terminal, crew prints one line per event instead, after the boot log and any startup warnings:

```text

14:22:58 crew: poll: listed 1 issue, took 1
14:22:59 crew: #42 moved from ready to in progress
14:23:04 crew: #42 implement/acceptance started on branch crew/issue-42-acceptance, log .crew/logs/issue-42-acceptance.log
```

When a bot stops acting while crew runs, a line names it with the warning the live view shows under its header, such as `bot developer stopped acting: bot developer could not renew its token: …`, and `bot developer acts again: its token renewed` when it recovers.

`crew --version` prints the version: the release's tag for a downloaded release or a `go install …@vX.Y.Z` build, and `dev` for a build that records no version.

### Stop it

Press Ctrl-C (or `q` in the live view), or send SIGTERM or SIGHUP. Closing the terminal crew runs in sends SIGHUP. crew stops cleanly:

1. It starts nothing new.
2. Issues whose actions have all ended are judged as usual.
3. Running sessions and checks get 10 seconds to stop before they are killed. Their issues move to their rule's `failure` label, with a comment saying crew stopped them, and their status comments show the move. Their open pull requests get the `failure` label and a comment saying the rule failed because crew stopped it. When the `failure` label is another rule's `ready`, such as `ready`, that rule takes the issue again at the next poll.
4. Moves and comments still owed, on issues and pull requests, get one last try.

This can take a while if GitHub is slow: every `gh` and `git` call has up to 10 minutes. Press Ctrl-C (or `q`) again, or send a second SIGTERM or SIGHUP, to force the exit. crew kills every process it started and exits at once, so the issues it was working on stay in their `running` label until you relabel them.

If crew's output goes to a pipe that closes, for example `crew | head`, crew stops cleanly the same way and exits with 1.

The checks crew runs when it starts have the same 10 minutes. Past them, or on Ctrl-C, SIGTERM or SIGHUP meanwhile, crew kills every process it started and exits with 2, before its first poll.

### Run it for a set time

Set `run_time_limit_seconds` to start crew for a set time, such as overnight. The time counts from the first poll, so the checks crew runs when it starts do not use it up. When the time is up, crew winds down:

1. It takes no new issue, even one in a `ready` label.
2. Sessions and checks already running go on until they end, and their issues are judged as usual. No issue goes to its rule's `failure` label because of the limit.
3. Moves and comments still owed get their last try, as when you stop crew.
4. crew exits with 0.

crew says it is winding down, in the live view and with `--plain`:

```text
06:22:58 crew: run time of 8h0m0s is up: taking no new issues, winding down
```

A session that runs long keeps crew running past the limit, and so does a move that keeps failing while crew takes an issue, until GitHub answers. Press Ctrl-C (or `q`), or send SIGTERM or SIGHUP, to stop it the usual way: running sessions get 10 seconds to stop, and their issues move to their rule's `failure` label. A second one forces the exit.

### Exit codes

| Code | When |
| --- | --- |
| `0` | crew stopped cleanly, or wound down after its run time. |
| `1` | crew failed while running, or you forced the exit. |
| `2` | The config, a flag or the environment is wrong; nothing was polled. |

`crew bots create`, which gives crew GitHub identities of its own, has its own exit codes: see [Bots](/guide/bots#exit-codes).

## Limits

- **CODEOWNERS is read at startup.** A change to who the code owners are takes effect when crew restarts.
- **One crew per repository.** Two crews in one repository take the same issues. Nothing stops you from starting a second one.
- **No recovery after a crash on its own.** An issue left in a `running` label, such as `in progress`, by a crash or a forced exit stays there until you relabel it, and its status comment keeps saying its actions run until its next rule run starts. Relabeling it with its rule's `ready` label resumes its actions in their worktrees.
- **No time limit on a session.** A session runs until it ends or you stop crew. `run_time_limit_seconds` limits crew, not its sessions: it does not cut a running session short.
- **No retries on its own.** crew never runs a failed action, or one whose check failed, again by itself. Relabeling the issue is the retry, and it resumes the failed action. Two rules whose `failure` is each other's `ready` would hand an issue back and forth with no one relabeling it, resuming each time.
- **Only `github` and `claude`.** Other trackers and harnesses are not built yet. Several agents can run on `claude` at once, each with its own model and bot.
- **Not built yet from the old dispatcher:** pausing and resuming on usage limits, promoting to `ready to merge` when pull requests pass their checks, and per-rule progress.
- **At most 100 issues per poll**, the oldest first. With more waiting, a newer issue of high priority is not seen until older ones leave the list. The default board shows what that list holds.
- **At most 100 issues per author on a written [board](#the-board)**, the oldest first. With more open issues on its labels, the newest do not show.
- **Priority decides only the next free slot.** It never stops a running session to make room for a higher-priority issue, and it never moves an issue into another queue's free slot.
- **Sessions are headless.** They cannot ask you anything or talk to each other. The [acceptance tester](/guide/acceptance-tester) agent is interactive, so do not point an action at it.
