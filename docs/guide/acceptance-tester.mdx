# Acceptance tester

The acceptance tester writes one behavior test for each acceptance example in a plan. It works in its own session and its own git worktree, and it reads the plan, the docs and the public interface, never the implementation. You build the feature in another session as usual. When you are done, you bring its tests in and run them.

It does not write implementation code, unit tests, or tests of internals.

## Install once

The agent lives in this repository at `.agents/agents/acceptance-tester.md`. Link it into your user-level agents so every repository can use it:

```sh
mkdir -p ~/.claude/agents
ln -s "$(pwd)/.agents/agents/acceptance-tester.md" ~/.claude/agents/acceptance-tester.md
```

Run it from the root of your crew checkout. Changes to the file in crew apply everywhere at once, and so does switching branches there: a branch without the file removes the agent from every repository. Keep that checkout on `main`.

In each repository where you use it, ignore Claude Code's session worktrees by adding `.claude/worktrees/` to `.gitignore`.

## Start it

From the repository you are working on, give it the plan by absolute path:

```sh
claude --worktree my-feature-tests --name acceptance-tester --agent acceptance-tester "Plan: /absolute/path/to/plan.md"
```

- `--worktree` gives the tester its own worktree and branch (`worktree-my-feature-tests`), created from the default branch.
- `--name` lets your implementing session message it.
- Use an absolute path into your own checkout, so the tester can read a plan that is not committed or lives on another branch.

## What to expect

- **Plans with acceptance examples** (for example the `AE1.` items a `ce-brainstorm` plan has): one test per example, named with its ID, such as `test_ae3_…`.
- **Plans without them:** it proposes examples in Given/When/Then form and writes nothing until you confirm them.
- **Questions:** when the plan does not say how to call something, or a requirement has no observable outcome, it asks you instead of guessing.
- **No test framework in the repository:** it proposes one and waits for you.
- **Result:** tests in an `acceptance` folder of the test tree, with a `README.md` telling implementers not to edit them. Its commits end with `Role: acceptance-tester`. Before reporting, it runs the tests once without the feature and tells you which fail as expected and which look suspect.

## When the implementer disagrees

Your implementing session should not edit acceptance tests. When one looks wrong, it messages the `acceptance-tester` session directly. The tester re-reads the plan and either fixes the test or explains why it stands. If they still disagree, the tester brings both positions to you and you decide.

## Run the tests

When the feature is done, merge the tester's branch into your feature branch and run the acceptance tests with the repository's usual test command. Tests for behavior that did not exist yet should fail before the feature and pass after it.

## Limits

- Nothing technical stops the tester from reading code or the implementer from editing tests. Both are conventions the agent and the README state.
- It runs only as an interactive session: it has to ask you things and answer the implementer.
