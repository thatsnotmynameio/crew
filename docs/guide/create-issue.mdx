# Create an issue

`/cw-create-issue` is a Claude Code skill that records a piece of work as a GitHub issue for [crew](/guide/crew). It picks the type of work, fills that type's issue template, and creates the issue with the type's label. crew then takes it like an issue you labeled by hand. Two more skills, `/cw-update-issue-plan` and `/cw-brainstorm`, work on an issue that already exists.

The three skills are the crew repository's own aids for building crew, not part of crew. crew does not read them, and they do not read crew's config: each skill holds its own issue types, labels and prompts, which are the crew repository's. To use them in another repository, copy them and edit those tables and prompts to match your own rules and issue templates: see [Make them yours](#make-them-yours).

## Install once

The skills live in the crew repository, at `.agents/skills/cw-create-issue/`, `.agents/skills/cw-update-issue-plan/` and `.agents/skills/cw-brainstorm/`. Link a skill's directory into your user-level skills so every repository can use it:

```sh
mkdir -p ~/.claude/skills
ln -s "$(pwd)/.agents/skills/cw-create-issue" ~/.claude/skills/cw-create-issue
```

Run it from the root of your crew checkout. Changes to the skill in crew apply everywhere at once, and so does switching branches there: a branch without the skill removes it from every repository. Keep that checkout on `main`.

A linked skill carries the crew repository's labels into every repository. Link it only where those labels are the ones you use; elsewhere, copy it and make it yours.

The skills need `gh`, logged in, with permission to create the repository's issues and labels. They do not need the crew binary.

## Make them yours

Each skill's `SKILL.md` lists the types it knows in a table: a label, the issue template its body follows, a short description, and, in `/cw-create-issue`, what crew does with an issue of that type. In the crew repository, the types are the `ready` label of each of its rules that takes issues, plus `crew:brainstorm:ready`, which no rule takes: an idea parked there waits for `/cw-brainstorm`.

To use the skills in your own repository, copy their directories and edit:

- **The table of types,** in `/cw-create-issue` and `/cw-update-issue-plan`: your labels, your templates and your descriptions. A label a rule takes starts crew's work at the next poll with a free slot; a label no rule takes parks the issue.
- **The running labels and crew's labels,** in `/cw-update-issue-plan`, which uses them to leave alone an issue crew is working on and to know which labels a move removes.
- **The prompts,** in `/cw-brainstorm` and in step 8 of `/cw-update-issue-plan`: what to check, which labels to change and which skill to run.

Put the templates in `.github/ISSUE_TEMPLATE/`, where GitHub looks for them. Have each template's frontmatter `labels` name its type's label, so an issue opened from the template on the web lands in the same place. For a worked example, see the crew repository's `.crew/config.example.yaml`, `.github/ISSUE_TEMPLATE/` and the skills themselves. Those choices are crew's, not defaults: the `crew:brainstorm:ready` label, one template per rule, and a feature template laid out like a compound-engineering requirements plan. Copy only what fits your rules.

## Use it

In a Claude Code session in the repository:

```text
/cw-create-issue the login form loses what you typed when the session expires
/cw-create-issue idea for later: pause crew when Claude hits its usage limit
/cw-create-issue
```

- **The type:** the skill infers it from what you wrote. When you did not name one and no single type clearly fits, it lists the types and asks you to pick.
- **No arguments:** it records the session's work, such as a plan you just wrote. If the session has nothing to record, it asks what to record.
- **A plan:** this applies only if you write plans with the [compound-engineering](https://github.com/EveryInc/compound-engineering-plugin) plugin, such as the requirements plan its `ce-brainstorm` skill writes. To record one, pass its path, or run the skill with no arguments right after writing it. The issue's body is then the plan's content: each template heading takes the plan's section of the same name, so the crew session that takes the issue needs no file outside it. A plan the issue does not record stays out of its body, even when the session wrote one. Without such a plan, the skill fills the template from what you wrote.

## What it does

1. It decides the type from its table, asking only when it is not clear.
2. It fills the type's template from `.github/ISSUE_TEMPLATE/` with what you wrote and what the session knows. The template's frontmatter is dropped: its `labels`, `title` and `assignees` are not used. When the template file is missing, it writes a free-form body.
3. It creates the type's label when the repository does not have it yet.
4. It creates the issue with a short title taken from what you wrote and exactly the type's label, no other.
5. It prints the issue's link and label, and says when the template file was missing, which plan the body was copied from, that the session wrote a plan the body does not use, or that the rule that takes the label is turned off in the crew repository.

It creates the issue at once, with no preview and no confirmation. To fix a mistake, edit the issue on GitHub. With a rule's `ready` label, crew may take the issue at its next poll with a free slot, so fix a wrong label quickly.

## Put a plan in an existing issue

`/cw-update-issue-plan [label]` copies the session's plan file into the issue the session is working on, such as an idea you parked and then brainstormed. It finds the issue from the session and asks only when it cannot tell which one. The plan file is the one compound-engineering's `ce-brainstorm` writes when you confirm its synthesis, or the same file after `ce-plan` enriched it. The skill does not write the plan itself: without a plan file it stops and changes nothing, so let the brainstorm write its file first. The body follows the template of the issue's type, and the old body is kept in a comment.

An optional `label` then moves the issue to that type's label. Without one, the skill runs the prompt it holds in its step 8, filled with the issue as `/cw-brainstorm` fills its prompt, so the label that always comes next needs no typing. In the crew repository, that prompt moves the issue from `crew:brainstorm:in progress` to `crew:brainstorm:done`. A rule's `ready` label starts crew's work at the next poll with a free slot.

```text
/cw-update-issue-plan
/cw-update-issue-plan crew:development:ready
```

It refuses a label that is not one of its types' labels, and leaves an issue alone while it carries one of the running labels the skill lists, since crew is then working on it. A label that your own session put on the issue, such as the one `/cw-brainstorm` set, does not stop it. Install it like `/cw-create-issue`, linking `.agents/skills/cw-update-issue-plan` into `~/.claude/skills/`.

## Brainstorm an issue

`/cw-brainstorm <issue>` runs the brainstorm prompt the skill holds for an issue, in your session. A brainstorm asks you questions, so crew cannot run it unattended. The skill fills its prompt with the issue as crew fills an action's prompt, and follows it as if you had typed it. The skill adds nothing of its own: what to check, which labels to change and which skill to run are all in the prompt.

```text
/cw-brainstorm #42
```

The issue can be `#42`, `42` or its URL. Without one, the skill asks which issue.

The crew repository's prompt goes on only when the issue carries `crew:brainstorm:ready`. It then moves the issue to `crew:brainstorm:in progress`, so you can see it is being brainstormed, and runs `/compound-engineering:ce-brainstorm` on it. When the brainstorm has written its plan file, `/cw-update-issue-plan` copies it into the issue and moves the issue to `crew:brainstorm:done`. From there crew hands it on by itself: its `promote brainstorm` rule moves it to `crew:triage:ready`, the triage rule finds what blocks it and what it blocks, and `promote triage` moves it to `crew:development:ready`. Until the plan is in the issue, the issue stays in `crew:brainstorm:in progress`, which no rule takes; if you drop the brainstorm, put its label back by hand.

Install it like `/cw-create-issue`, linking `.agents/skills/cw-brainstorm` into `~/.claude/skills/`.

## Limits

- **crew takes only the issues its code owners and bots opened.** An issue someone else opens, from a template on the web or with these skills, is ignored whatever its label. The skills run as your `gh` login, so the issues you create with them are taken when you are a code owner: see [Code owners](/guide/crew#code-owners).
- **The skills do not follow your config.** When you rename a rule's label in `.crew/config.yaml`, change it in the skills too, or they put a label no rule takes.
