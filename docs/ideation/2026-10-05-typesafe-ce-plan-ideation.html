Grounding Context

Topic Context

The thing being reproduced

ce-plan (compound-engineering 3.30.3) is a long prose procedure: a 60-line SKILL.md plus 19 reference files. Its phases run in order: output and resume routing, source intake, bootstrap, blockers, the Output Contract gate (Direct, Chat brief or Durable), depth (Lightweight, Standard or Deep), scoping synthesis, research, planning questions, structure (implementation units with stable U-IDs), writing, a pre-write review of about 20 checks, the confidence check that picks sections to deepen, document review, and a handoff menu.

About 23 decisions branch the flow. Most are written as prose heuristics: "use judgment", "borderline means stay silent", "clearly high", "material", "thin". Two gates overlap and depend on order: contract and depth are decided separately, and research can later bump Lightweight to Standard. The plan body is free generation. Research runs through about 14 subagents whose output depends on the tools the host has. Timestamps, random scratch directories and model-chosen filenames add more variation.

What Jev is, measured live today

  • Jev returns typed answers with calibrated probabilities, not text. There are three primitives: Choice picks one of a set and returns a confidence. Noul returns the probability of yes, with no confidence field. Score returns a probability-weighted position on 2 to 10 described levels. One request is one state plus many named questions, answered in parallel. No answer sees another.
  • Calls through the env var key worked with the Python SDK (pip install typesafe-sdk; TypeSafeClient().system_one(state=..., questions=...)). A 3-question call used about 525 input tokens, about $0.00002, and took about 250 ms warm. 60 Nouls in one request took 335 ms. Output tokens are free.
  • Jev is not deterministic. Six identical requests returned the same winning answer every time, but the probabilities moved by 0.01 to 0.03. The order of keys in the probabilities dict also changed. The docs describe no cache or idempotency key.
  • The docs' jaggedness page for jev-1.13 says Jev reads literally, so write exact conditions and boundary cases. Don't ask it to count, do math or compare dates. Don't send irrelevant state. Treat state as untrusted. It does not generate text, so turn extraction into a Choice over candidates. Keep questions and thresholds in one reviewable place, edit questions written by agents by hand, and pin jev-1.13.0 once thresholds are tuned.

The SDK shape that worked

from typesafe_sdk import TypeSafeClient, Choice, Noul, Score

with TypeSafeClient(model="jev-1.13.0") as client:   # reads TYPESAFE_API_KEY
    r = client.system_one(
        state={"request": request_text, "upstream": contract_summary},
        questions={
            "tier": Choice(instructions="...", criteria={"direct": "...", "chat_brief": "...", "durable": "..."}),
            "risk_surface": Noul(instructions="...", criteria={"true": "...", "false": "..."}),
            "ambiguity": Score(instructions="...", criteria=["one reading", "minor gaps", "several readings", "goal unclear"]),
        })
    r.answers["tier"].choice, r.answers["tier"].probabilities, r.model, r.usage.input_tokens

What this repository already learned

  • cw-split-plan measures plan size in code (measure.sh: characters and distinct R/AE IDs) and asks Jev one Noul per part in shadow. The answer is recorded and gates nothing. The split plan's own decision: "Size is measured in code; Jev judges delivery, not size … no Jev score could be shown to predict cost better than size, whose correlation is already 0.83."
  • Jev experiments on 2026-10-05 found two strong uses: judging how a session ended from its last message, and ranking likely blockers. They found one failure: auto-answering brainstorm questions was "no better than always taking the recommended option once thresholds were chosen on held-out sessions". Rules carried forward: one pair per request beat 49 candidates in one state (0.93 vs 0.58), choose thresholds on held-out data, run each Choice in two option orders, and never send empty text.
  • The evaluation data is real but thin: 34 lfg sessions in .crew/logs, 18 complete cost runs, and a handful of plans.

Prior art

Spec-driven tools (Spec Kit, Kiro) fix the phase sequence and templates, but an LLM still writes the prose and makes the scoping calls. Structured-output libraries (Instructor, BAML, Outlines) fix the shape of output, not its content. Temporal makes workflows reproducible by recording each activity's result and replaying it, with workflow code free of clocks and randomness. Research on selective prediction warns against abstaining on a single raw confidence (arXiv 2603.21172). The web search found no tool that makes the planning decisions themselves typed, calibrated judgments with logged probabilities.

The limit every idea below accepts: Jev decides; it does not write. Plan prose (Problem Frame, decision rationale, unit Approach, test scenarios) still needs a generative model. "As deterministic as possible" can cover the gates, the structure, the IDs, the rendering and the verification. It cannot cover the words.

Topic Axes

  1. Gates: the routing and classification decisions before and during planning.
  2. The plan as data: schema, units, IDs, the generated residue, rendering.
  3. Review and verification: the confidence gate, pre-write checks, claims checked against sources.
  4. Run record, replay and calibration: reproducibility, model pinning, thresholds from held-out data.
  5. People and escalation: when the app asks a person, and how uncertainty is handled.

1. Single-snapshot intake: atomic facets in one request, routing in a decision table

GatesConfidence 80%Complexity Medium
Description
Replace ce-plan's chain of prose gates with one system_one request. It asks every intake facet as its own atomic question over one small state that code builds. Facets include: touches a risk surface, has a decision the user would weigh, needs multi-pass verification, asks for a file or format, spans several components, bug-shaped, domain, ambiguity, and needs external research. A plain Python decision table then applies ce-plan's precedence: pins first, then "uncertain → heavier tier", then the Lightweight → Standard bump. It emits the Output Contract tier, the depth and the flags. For each outcome the table also prints which facets drove it, like the reason codes a credit scorecard gives.
Basis
direct: ce-plan's pain point is "overlapping order-dependent gates (contract vs depth decided separately, reclassified later)". SKILL.md: "When the tier is still uncertain after those reads, take the heavier one." TypeSafe docs: "ask every question once in one request, including speculative ones" and "split complex judgments into atomic questions weighted in code". Measured live: answers never feed each other, and 60 Nouls took 335 ms. external: faceted classification (Ranganathan) and adverse-action reason codes.
Rationale
Order dependence is the largest source of path variation that does not come from generation. When every facet is read from the same snapshot, routing becomes a pure function of logged answers. A disagreement can then be traced to one named facet, and the table itself becomes the spec that people review and test.
Downsides
Each facet must be written literally, with boundary cases, and checked by a person. The table encodes ce-plan's heuristics, which gets them wrong in the same places the prose does until real data corrects them. Running this gate on every issue to skip planning altogether is tempting, but how many issues it would skip is unmeasured.

2. Judgment cassette: record every Jev call and replay it

Run record, replay and calibrationConfidence 85%Complexity Low
Description
Store every Jev call in a cassette (SQLite or JSONL next to the plan). The key is a hash of the pinned model, the canonical state JSON and the canonical question. The value holds the answer, the sorted probabilities, response.model and the token usage. Re-runs, resumes and deepening replay what is recorded and pay only for questions whose facts changed. The orchestrator contains no clock or randomness: IDs, filenames and "recent" windows come from the input or the cassette. Live answers within 0.03 of a threshold, the observed jitter, are flagged as unstable and never re-asked.
Basis
direct: live probe: "NOT bit-identical — probabilities jitter 0.01-0.03 … No caching/idempotency key documented". TypeSafe docs: "pin jev-1.13.0 when thresholds were tuned, log response.model". ce-plan's pain points include timestamps, random scratch directories and model-chosen filenames. external: Temporal's event-sourced replay, in which completed activities return their recorded results and workflow code must be deterministic.
Rationale
The API promises no repeatability, so the app has to supply it. The cassette turns "as deterministic as possible" into a property you can test: the same inputs give the same plan bytes. Every difference then comes from a named fact that changed. The same file later supplies the labelled data for idea 5.
Downsides
This is reproducibility of a recorded run, not determinism of a fresh one. The rule for canonicalising state decides what counts as "the same case", and a careless rule either busts the cache on whitespace or replays stale answers. Re-asking inside the band was considered and dropped, because a re-ask can flip again.

3. The plan is a typed record; markdown is a rendering

The plan as dataConfidence 75%Complexity Medium
Description
The app's output is a Pydantic PlanRecord holding the Goal Capsule, the R/A/F/AE IDs, the decisions, the U-IDs, the Verification Contract, the Definition of Done and every gate answer with its probability. Code assigns the IDs and enforces uniqueness, no renumbering and acyclic dependencies. A Jinja template renders it to ce-plan's markdown or HTML with identical bytes every time. Traceability works like double-entry bookkeeping: each R/AE has to appear in at least one unit and in the Verification Contract, or the write fails. Jev checks each pair's substance with one Noul per (requirement, unit), asking "does this unit advance this requirement?". Free text lives only in named slots: copied verbatim from the source, or filled by a labelled generative step.
Basis
direct: TypeSafe autoformat cookbook: "the model never generates text … and code does the rendering, so every character of the output comes from the input". ce-plan plan-sections: "the section names and anchor ids are the stable contract". The deepening-workflow checklist flags requirements "vague or disconnected from implementation units". Memory: one pair per request beat 49 candidates in one state (0.93 vs 0.58).
Rationale
Variation stays inside a few slots you can audit, not spread across a whole document. Downstream consumers (cw-split-plan's size measure, an lfg session, an acceptance tester) can read the record instead of re-parsing prose. For crew, that makes the record the contract between brainstorm, plan, split and work.
Downsides
Units still come from a generative step, so the balance check verifies them but does not create them. Computing units from a requirement × component matrix was considered and set aside as an experiment, because it may produce worse plans than ce-plan. Pairwise checks mean one small request per pair, run in parallel with the async client, rather than one large shared state.

4. The generator proposes, Jev and code accept

Review and verificationConfidence 70%Complexity Medium
Description
Each generated slot (Problem Frame, decision rationale, unit Approach, test scenarios) comes from a bounded per-field LLM call that sees only that field's inputs. Nothing is accepted until it passes a typed acceptance suite in two layers. In the first layer, every claim carries {file, line range, quote}. Code checks that the quote exists, and one Choice per claim asks whether the quote supports it (the citation_check pattern). In the second layer, ce-plan's confidence checklist runs as atomic Nouls, each over only its own section. Trigger counts, the critical-section bonus, the 2+ threshold and the top-N sort run in code, with ties broken by registry order. A field that fails is regenerated with only the failing item as feedback, up to N times, then becomes a blocker. Keep a final post-write pass too, because the gate is meant to score a finished plan.
Basis
direct: deepening-workflow: "Trigger count … Critical-section bonus - add 1 … Treat a section as a candidate if: it hits 2+ total points". The grounding calls the confidence gate "code arithmetic + Noul per checklist line — the cleanest Jev fit". Jaggedness page: don't ask Jev to count. citation_check cookbook: string-match the quote first, then a Choice on support. Docs: "state is untrusted", which argues for short, bounded quotes.
Rationale
Code verifies that the evidence exists, and Jev judges only whether it supports the claim. So the generator can stay creative while acceptance is typed, logged and repeatable. "Which sections get deepened", the most variable step in ce-plan, becomes a pure function you can unit-test.
Downsides
The generator is not Jev, so the plan's words stay non-deterministic. The suite constrains and verifies them. Judgments like "describes product behavior absent from requirements" are unmeasured. Tuning checklist weights from revision history is a later step, because there are too few plans to fit them today.

5. A question bank where every gate starts in shadow

Run record, replay and calibrationConfidence 80%Complexity Medium
Description
Every question lives in one versioned bank (YAML or a Python module), not as strings scattered through code. Each entry holds its ID, primitive, instructions, criteria, pinned model, act / confirm / don't-act bands, risk class and a pointer to labelled examples. A lint enforces the docs' rules: no empty state, no "and" inside a Noul, no numeric-only Score levels, and every Choice has an other or none option. Every gate starts in shadow and is recorded next to what ce-plan, a person or a trivial rule decided. Trivial rules include "always Durable", "always the recommended option" and a zero-LLM plan built only from the repo's own precedent. A gate is promoted to acting only after it beats its trivial baseline leave-one-session-out, with each Choice run in both option orders. CI re-checks every promoted gate when the model pin moves.
Basis
direct: TypeSafe docs: "keep questions and thresholds in one reviewable place, agents write weak questions so edit by hand". Memory: auto-answering brainstorm questions was "no better than always taking the recommended option once thresholds were chosen on held-out sessions", and "an in-sample threshold misled once". cw-split-plan: Jev's answers are recorded in shadow so that "the records it leaves become the labelled data".
Rationale
Without this, the app becomes a Jev showcase full of gates of unknown accuracy. With it, each gate earns its autonomy, a non-fit is recorded honestly (the repo's own rule: "say plainly when Jev does not fit"), and model upgrades fail a test instead of silently changing plans.
Downsides
34 sessions and a few plans will only label a few gates. Most gates will stay in shadow for a long time, and that is the honest result. Calibrating against downstream outcomes (session cost, how the session ended) is the long-term goal, but those outcomes are confounded by issue size and too few to fit today.

6. Jev decides whether to ask, never what the answer is

People and escalationConfidence 75%Complexity Low
Description
Jev classifies each open question as technical or product, and flags "a decision the user would weigh". It never answers a product question. With a person present, middle-band questions are collected and asked once per phase, with Jev's pick shown as a visible default. With no person present (crew's normal case), technical unknowns become typed entries. Each entry goes either into ce-plan's own "Deferred to implementation" list or into an Assumptions table that shows its probability. A product question ends the run with status: blocked and a recovery_path, or carries the brainstorm's recommended option marked unconfirmed. "Never re-ask a settled decision" is enforced in code against a store of settled decisions. For a consequential Choice, the bank asks it in both option orders within the same request. If the two orders disagree, the gate goes to the confirm band whatever the top probability is.
Basis
direct: memory: Jev "FAILED for auto-answering brainstorm questions", and adding past answers "made the brainstorm prediction worse". structure.md: "Deferred to implementation - the answer depends on code changes, runtime behavior, or execution-time discovery". confidence.md: "Low confidence: Do not act. Route to a human, request clarification, or fall back". Live probe and docs: first-option lean, and running each Choice in two orders.
Rationale
Jev is used where it measured well (routing, flagging) and kept away from where it failed. Interruptions, the main source of path variation in ce-plan, become rare, batched and recorded. Unattended runs stay deterministic and auditable instead of guessing.
Downsides
The technical-vs-product Choice is itself unmeasured, so it starts in shadow like every other gate. Value-of-information question selection and an escalation cascade to a reasoning LLM were considered and left out. The first is over-engineered for a handful of facets, and the second puts an LLM back into the gates.

7. Local research by enumeration plus pairwise Nouls

GatesConfidence 70%Complexity Medium
Description
Replace the cheap lookups done by ce-plan's research subagents. Code lists the candidates: git ls-files, docs/solutions/ frontmatter (module, tags, problem_type), past docs/plans/ units and git log. Jev filters them with one small request per (requirement, candidate) pair, run in parallel with the async client, and code keeps those above the threshold. "Fewer than 3 local examples, so research externally" becomes an exact count. External research runs only when explicitly requested, or when a Noul and the count agree it is needed.
Basis
direct: the grounding's pain point: "research by ~14 subagents varies with environment/tools". rerank cookbook: one question per query-candidate pair. Memory: one pair per request scored 0.93 vs 0.58 for bulk state. Jaggedness page: "don't send irrelevant state … filter first, or a Noul relevance filter".
Rationale
Research is the largest source of variation in ce-plan's input. The same repo SHA, candidates and threshold give the same evidence set, so everything downstream can replay. It costs cents and stops depending on the tools a host exposes.
Downsides
It loses the open-ended discovery that a research agent does. Treat it as the baseline that covers routine lookups, with an agent kept for the gaps it reports. At 80 requests per second, a large repo needs a prefilter in code before the pairwise pass.
