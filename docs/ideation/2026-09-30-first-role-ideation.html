Which role does crew stand up first? The first round of this ideation picked the strategist / PM. The plan that came out of it needed 3 GitHub Apps, a token launcher, a ruleset and a board sync, and it was too heavy, so the boss decided not to build the PM now. This round starts from the two positions the boss proposed, the customer and whoever writes acceptance tests from the docs, and adds one test: the least mechanism that delivers value now.

Top pick: the first role is the acceptance-test writer. It is one agent file and one Claude Code session that reads only the docs and the acceptance examples, never the code, and writes behavior tests while development happens in parallel. It posts with the boss's gh login, as /pr-review already does, and needs no GitHub App, board or launcher.

Ideas 2 to 4 shape that role. Ideas 5 and 6 are the customer, which comes second. Idea 7 is the link between the two.

What changed since the first round: the PM was dropped for weight, not for value. This round's research shows the cheapest check by someone other than the author is a test written by another session from the spec, because the implementer should not decide whether its own code is correct. No study compares tester and customer head to head; "tester first" is an argument, not a measurement.

Grounding context

Codebase context

  • thatsnotmynameio/crew is public and nearly empty: STRATEGY.md, AGENTS.md, the /pr-review skill and review-reader agent in .agents/, CI workflows that call thatsnotmynameio/.github, and docs on docs.page. There is no application code, no tests, no issues and no custom labels.
  • The org ruleset ("main rule") requires a PR, 0 approvals, resolved threads and squash merges. The org has one human, the boss.
  • Installed plugins already cover strategy, ideation, brainstorming, planning, implementation and code review. None writes acceptance tests from a requirements doc as a separate role, and none acts as a customer.
  • ce-brainstorm plans carry acceptance examples with IDs in Given/When/Then form; the PM plan, for example, has AE1 to AE8.
  • The docs home page is still the template placeholder: "Replace this page with what the project does and who it is for." (docs/index.mdx).

User-named references

  • STRATEGY.md: "no change merges without approval from a role other than its author"; "Resist a change when: it would let work reach production — or merge — without a check by someone other than its author."; the "Customer feedback loop" track names the boss's private Home Assistant repo.
  • The boss's direction for this round: don't build the PM now, simplify, and start from the customer or from whoever writes acceptance tests.

External context

  • Test author separate from implementer: when one agent writes both, a misread requirement goes into the code and the test at once. AgentCoder (arXiv 2312.13010) splits programmer and test designer. Tests anchored to requirements find more defects (arXiv 2607.06636).
  • Agents game tests: GPT-5 cheated on 76% of ImpossibleBench's impossible tasks (Oct 2025). Asking them not to barely helps. Structure works: tests outside the implementer's write access, review of every test change, hidden suites.
  • Tests that can never fail: a solo developer had 6,104 tests at 94.6% coverage while a route guard never worked in production. It surfaced only when the guard was removed and the tests still passed. A 2026 study of 1.2M commits shows agents adding mocks in 36% of their commits.
  • Customer agents: LinkedIn's QA Agent found 200+ valid bugs but needed a detect-then-verify stage to stay precise. Agentic exploratory QA sits on top of scripted tests, not in place of them.

1. The acceptance-test writer goes first, as one file and one session

Description
The first role is an agent file in .agents/agents/, opened in its own Claude Code session. It gets only the docs and a plan's acceptance examples, never the code, and writes behavior tests while the boss implements with Claude Code in another session. It posts with the boss's gh login, and its PR or commit carries a line naming the role. No GitHub App, token, board or launcher.
Basis
direct STRATEGY.md: "Resist a change when: it would let work reach production — or merge — without a check by someone other than its author." direct .agents/skills/pr-review/SKILL.md: "post the review with the user's gh". external AgentCoder (arXiv 2312.13010): a test designer independent of the programmer.
Rationale
It is the cheapest form of the strategy's core rule: the implementer does not write the test that judges it. The result is a deterministic pass or fail, not another LLM's opinion. It works in any of the boss's repos that has a plan, not only in crew.
Downsides
For now the separation is a convention. With 0 approvals and one human, nothing stops the implementer from editing a test. The test runner and language are also undecided, because the repo has none yet.

2. Acceptance examples are the contract

Description
Each acceptance example becomes one test whose name carries the example's ID (AE3 → test_ae3_…). A grep shows which examples have a test and which are red. When a doc sentence can't become one deterministic test, the tester asks on the doc's PR instead of guessing.
Basis
direct the shelved PM plan (since removed): "AE1. Covers R11. Given an ideation with 7 surviving ideas, when its PR merges, then …". external Research names requirements quality as the bottleneck for spec-driven test writers.
Rationale
No new format is needed, because ce-brainstorm already writes these examples. The link from requirement to example to test comes for free, and "this can't be tested" improves the doc before anyone builds it.
Downsides
Plans without acceptance examples leave the tester with no input. Vague examples produce questions that pull the boss back into the doc.

3. First job: the promises crew already makes

Description
With no code in the repo, the tester starts from what the docs already promise. For example: VERSION is MAJOR.MINOR.PATCH and never below the latest release; CLAUDE.md, .claude/skills and .claude/agents point at their sources in AGENTS.md and .agents/. The first case it would write, "nothing merges without approval from someone other than its author", already exposes a real contradiction: the ruleset requires 0 approvals.
Basis
direct AGENTS.md: "The version must be MAJOR.MINOR.PATCH and not below the latest release"; "AGENTS.md and .agents/ are the source; CLAUDE.md, .claude/skills and .claude/agents are symlinks to them." direct Ruleset "main rule": required_approving_review_count: 0.
Rationale
The role shows results today, in this repo, and settles the test convention (runner and location) before the first feature. The 0-approvals finding is something the boss had not seen.
Downsides
CI already covers much of this with the version check and docs:check, so the direct gain is small. The ruleset case works better as a finding than as a permanent test, since it would stay red until the rule changes.

4. Tests land before code, by convention

Description
Like a pre-registered clinical trial, the acceptance tests land in their own PR before the implementation, marked expected-to-fail. The implementation PR only removes the markers and never touches assertions. Anyone can see that in one diff, and /pr-review can treat an assertion change in an implementation PR as a serious finding. No new check, no App.
Basis
external Clinical-trial pre-registration (ClinicalTrials.gov). external ImpossibleBench: structural controls work, requests don't. direct .agents/skills/pr-review/rules.md holds the repo's review rules.
Rationale
History on main becomes the record of what was promised before the code existed. A test that passes before the feature exists shows up at once.
Downsides
It is a convention, not a block. With one human and 0 approvals, the guarantee depends on the boss and the review reading the diff.

5. The customer reads only the published docs, in a clean environment

Description
The customer is a session without the boss's plugins, in a temporary directory, given only the docs site and a goal ("start using crew in an empty repo"). Its main output is a list of "places I had to guess", filed as issues labeled bug. Its first run would already find that the home page is a placeholder.
Basis
direct docs/index.mdx: "Replace this page with what the project does and who it is for." direct STRATEGY.md: "crew stays configurable and documented enough for them to adopt." external LinkedIn's QA Agent: detect, then verify.
Rationale
It is the generic customer the boss asked for, and the lightest one to run: no identity, no CI. The clean environment is what makes it generic. A session with every plugin fills gaps on its own and can't see what's missing.
Downsides
Today the docs are nearly empty, so it has little to read beyond the placeholder. It pays off once a real guide exists, which is why it comes second.
i6The customer's worldConfidence 75%Complexity Low

6. Reports from private repos arrive de-identified

Description
When a customer runs in a private repo, such as the Home Assistant one, and reports to crew, the report follows an aviation near-miss format: goal, what it tried, what happened, what it expected, and whether it only worked with a workaround. Before filing, it strips entity names, hosts and paths. It is a rule of the customer role, not infrastructure.
Basis
direct STRATEGY.md: "Agents in consuming repos (e.g. my private Home Assistant repo) report back to the product team." direct The crew repo is public. external NASA's ASRS: structured, de-identified reports.
Rationale
It keeps details of the boss's home out of a public tracker, a risk nobody had raised. Near-misses show friction before it becomes a bug.
Downsides
The Home Assistant repo doesn't use crew yet, so this is a rule for when the customer exists, not a first step.

7. Later: the customer finds, the tester ratchets

Description
Once both roles exist, they meet in one artifact. A customer report counts only when the tester can reproduce it as a failing acceptance example, and it closes when that test turns green. Anything that doesn't reproduce goes back as noise or as a doc gap.
Basis
external LinkedIn's QA Agent detects, then verifies to stay precise. reasoned Turning reproduction into a test is the verify stage, and each escaped defect can only escape once.
Rationale
It joins the boss's two positions with no board, App or protocol. Escaped defects, one of the strategy's metrics, become regression tests.
Downsides
It needs both roles working before it proves anything. It is the third step, not the first.
