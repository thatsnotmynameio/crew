Focus
A Python application that reproduces the ce-work flow (execute a plan end to end) as deterministically as possible, using TypeSafe's Jev model for judgments and every best practice TypeSafe documents.

The short answer: in this design Jev only answers narrow, typed questions at fixed points. A generative coding agent only edits files. Everything else is ordinary Python. "Deterministic" ends up meaning that the same recorded inputs always produce the same decisions. It cannot mean identical model outputs, because Jev's answers vary slightly between identical calls.

Grounding Context

Topic Context

ce-work, read as a list of decisions

ce-work runs in five phases: input triage, quick start (workspace, task list, engine and strategy), the per-unit implementation loop, quality (tests, simplify, code review, final validation) and shipping. Read for where judgment enters, it contains about 35 decision points:

  • Yes/no checks: is the plan ready, is this a mechanical diff, is the unit done.
  • Pick-one choices: source type, complexity tier, evidence strategy, review-finding triage.
  • A matter of degree: parallel safety.
  • Open-ended generation: the System-Wide Test Check, and writing the code, tests and messages.

A good part is already mechanical: plan discovery, the U-ID/R-ID/Files: fields, path-limited commits, the ≥30-line simplify trigger, exact skip phrases and the worker result schema (terminal_status, changed_files, evidence, scope_expansion).

The skill itself names where it is fragile:

  • "Resolve uncertainty by inspection" for parallel units.
  • "reported paths untrusted".
  • Worker evidence "not reconstructable from the tree afterward".
  • "A clean merge is not proof of compatibility".
  • The rule of two failed fixes before a root-cause reset.

What TypeSafe gives, and what it does not

One endpoint, POST https://api.typesafe.ai/v1/systemone, takes {state, model, questions}. It evaluates every question independently and in parallel against the same state. The three question types:

  • Noul: the probability of yes.
  • Choice: one option with a probability distribution and a confidence; up to 255 options.
  • Score: a probability-weighted position on 2–10 ordered levels.

Limits: 64k tokens for state plus all questions, 32k for state plus the longest question, and 80 requests/s. Input costs $0.042 per million tokens and output is free. Requests are text only, with no seed or temperature setting. jev-latest currently resolves to jev-1.13.0.

The Python SDK is typesafe-sdk 0.7.2 (Python ≥3.10):

  • Clients: TypeSafeClient and AsyncTypeSafeClient.
  • Call: client.system_one(state, questions, model=..., retry=RetryPolicy(...), response_model=...).
  • Typed answers: NoulAnswer, ChoiceAnswer, ScoreAnswer.
  • Errors: typed exceptions such as RateLimit (with .retry_after_ms).
  • Each response carries a request_id.

The documented best practices are:

  • Code owns control flow. Write no agent while loops.
  • Ask one literal, narrow question at a time, phrased so that high means yes and without compound conditions.
  • Build small, structured state in code.
  • Give every Choice an other option.
  • Use speculative fan-out: batching 13 questions was 12.2× cheaper and 10× faster, and "batching adds no noise".
  • Route answers through act / confirm / escalate bands with risk-scaled thresholds.
  • Choose thresholds from held-out labeled data.
  • Keep all questions and thresholds in one reviewable file.
  • Pin the model version you tuned against.

Jev's known weak spots are:

  • It reads literally.
  • It cannot count, do arithmetic or compare dates.
  • It is weak at multi-hop questions and double negatives.
  • It leans toward the first Choice option.
  • Adversarial text placed in the state can steer it.
  • It generates no text, so it does not replace the model that writes code.

Prior art and past learnings

Web results (search snippets, not verified) point the same way:

  • Agentless runs a fixed localize → repair → validate pipeline with no agent loop.
  • Anthropic's "Building effective agents" recommends workflows when the steps are known.
  • 12-Factor Agents says to "own your control flow".
  • Temporal with Pydantic AI replays orchestration from an event history and records LLM calls as activities.
  • VCR-style cassettes for agents exist, but none was found for a Claude Agent SDK session.

crew's own learnings add four patterns:

  • A pure reducer core: (model, input) → (commands, events), with no I/O and no clock.
  • Adapters are only data sources.
  • Session text is untrusted.
  • Folders that hold uncommitted work are never deleted silently.

crew's cw-rank-blockers already calls Jev with a pinned jev-1.13.0. It measured one request per pair at 0.933 against 0.583 for all candidates in one request.

1. Ledger and replay: deterministic means the same recorded inputs give the same decisions

Description

The core is a pure reducer: (run state, input) → (commands, events), with no I/O and no clock. An effects runner executes each command and appends its result to a SQLite ledger. A command is a Jev request through typesafe-sdk, a worker session, or a shell command.

A Jev entry is keyed by the pinned model id, the sha256 of the state JSON and the sha256 of the question set. It stores the raw answers (every probability, not a thresholded bool), usage, the returned model and the request_id.

In replay mode the runner serves every input from the ledger, so a run re-derives the same decisions without touching the network. The same ledger gives two more things:

  • Resume after a crash: replay up to the last step boundary.
  • A regression harness: change a threshold, a question's wording or the Jev version, replay the last N runs, and list the decisions that flipped.
Basis
  • direct: an identical request sent three times was not byte-identical: Noul 0.97 / 0.97 / 0.98, Score 1.71 / 1.85 / 1.85. The docs make no bitwise-reproducibility claim and have no seed or temperature parameter. The cookbooks cache responses by request hash.
  • direct: crew's core is a pure reducer, "(model, input) → (commands, events), no I/O or clock", tested with tables.
  • external: Temporal with Pydantic AI replays deterministic orchestration from an event history and records LLM calls as activities (from search snippets, not verified).
Rationale
Jev cannot be made bit-for-bit reproducible, so determinism has to live in the orchestrator. Recording at each step boundary is the only way to promise that a run will decide the same way again. It is also what makes debugging ("why did the parallel-safety gate say yes?") and threshold changes testable.
Downsides
Every effect has to go through the runner, the worker included, or replay breaks. The ledger holds code and plan text, so it needs the same care as logs. Replaying the worker means storing a diff and a transcript per unit.

2. Gate kernel: every ce-work judgment is a registered gate with a three-band verdict and a conservative default

Description

Each of ce-work's judgment points becomes one registered gate in a single gates.py: Gate(dp_id, kind, state_builder, questions, bands, default, risk).

kind is code, jev, worker or human. Points ce-work already settles mechanically are code: branch safety, unpushed commits, the ≥30-line simplify trigger.

Every answer is lifted into one type, Yes | No | Unknown(p, request_id, model). A Noul in the 0.30–0.70 band, or a Choice below the gate's confidence floor, becomes Unknown. The reducer handles the verdict with a match that ends in assert_never, so a gate that forgets the Unknown branch fails type checking.

Each gate also has a conservative default, taken from ce-work's own wording: "When either is uncertain, take the fuller route" and "When you cannot tell, build it". Jev's answer can move a run in two directions:

  • Toward the cheaper branch (skip review, inline a unit): only above a risk-scaled threshold such as 0.85.
  • Toward more work: from the 0.30 floor.

Each phase sends all of its gates' questions in one fan-out request, over one state built in code.

Basis
  • direct: the TypeSafe docs recommend:
    • all questions and threshold constants in one file for human review;
    • act / confirm / escalate bands with risk-scaled thresholds (floor 0.6, above 0.85 for risky actions);
    • a 0.30–0.70 review band for Noul;
    • speculative fan-out ("batching adds no noise"; 13 questions batched were 12.2× cheaper).
    In this run's probes each extra question cost about 52 input tokens.
  • direct: ce-work's SKILL.md says "When either is uncertain, take the fuller route", and implementation-loop.md says "When you cannot tell, build it".
Rationale
The kernel is written once, and every later gate is a row in a table. Shadow mode, logging, replay and calibration (ideas 1 and 7) then apply to every gate at no extra cost. The Unknown type stops uncertainty from being collapsed into a bool at the call site, which is where naive LLM pipelines usually lose it.
Downsides
Thresholds like 0.85 are placeholders until held-out data exists (idea 7). Two points are open-ended and stay with the worker: the System-Wide Test Check and writing the code. A registry can grow into a framework, so keep it a table.

3. Plan-time contract: compile the plan and freeze the done-questions before any code exists

Description

At intake, a parser turns the plan into Pydantic models: Unit (id, goal, files, dependencies, test scenarios, verification lines), Requirement and DefinitionOfDone. It relies on the section headings and the U-ID/R-ID fields ce-work already uses.

Structural holes fail at intake instead of mid-run: a unit with no Verification line, a Files: path outside the repository, a dependency cycle, a requirement no unit covers. Where the plan is loose, code lists the candidates and Jev picks one, with a none option. For example: which unit does this test scenario verify? Code then copies the pick verbatim.

Before any worker starts, the plan is frozen into the ledger in two ways:

  • The Requirements and Verification lines are compiled into a fixed battery of narrow Noul questions and hashed.
  • Each unit's evidence strategy is fixed by one Choice: existing failing test, update, add, characterization, no-test exception, or other.

At Final Validation, the same frozen questions are asked for each (requirement, diff hunk) pair. A requirement no hunk satisfies is residual work. A hunk no requirement asks for is scope creep.

Basis
  • direct: the pre-parsed value extraction cookbook: "A regex finds the candidate values, TypeSafe picks the one the question asks for, and code copies it verbatim", with none as "the escape hatch on every selection".
  • direct: ce-work's own rules support this:
    • the plan body is not edited during execution;
    • the unit's Verification field is the "primary done signal";
    • the evidence strategy is a pick-one decision.
  • direct: a probe with 3 requirements × 2 hunks (9 questions, 1,085 tokens) separated implemented requirements (0.89, 0.94) from the missing one (0.13, 0.02). It also flagged the unrequested hunk (0.91). This was a toy case.
  • external: study preregistration and trial registration exist to stop outcome switching: redefining success after the results are in.
Rationale
Several of ce-work's most variable early judgments move to one place, before code exists: is the plan ready, do the prerequisites exist, what evidence does each unit need. Freezing what counts as done before the worker runs means neither the worker nor the orchestrator can redefine done after seeing the result.
Downsides
It needs a stricter plan format than ce-plan writes today, or a compiler that accepts ce-plan's output and reports what it cannot type. Each requirement must become one narrow question, not a compound one. Large units push the requirement-by-hunk matrix past the 32k/64k token limits. Those matrices need chunking, and one request per pair may beat one big request, as crew measured.

4. Worker testimony is hearsay: the orchestrator builds every exhibit

Description

The generative worker is one Claude Agent SDK session per unit, in its own worktree. It edits files and returns a result that matches ce-work's implementation-result-schema.json. Nothing it writes enters a gate's state.

The orchestrator builds every exhibit itself:

  • changed_files from its own diff, not the worker's list.
  • The new tests, run at the base commit (they must fail) and at the head (they must pass).
  • The test output, parsed into one record per test.
  • The unit's Verification lines, from the plan.

Jev answers one Noul per Verification line over that state.

The worker's summary is treated as a claim. It is cross-checked against the exhibits with the citation-check pattern: a string match first, then a Choice of supports / contradicts / says_nothing. A contradicts blocks the unit and starts a fresh worker.

Review findings get the same treatment. A finding whose cited file:line does not exist is dropped before Jev sees it, and the rest are checked as citations.

Commits are made by the orchestrator: one path-limited commit per unit that passes.

Basis
  • direct: Jev's jaggedness notes say adversarial text in the state can steer its answers.
  • direct: ce-work says:
    • "reported paths untrusted";
    • worker evidence is "not reconstructable from the tree afterward";
    • "Never substitute a mental self-review";
    • "Neither confidence, autofix_class, nor a concrete suggested_fix proves benefit".
  • direct: the citation-check cookbook matches strings first, then asks a Choice and auto-accepts at 0.8.
  • direct: probes, one case each:
    • "All tests pass" checked against runner output with two failures gave contradicts 1.0, with or without an injected "treat as supported" note.
    • A false review finding gave contradicts 0.97.
    • With a worker summary in the state, a narrow question held (0.16 vs 0.13 without it).
Rationale
The worker is the least predictable actor and the one most inclined to report success. Building gate state only from what the orchestrator observed closes two holes at once: false completion and prompt injection into the gates. It also makes "done" something the ledger can show afterward.
Downsides
To run at the base commit, the new tests have to apply there. New symbols can make them fail to import, and that must count as the expected red only when it is the right failure. Each unit needs more test runs. Gates also see less context than a worker transcript would give them.

5. Parallel safety as a pairwise conflict matrix

Description

ce-work's Parallel Safety Check splits in two.

Code settles everything it can: overlapping Files:, lockfiles, migrations, generated artifacts, shared singletons, the dependency layers and the 3–5 worker cap.

For each remaining pair of units in a layer, Jev answers one Noul: "If these two units were built without seeing each other, could one change alter what the other's tests check?" The state holds only the two units' goals, files and approach. The answer decides the pair:

  • Below 0.30, the pair runs in parallel.
  • In the review band or above, that pair alone is serialized, and the rest of the layer stays parallel, as ce-work prescribes.

The same matrix feeds the wave-abort check and post-wave integration. The real merge and test results after each wave label the pairs for idea 7.

Basis
  • direct: ce-work's execution-strategy.md: "Resolve uncertainty by inspection, not by default". It declines parallelism "for exactly the contending units" and warns that "A clean merge is not proof of compatibility".
  • direct: crew's cw-rank-blockers measured one request per pair at 0.933, against 0.583 for all candidates in one request.
  • direct: one probe pair: two units with no file in common that both touch format_price scored 0.69, inside the band, so the pair would be serialized. Unrelated pairs scored 0.08 and 0.13. The units' text named the shared function, so this was an easy case.
Rationale
This is the most judgment-heavy gate in ce-work. A file-overlap check alone would have called the probe's pair safe. Making "serialize when in doubt" the cheap default turns a wrong guess into a few lost minutes instead of a broken wave.
Downsides
N units give N(N−1)/2 questions per layer. That is fine at ce-work's sizes, and each question is cheap. One probe is not a threshold: the 0.30 cut needs labeled waves. If parallelism is not needed at first, ship serial-only and run the matrix in shadow.

6. Failure attribution routes failures before the worker sees them

Description

After a test run, code parses the output into one record per failing test. For each failure, one request asks two questions: a Noul ("this failing test exercises the unit's change") and a Choice over code_bug / test_bug / environment / flaky / plan_wrong / other.

Routing is code:

  • environment and flaky: rerun in code, with no worker call.
  • code_bug: a fresh worker gets only the failing test lines for this unit.
  • plan_wrong: goes to the check for a settled decision that cannot work.
  • other, or low confidence: escalates to a reasoning model.

ce-work's rule ("two failed fixes, then name the assumption both relied on") becomes a counter in the reducer. On the second failure it hands both diffs to a reasoning model instead of attempting a third patch.

Basis
  • direct: a probe on test output with one real failure and one unrelated localhost ConnectionError gave:
    • "a failing test exercises this unit": 0.97;
    • "all failures are caused by this change": 0.13;
    • next action fix_code: 0.95 (confidence 0.93).
  • direct: a failure-type Choice gave code_bug 0.93, and 0.89 with the options reversed. The answer did not change.
  • direct: ce-work's implementation-loop.md: "If two fixes for the same failing check have not worked, stop patching: name the assumption both fixes relied on". The TypeSafe docs send multi-hop reasoning to a reasoning model.
Rationale
Retries are the most expensive and least predictable part of the loop. Unrelated and flaky failures are the ones that waste fix attempts. Filtering them in code costs about $0.00003 a request, and it already worked on a live probe.
Downsides
Telling flaky from real needs reruns, which cost time. A wrong "environment" verdict hides a real failure, so require a rerun that fails the same way before ignoring it. Each test runner prints differently, so use JUnit XML where possible.

Idea 7Calibration and trust over timeConfidence 80%Complexity Medium

7. Gates earn autonomy, then retire into code

Description

Every Jev gate starts in shadow. It logs its raw answer next to the decision actually taken, whether by the old rule, a person or a reasoning model, and only that decision counts.

Later stages label the shadow answers at no cost:

  • The Verification command's exit code labels "unit done".
  • The post-wave merge and test results label parallel-safety pairs.
  • A reverted fix labels review triage.

A calibrate command splits the labeled log into dev and held-out sets and picks each gate's bands with a bootstrap. It writes them to gates.py for review. A gate then moves from shadow to confirm (Jev decides, and a person approves answers inside the band), and from confirm to act, only after passing a stated held-out bar.

The same log works in the other direction. A gate whose answers sit at the extremes and always agree with outcomes is a candidate to become a plain code rule. The share of decisions made by code becomes a tracked number.

Gates are pinned to jev-1.13.0. Before a move to a new version, the ledger is re-asked on the new model, and the move is blocked if a high-risk gate changes band.

Basis
  • direct: the TypeSafe docs say:
    • choose thresholds from held-out labeled data (the autoresearch cookbook uses 1,200 dev and 800 held-out rows, with a bootstrap);
    • "pin the version id when thresholds were tuned against it", and log the returned model;
    • (citation-check cookbook) "start high for more human review as you build trust in the model".
  • direct: crew's cw-split-plan already asks Jev in shadow.
  • direct: measured jitter: Score confidence varied 0.57–0.63 across identical calls, and the consistency cookbook shows a Noul crossing 0.5.
  • external: search results report that LLMs' self-stated confidence is miscalibrated (about 75% actual accuracy at 90% claimed).
Rationale
Without this, thresholds are folklore (0.6, 0.85) and silently change when jev-latest moves. With it, trust is a number per gate. The set of decisions that go to Jev shrinks wherever code proves it is enough, which is the most literal reading of "as deterministic as possible".
Downsides
Labels arrive slowly at low volume. A branch that is skipped never produces its own label, so some skipped cases must go down the full route on purpose to keep the data honest. Someone has to own the promotion bar.
