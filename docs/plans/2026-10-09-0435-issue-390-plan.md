## Planning Contract

### Key Technical Decisions

- KTD8. **Severity mapping: every tool reports at a SARIF level of `error`, `warning` or `note`, and none is remapped.** This answers the Product Contract's deferred question.
  - CodeQL reports its own levels plus `security-severity`.
  - Opengrep maps `ERROR`, `WARNING` and `INFO` to `error`, `warning` and `note`.
  - zizmor maps its severities to SARIF levels.
  - gitleaks writes no level, and code scanning reads a missing level as `warning`.
  - `tools/shellchecksarif` maps `error` to `error`, `warning` to `warning`, and `info` and `style` to `note`. It never writes `none`.

  Each level becomes an alert. Part 7's code scanning rule, set to "All" for both alerts and security alerts, therefore blocks everything these tools report, with no remapping here.
- KTD12. **shellcheck's SARIF comes from a small tested Go command, `tools/shellchecksarif`.** shellcheck has no SARIF output, and `shellcheck-sarif`'s release binaries carry no checksum. The command reads shellcheck's `json1` output on stdin and writes SARIF 2.1.0. It uses only the standard library, like `tools/diffcover`. A committed `jq` program was rejected because the repository keeps check logic in tested Go (the release plan's KTD2). A conversion bug there would silently drop findings and pass no test.

## Implementation Units

### U1. `tools/shellchecksarif`: shellcheck's json1 to SARIF

**Goal:** a standard-library Go command that turns shellcheck's `--format=json1` output into a SARIF 2.1.0 log that code scanning accepts.

**Requirements:** R5. KTD8, KTD12.

**Dependencies:** none.

**Files:**
- `tools/shellchecksarif/main.go` (new)
- `tools/shellchecksarif/main_test.go` (new)

**Approach:**
- It reads json1 from stdin and writes SARIF to stdout.
- The run's tool is `shellcheck`. Each distinct code becomes a rule `SC<code>` with a short description and a help URI `https://www.shellcheck.net/wiki/SC<code>`.
- Each comment becomes a result with its message and its file, line, end line, column and end column as one physical location. The file path stays repo-relative, as shellcheck printed it.
- Levels follow KTD8.
- Malformed input, or input that is not a json1 object, exits non-zero and writes nothing to stdout. An empty `comments` array yields a valid SARIF log with one run and no results.

**Patterns to follow:** `tools/diffcover/main.go` and its tests: a package comment with usage, a `run` function testable apart from `main`, standard library only.

**Test scenarios:**
- Two comments in two files, codes 2086 (warning) and 1090 (error), produce two results and two rules. Each has the right `ruleId`, level, path and region.
- A comment at level `style` and one at `info` both produce level `note`, never `none`.
- Three comments with the same code produce one rule and three results.
- `{"comments": []}` produces a SARIF log with version `2.1.0`, one run named `shellcheck`, and no results.
- Input that is not JSON exits non-zero with an error on stderr and nothing on stdout.
- A JSON array instead of the json1 object exits non-zero.
- Golden check: the SARIF for a fixed input matches a committed expected file, so the schema fields code scanning requires (`rules[].id`, `shortDescription`, `fullDescription`, `help`, `result.message.text`, `locations`) cannot silently disappear.

**Verification:** `go test -race ./tools/shellchecksarif` passes, and both coverage floors hold with the new package.
