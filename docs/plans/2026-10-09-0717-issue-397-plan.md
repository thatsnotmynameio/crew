## Planning Contract

### Key Technical Decisions

- KTD2. **The jobs live in `.github/workflows/security.yml`, with the shape #391 (KTD1, KTD3, KTD4 of its plan) gives that file.** The file runs on `pull_request` and on `push` to `main`, with no `paths` filter and no `workflow_dispatch`. It sets `permissions: {}`, and each job grants itself only what it needs. Every checkout uses the default merge commit and `persist-credentials: false`. If #391 is on `main` when this part starts, add the two jobs to its file. Otherwise create the file with that header, triggers and permissions, and whichever of the two pull requests merges second rebases onto the other. Concurrency is set per job. Each group carries the job's id written out, for example `${{ github.workflow }}-grype-${{ github.event_name == 'push' && github.sha || github.ref }}`, with `cancel-in-progress` only for pull requests. `github.job` cannot stand in for it: GitHub sets it only inside a job's steps, so in `concurrency` it is null. A group without the job's id would make the file's jobs cancel each other. #391's plan copies `ci.yml`'s group unchanged, and its CodeQL matrix also needs `matrix.language` in its group. Whichever plan lands second aligns the other's jobs on this form.
- KTD3. **Grype runs as a pinned release binary, not through `anchore/scan-action`.** The job downloads `grype_<version>_linux_amd64.tar.gz` into `$RUNNER_TEMP` with `curl -fsSL`, checks it against a sha256 written in the workflow with `sha256sum --check --strict`, and extracts it there. This is the codacy job's pattern in `ci.yml`. `scan-action` fails the same way on findings and on errors, and its SARIF output is set before it checks grype's exit code, so the job could not tell the two apart (KTD4). Dependabot does not bump a version in a `run:` step, so a comment beside it says the bump is manual, as for `REPORTER_VERSION`. Pins as of 2026-10-09, re-checked at implementation:

  | Item | Version | Commit SHA | Asset sha256 |
  | --- | --- | --- | --- |
  | grype | v0.120.1 | `6f8d854af29d3a3086b11a84afa51554a2a245fe` | `grype_0.120.1_linux_amd64.tar.gz`: `0a9ee97ef5ae2ee953b0a80098105052e846cdbe319a57d808b519c33cd1343d` |
  | `github/codeql-action` (`upload-sarif`) | v4.38.3 | `24c54180a607b1449ed407dd24f251e4e9147c8d` | |
  | `actions/dependency-review-action` | v5.0.0 | `a1d282b36b6f3519aa1f3fc636f609c47dddb294` | |

- KTD7. **Dependency review gates pull requests with the allowlist in the workflow, and publishes its license findings as SARIF.** The action runs only on pull requests, under a step-level `if: github.event_name == 'pull_request'`, because it throws on `push`. The job itself runs on both events, so that code scanning has a base analysis for its category. It has `contents: read` and `security-events: write`. Its inputs:
  - `allow-licenses`: `MIT`, `MIT-0`, `BSD-2-Clause`, `BSD-3-Clause`, `Apache-2.0`, `ISC`, `0BSD` and `LicenseRef-scancode-google-patent-license-golang`. Today's dependency graph holds only MIT and BSD-3-Clause, `Apache-2.0 AND MIT` for `go.yaml.in/yaml/v3`, and `BSD-3-Clause AND LicenseRef-scancode-google-patent-license-golang` for the `golang.org/x/*` modules. The other entries are permissive notice-only licenses that ask nothing more of crew's MIT license. No copyleft license is on the list (MPL-2.0, LGPL, GPL), so adding one is a decision the boss makes through the allowlist.
  - `fail-on-severity: low` and `fail-on-scopes: runtime, development, unknown`, so a new vulnerable dependency fails whatever its scope.
  - `comment-summary-in-pr: never`, which would need `pull-requests: write`.
  - `warn-only: true`, so the action reports violations without failing its step, and the job fails on them itself after the upload.
  - `deny-licenses` is deprecated and is not used.

  The allowlist sits in the workflow with a comment, and the workflow comes from the pull request's merge commit, so R8 holds. The action writes no SARIF, so the job builds one (R5):
  1. A step reads the action's `invalid-license-changes` and `denied-changes` outputs and writes one result per package, at line 1 of the manifest the change names, with level `error`, the package, its version and its license in the message, and no `security-severity`.
  2. It uploads that file with category `dependency-review`. On `push` it uploads the same file with no results, which gives pull requests their base analysis.
  3. It fails the job when the file has a result or the action's `vulnerable-changes` output is not empty.

  Vulnerable new dependencies are not written into this SARIF. Grype already publishes the same advisory on the same manifest (KTD4), and a second copy would open two alerts for one finding. The job still fails on them.
- KTD8. **The names are contracts.** The jobs are `grype` and `dependency-review`, and their SARIF categories are `grype` and `dependency-review`. Part 7 requires the jobs by name, and part 6's daily scan uploads under category `grype` with the same scan settings. A renamed category leaves its old alerts open on `main`, and a renamed job leaves a required check pending forever. A comment in the workflow says so.
- KTD10. **Codacy's Trivy stays as it is until part 8.** Its patterns stay in `.codacy/codacy.config.json`, and Codacy keeps running beside the new checks, as #391's plan also assumes. Removing them here would change Codacy's server analysis only after this pull request merges, and part 8 removes Codacy whole.
- KTD11. **The suppression forms:**
  - Grype: a rule in `.grype.yaml` by vulnerability id and package, with a `reason` (KTD6).
  - Dependency review: a package exempted through `allow-dependencies-licenses` (a purl), or an advisory through `allow-ghsas`, each with a comment giving the reason.

  A match on a malware advisory is never suppressed, neither in `.grype.yaml` nor through `allow-ghsas`. The package is removed instead. `.grype.yaml` holds only ignore rules. A `fail-on-severity` there would make grype exit non-zero on findings, which the job reads as an error (KTD4). That fails loudly and is not a silent pass.

### High-Level Technical Design

| Job | Runs on | Permissions | Fails on | Publishes |
| --- | --- | --- | --- | --- |
| `dependency-review` | PR (review), push (empty base analysis) | `contents: read`, `security-events: write` | added dependency with a license off the allowlist, or with a known vulnerability | SARIF of license findings, category `dependency-review` |

### Assumptions

- The action sets its `invalid-license-changes`, `denied-changes` and `vulnerable-changes` outputs under `warn-only: true`, and still fails its step on an error of its own, such as a failed API call. U3 checks both on its first runs.
- A dependency whose license GitHub cannot detect passes dependency review with a log line. The action offers no way to fail on it. Today that covers the SHA-pinned GitHub Actions in the dependency graph.
- GitHub's dependency graph sees only `pnpm` itself from `pnpm-lock.yaml`, not the Codacy CLIs' tree. Dependency review cannot check those packages' licenses or vulnerabilities, while Grype scans them. This ends when #385 removes the lock file.
- Code scanning accepts uploads from fork and Dependabot pull requests, whose tokens are read-only, as GitHub's documentation and its 2023 change state. Nobody has tested it here. #391 carries the same assumption.
- `LicenseRef-scancode-google-patent-license-golang` passes the action's SPDX check of `allow-licenses`. crush's workflow uses the same entry.

## Implementation Units

### U3. The `dependency-review` job

**Goal:** a pull request that adds a dependency with a license off the allowlist or with a known vulnerability fails the `dependency-review` check, and its license findings appear in code scanning.

**Requirements:** R4 (new dependencies' vulnerabilities and licenses row), R5, R7, R8, R17. KTD2, KTD7, KTD8.

**Dependencies:** U2 when U2 creates the workflow.

**Files:**
- `.github/workflows/security.yml`

**Approach:**
1. Add the job `dependency-review` with `name: dependency-review`, the per-job concurrency of KTD2, the permissions of the table above and a short timeout.
2. Check out the merge commit with `persist-credentials: false`. On pull requests, run `actions/dependency-review-action`, pinned by SHA, with KTD7's inputs.
3. Build the SARIF from the action's outputs, upload it with category `dependency-review`, then fail on its results or on vulnerable changes (KTD7). On `push`, upload the SARIF with no results.
4. Comment the allowlist: where each entry comes from, and that a new license is a decision made in this list.

**Patterns to follow:** U2's upload step and its SHA pin.

**Test scenarios:**
- The pull request's own run: `dependency-review` is green, it reports either no change or only allowed licenses, and it uploads a `dependency-review` analysis with no result. U1's `golang.org/x/sys` bump is a change it checks.
- On a throwaway pull request, a Go dependency under MPL-2.0 (for example `github.com/hashicorp/golang-lru/v2`) added to `go.mod` fails the job, and code scanning shows a `dependency-review` alert on `go.mod` naming the package and MPL-2.0.
- On a throwaway pull request, a Go dependency pinned to a version with a known advisory fails the job on the vulnerability, and the advisory appears as a `grype` alert, not as a `dependency-review` one.
- A push to `main` runs `dependency-review` green and uploads its empty base analysis. A later pull request's `dependency-review` analysis does not report a missing base.

**Verification:** both throwaway pull requests failed for the stated reason and were closed unmerged. The job is green on the implementing pull request.
