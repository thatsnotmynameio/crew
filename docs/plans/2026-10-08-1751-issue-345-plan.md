## Product Contract

### Summary

The domain's usage gains a per-model token list, `ByModel`, beside its sum and model names, and every copy of a `Usage` (the core's event, the run, its snapshot, the fake harness) copies it. No adapter fills it yet.

### Context

Today crew's usage carries only a session's summed tokens, so the per-model detail has nowhere to go. This part builds the carrier for R16; part 2 completes R16 by making the Claude Code adapter fill it. "Part 5" in the plan's text below is #315's part 5, which records the per-model tokens.

### Key Decisions

- **The core decides what to record, the engine writes it.** The core already knows the issue, its labels, the run's rule, action, bot, verdict and route, so it builds the records and emits commands; the engine executes them through the port, the way it executes journal records today. Crew's own time reaches the core with the fact the engine hands it, so the core keeps no clock. Harness-specific detail stays in the harness's adapter. Governs R7, R8, R9, R10, R11, R12, R16. (session-settled: user-approved — chosen over the engine assembling records on its own: the core keeps the decision pure and table-testable)

### Scope Boundaries

- Filling `ByModel` from Claude Code's final result is part 2's; after this part no adapter fills it, and nothing reads it.
- Recording the tokens anywhere new is #315's part 5.
- The run journal (`.crew/logs/runs.jsonl`) stays as it is: it keeps writing and reading the sum and the model names only.
- The live view, the status comment, `Spend`, the Codex adapter, the config and the README are unchanged.

## Planning Contract

### Key Technical Decisions

- KTD1. **`crew.Usage` gains a per-model list, kept beside `Tokens` and `Models`.** A new `ModelTokens` (a model's name and its `Tokens`) and a `Usage.ByModel` list of them, sorted by model name, empty when the harness does not tell tokens by model. `Tokens` stays the session's sum and `Models` its model names: the Codex adapter reports a sum with no model, and the journal, the live view, the status comment and `Spend` read only those two fields, so none of them changes. A sorted list rather than a map keeps the core's events deterministic for table tests and for part 5's records, and follows how `Models` is already a sorted list.
- KTD3. **Every copy of a `Usage` copies `ByModel` too.** `Usage` already travels from the engine's fact into the core's `ActionSessionEnded` event, the `ActionRun`, its snapshot and the fake harness, each through a clone of `Models` so no two holders share memory. The same clones copy `ByModel`, so a holder that changes its list never changes another's.
- KTD4. **The journal stays as it is (Scope Boundaries).** `internal/adapter/jsonl` keeps writing and reading the sum and the model names only. A run restored from the journal after a restart has no per-model tokens. That loses nothing part 5 needs: it records a session's tokens when the session ends, in the process that ran it.

### Assumptions

- The per-model detail is what the final result's `modelUsage` gives (input, output, cache read, cache write per model name), with no further split by subagent or skill; #315 defers those to its model-call slices.
- No test or caller compares two `Usage` values with `==`: `Usage` already holds a slice, so it is not comparable today, and adding a second slice changes nothing there.

### Deferred to Implementation

- Whether the domain test for KTD3 sits in `internal/crew/run_test.go`, beside the existing "shares … with the snapshot" checks, or in a test file of its own.

### Sequencing

U1 alone: the type and the field first, then the clones.

## Implementation Units

### U1. Per-model tokens in the domain's usage

- **Goal:** `crew.Usage` can hold a session's tokens for each model, and every holder of a `Usage` owns its copy.
- **Requirements:** R16; KTD1, KTD3.
- **Dependencies:** none.
- **Files:**
  - Modify: `internal/crew/usage.go` (the `ModelTokens` type and the `ByModel` field, documented as sorted by model and empty when not reported).
  - Modify: `internal/crew/action.go` (`cloneUsage` copies `ByModel`).
  - Modify: `internal/fake/harness.go` (`Session.SetUsage` and `UsageSession.Usage` copy `ByModel`, as they copy `Models`).
  - Test: `internal/crew/run_test.go`, `internal/fake/fake_test.go`, `internal/core/usage_test.go`.
- **Approach:**
  1. Add the type and the field in `internal/crew/usage.go`, with `Spend` untouched: it keeps reading `Tokens`.
  2. Make `cloneUsage` and the fake harness's two copies clone `ByModel`.
- **Patterns to follow:** `Usage.Models` and its clones in `internal/crew/action.go` and `internal/fake/harness.go`; the restored-run sharing checks in `internal/crew/run_test.go`.
- **Test scenarios:**
  - A run whose session ended with a usage of two models, Opus then Sonnet, returns that list from its action's `Usage()`, and changing the returned list's first entry leaves the next `Usage()` call unchanged.
  - A snapshot of that run, restored, holds the same two entries and shares no memory with the snapshot.
  - The fake usage harness's session, given a usage with two per-model entries, reports them, and changing the given list after `SetUsage` leaves what it reports unchanged.
  - Integration: the core, handed `SessionEnded` with a usage of two models, records an `ActionSessionEnded` whose usage carries both entries in model order, beside the same `Tokens` and `Models` it records today.
- **Verification:** the domain, fake and core tests above pass, and the existing usage, journal, status and view tests pass unchanged.
