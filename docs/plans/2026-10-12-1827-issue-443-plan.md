## Product Contract

### Summary

Defines `port.StackFinder` and implements it in the GitHub adapter with three aliased GraphQL rounds. Nothing calls it until part 7 wires it into the listing.

### Context

crew can stack an issue only on a pull request GitHub's relationship data links to its blocker, so it needs a read that finds that pull request without closing references or a pull request's body. Its unit builds some of R2, R5 and R6, which part 6 completes.

### Key Decisions

- **crew checks the blocker's open pull request itself.** Governs R2, R3. (session-settled: user-directed — chosen over taking an issue when its blocker carries a given label, and over taking every blocked issue and letting the prompt give back the ones not ready: crew can read the pull request directly.)
- **crew finds the blocker's pull request through GitHub's API links between an issue and its pull requests, not through closing references or a pull request's body.** Governs R3. (session-settled: user-directed — chosen over closing references, which a pull request on a base other than the default branch does not get, and over reading the pull request's body: GitHub already relates pull requests to issues.)
- **Sub-issues of one parent may all stack on the same blocker's pull request; any other issue waits for the merge.** Governs R5, R6. (session-settled: user-directed — chosen over stacking each sibling on top of the one before it, which brings back the sibling walk-up, and over letting only the first issue stack in every case: `gh stack` restacks siblings easily, and only issues of one parent are meant to land together.)
- **Only pull requests from the repository itself count, whoever opened them.** Governs R3. A branch in the repository already needs write access. (session-settled: user-approved — chosen over also requiring the pull request's author to be a code owner or one of crew's bots: the repository's branches are enough.)
- **Only an issue with exactly one blocker stacks; an issue with more waits for every merge, as today.** Governs R2. Split parts keep only direct links, so the common chain has one blocker per part. (session-settled: user-directed — chosen over reading chains of pull requests to find the top of several blockers, and over stacking once a single blocker is left open, which would start the issue on a branch without the merged blocker's code.)
- **An issue stacks only on a pull request whose run has ended, never on a branch still being worked.** Governs R2. A session goes on pushing CI and review fixes after it opens its pull request. (session-settled: user-approved — chosen over stacking as soon as the blocker's pull request opens.)

### Requirements

**Taking a blocked issue**

- R3. The blocker's pull request is one GitHub's relationship data links to the blocker, opened from a branch of the same repository, never from a fork; crew never reads a pull request's body to find it.

### Key Flows

- F1. A split's chain of parts
  - **Trigger:** refinement splits #P into sub-issues #A, #B and #C, where #B is blocked by #A and #C by #B, and moves them to `crew:development:ready`.
  - **Steps:** `development` takes #A from `main`, as today. Its run ends in `crew:development:waiting review` with its pull request open. At the next listing, `development` takes #B with a workspace made from #A's branch, and #B's session opens its pull request on #A's branch and links it into a stack. #C follows the same way once #B's run ends with its pull request open.
  - **Outcome:** the stack is `main ← #A ← #B ← #C`, all in review at once. When the boss merges #A's pull request, GitHub retargets #B's to `main` and rebases #C's.
  - **Covered by:** R2, R3, R5, R7, R8, R10, R12.

### Scope Boundaries

- No walk up a chain of pull requests to find its top.

## Planning Contract

### Key Technical Decisions

- KTD1. **The tracker reads stack data during the listing, through an optional port, for the candidates only.** `ListIssues` carries the ready labels of the rules with stacking on. After `Tracker.List`, the engine calls the new optional `port.StackFinder` with the listed issues that are blocked and sit only in one of those labels, and puts the issues it returns into the same `IssuesListed`. The core then decides each take in its own pure code. This follows the shipped pattern of tracker data on the issue (`docs/solutions/integration-issues/blocked-issues-dispatched-by-github-tracker.md`). It was chosen over enriching every blocked issue inside `Tracker.List`, which costs queries in repositories that never stack and changes every tracker, and over a new command and input round trip before the take, which adds a pending-take state to the scheduler. If the read fails, the candidates stay unenriched and wait (R4), and the core publishes a `StacksNotFound` warning, as it does `StatisticNotRecorded`. One unreadable query must not stop crew taking its other issues.
- KTD2. **GitHub is read in at most three aliased GraphQL rounds, each through `issue(number:)` or `repository.pullRequests`, never through a timeline nested in `repository.issues`.** Nested timelines have been served hours stale (`docs/solutions/integration-issues/graphql-issues-connection-serves-stale-timelines.md`).
  1. Round 1, per candidate: `issueDependenciesSummary { blockedBy totalBlockedBy }`, the `blockedBy` nodes with number, state, repository and labels, and `parent` with its `subIssues(first: 100)`, each with its repository. The adapter keeps a candidate only when `totalBlockedBy == 1`, `blockedBy == 1`, and that blocker is in the same repository. Counting closed blockers keeps AE4: an issue that two issues block never stacks, even after one of them closes.
  2. Round 2, per distinct blocker: `timelineItems(itemTypes: [CROSS_REFERENCED_EVENT, CONNECTED_EVENT, DISCONNECTED_EVENT])` pull-request sources and subjects with number, URL, state, `isDraft`, `headRefName`, `baseRefName`, `isCrossRepository` and head repository. It keeps only open pull requests whose head is in the same repository (R3). Each is flagged as connected when its latest connect or disconnect event is a connect: that is a person linking it in the issue's Development sidebar. Connection arguments are not filters, so each node's state and repository are checked (`docs/solutions/integration-issues/closing-pull-requests-include-merged-and-foreign-ones.md`).
  3. Round 3, per distinct kept head branch: `repository.pullRequests(baseRefName:, states: OPEN)`, giving the head branches of the same-repository pull requests based on it.

  Every new selection is tried live on a user-owned and an org-owned repository before it merges, because a valid-looking selection once failed the whole listing on user repositories (`docs/solutions/integration-issues/issue-field-total-count-fails-listing-on-user-repositories.md`).
- KTD3. **The blocker's own pull request is a linked one that comes from a branch of a crew run of the blocker, or that a person connected to the blocker in GitHub's Development sidebar.** Discovery and ownership use only GitHub's relationship events between the blocker and its pull requests (KTD2 round 2), never closing references or a body, as the Product Contract's Key Decision on R3 requires. A pull request that merely mentions the blocker is not its own. Branches come from the workspaces of the blocker's runs in `History` and its held run, which covers a stacked blocker that has no closing reference. The connect arm covers a blocker crew never ran (R2's "if any"). Consequences: a person's pull request for a blocker crew never ran counts only once it is connected in the sidebar. A crew pull request whose body never mentions the blocker has no link, and its dependents wait.

### Assumptions

- GitHub records a cross-reference on an issue for a pull request whose body names it, whatever the pull request's base. The brainstorm checked this only for a pull request based on `main` (#426 on #423). No pull request in this repository has had another base yet. U5 checks it live before shipping. If GitHub does not record it, stop (Goal Capsule).
- The candidate's parent has at most 100 sub-issues, the blocker's timeline holds its links among its last 100 cross-reference and connect events, and a pull request branch has at most 20 open pull requests based on it.

### Implementation Constraints

- New optional capabilities are separate interfaces found by type assertion (AGENTS.md "New adapter").

### Sequencing

U5 is the only unit. Part 7 builds on it.

### Alternatives Considered

- **A GitHub function that finds what blocks a pull request, going from the pull request to its linked issues and their `blocked by` dependencies.** A teammate session suggested this during planning. It is not used: crew starts from the blocked issue, not from a pull request, so the dependency is already in hand (round 1). The pull-request-to-issue direction also fails exactly where stacking needs it. A pull request based on another pull request's branch has no closing references, the only issue link GitHub lists on the pull request's side. All the relation lookups still live in the GitHub adapter, as functions of `StackFinder`, in the issue-to-pull-request direction.

## Implementation Units

### U5. GitHub: the `StackFinder`

- **Goal:** the GitHub tracker reads the blocker, its pull requests, the pull requests based on them and the candidate's siblings.
- **Requirements:** R2, R3, R5, R6; KTD2, KTD3.
- **Dependencies:** U1.
- **Files:** `internal/port/port.go`, `internal/adapter/github/stack.go` (new), `internal/adapter/github/stack_test.go` (new), `internal/adapter/github/tracker.go` (the interface guard).
- **Approach:** define `port.StackFinder` with one method that takes the candidate issues and returns them with the stack reading set. Implement it with KTD2's three rounds, one `gh api graphql` call per round with an aliased field per item, and skip each later round when there is nothing to read. Map the blocker's labels to crew states as `item` does. An issue that loses a filter keeps no stack reading. An unresolvable number leaves that issue out, and any other error fails the read.
- **Execution note:** before shipping, run the three queries live against this repository (org-owned) and a user-owned repository. Check that a pull request based on a branch other than `main`, whose body names an issue, shows as a cross-reference on that issue.
- **Patterns to follow:** `pullRequestsQuery` and its tests (`internal/adapter/github/pullrequest.go`, `pullrequest_test.go`), and the scripted `newFakeGh`.
- **Test scenarios:**
  - A candidate with one blocker in total, open and in this repository, gets that blocker with its states.
  - A candidate with `totalBlockedBy` 2 and one open blocker gets no stack reading.
  - A candidate whose only blocker is in another repository gets none.
  - The blocker's timeline lists an open same-repository pull request, a merged one, a fork's and a mention by an issue: only the first is kept, with its head, base and draft flag.
  - A pull request whose latest event on the blocker is a connect is flagged as connected. One connected then disconnected, or only cross-referenced, is not.
  - Round 3 lists the head branches of the open same-repository pull requests based on each kept head.
  - The parent's sub-issues are read with their repositories, and a candidate without a parent has none.
  - No candidate means no `gh` call, and no kept pull request means no round 3.
  - A GraphQL error fails the read with `gh`'s message.
- **Verification:** the adapter tests pass. No test checks the GraphQL against GitHub, so the live check above, passed on both repositories, is the queries' only check.
