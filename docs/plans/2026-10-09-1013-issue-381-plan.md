# SECURITY.md and GitHub's free security settings - Plan

## Goal Capsule

- **Objective:** someone who finds a vulnerability in crew knows how to report it privately and what crew counts as one, and after the pull request merges the boss can turn on every free GitHub security setting from one list.
- **Means:** a crew-specific `SECURITY.md` at the repository root that replaces the organization's default policy for this repository (KTD1), and a checklist of settings in the pull request's description (KTD4).
- **Parent:** #272, part 4 of 8. Read it only for a question this part does not answer.
- **Open blockers:** none. The repository has been public since 2026-10-08, and private vulnerability reporting was already on when this plan was written.
- **Authority:** the Product Contract wins on behaviour, the KTDs on mechanism. A unit overrides neither.
- **Stop conditions:** stop and report if the checklist would need a setting that costs money on a public repository (R17), or if GitHub no longer serves the repository's own `SECURITY.md` ahead of the organization's default.
- **Execution profile:** documentation only. No Go code, workflow or config changes.

## Planning Contract

### Key Technical Decisions

- KTD1. **crew's own `SECURITY.md` replaces the organization's default, so it carries the default's points and adds crew's scope.** A repository's file hides the organization's default entirely, so dropping a point drops it for crew. It keeps four points from the default: only the latest release gets fixes, report privately through GitHub, don't open a public issue, and what a report should include. It adds what makes crew different: which of crew's behaviours count as vulnerabilities and which don't. Like the default, it promises no response time. Nobody has committed to one, and a promise nobody keeps is worse than none. Governs R14.
- KTD2. **The report link goes straight to the form.** `SECURITY.md` links `https://github.com/thatsnotmynameio/crew/security/advisories/new` and also names the UI path (Security, then Report a vulnerability). The link saves the reporter a search, and the path still works if the reporter reads a fork's copy. Governs R14.
- KTD3. **CodeQL ends on advanced setup, with default setup only as a stopgap.** #391 adds CodeQL as an advanced-setup workflow, and GitHub rejects its uploads while default setup is on. If #391's workflow is on `main` when this pull request merges, the checklist tells the boss to leave default setup off. If it isn't, the boss turns default setup on now, so CodeQL runs in the meantime, and switches it off before #391 merges, as #391's Assumptions already ask. Copilot Autofix works on alerts from either setup, so it still needs no separate step. Governs R15.
- KTD4. **The settings checklist lives only in the pull request's description.** R15 puts it there. The README's audience rules keep admin settings out of it, and a repository file would go stale the moment the boss flips a switch. Governs R15.
- KTD5. **The checklist gives each setting's state as checked on 2026-10-09, and an action for the boss.** Private vulnerability reporting was confirmed on through the API. Every other setting returned 403 to this session's token, so the checklist marks them as "check, turn on if off". The boss acts on each line, and none of them asks for a change the boss can't verify on the Settings page. Governs R15.

### Assumptions

- The scope section's lists (U1) are this plan's reading of what the README and `AGENTS.md` describe. The brainstorm left them open. Their wording decides any line the implementer doubts.
- No sibling part of #272 adds a `SECURITY.md` of its own. Checked against #382–#385 and #391–#395 on 2026-10-09.
- GitHub still serves a repository's root `SECURITY.md` ahead of the organization's default.
- Dependabot security updates honour the `ignore` entry for `modernc.org/libc` in `.github/dependabot.yml`, so a libc advisory gets no pull request of its own. That is the intended behaviour: libc moves only with `modernc.org/sqlite`.

## Implementation Units

### U1. `SECURITY.md` at the repository root

- **Goal:** a reporter learns how to report privately, which versions get fixes, what to include, and whether their finding is in crew's scope.
- **Requirements:** R14, R17. KTD1, KTD2.
- **Dependencies:** none.
- **Files:** `SECURITY.md` (new).
- **Approach:**
  1. Open with one line saying this is crew's policy, so the reader knows it replaced the organization's default.
  2. **Supported versions:** only the latest release gets fixes. Point to the README's "Upgrading crew" section for `crew upgrade`, and note that a crew built with `go install` or from a checkout is updated the way it was installed.
  3. **Reporting:** the private form (KTD2), a plea not to open a public issue, pull request or discussion, and what to include: crew's version as `crew --version` prints it, OS and architecture, the steps to reproduce with anything private removed, and what an attacker could do.
  4. **In scope**, each grounded in what the README or `AGENTS.md` describes:
     - crew posting secrets or session text to a public issue, pull request or comment.
     - A bot's private key or token leaving the bots' files (under `$XDG_CONFIG_HOME/crew/bots`, else `~/.config/crew/bots`) or the private gh config directories crew writes for them.
     - A comment from someone off the code owners and `answering_apps` lists counting as an answer.
     - `crew upgrade` installing an archive that fails `checksums.txt`, or writing outside its own path.
     - A release archive that doesn't match the release's `checksums.txt`, or a release that crew's Release workflow didn't build. Build provenance is #382's, so this line names no attestation.
  5. **Out of scope:**
     - What a repository's own `.crew/config.yaml` tells crew to run. Shell actions, functions and agent sessions run with the user's rights by design, and the config is code the user trusts.
     - Vulnerabilities in Claude Code, Codex, `gh` or `git` themselves, which their own projects take.
  6. Write it in the README's register: short plain sentences, no marketing.
- **Patterns to follow:** `thatsnotmynameio/.github`'s `SECURITY.md` for its sections and tone. The README's "Upgrading crew" and answering sections for the behaviour the scope names.
- **Test expectation:** none. A documentation file with no behaviour, and no Markdown linter runs in CI or Codacy.
- **Verification:**
  - Every link in the file resolves.
  - Every in-scope line names a behaviour the README or `AGENTS.md` describes.
  - The supported-versions and reporting points match the organization's default.

### U3. The pull request's settings checklist

- **Goal:** after merging, the boss can turn on each free setting from one list, with nothing paid on it.
- **Requirements:** R15, R17. KTD3, KTD4, KTD5.
- **Dependencies:** U1, U2.
- **Files:** none. The checklist goes in the pull request's description.
- **Approach:** one checkbox line per setting, each naming where it is on the Settings page (Settings, then Advanced Security, or Code security on older layouts) and what to do:
  1. Private vulnerability reporting: on as of 2026-10-09. Keep it on.
  2. Secret scanning: check it is on.
  3. Push protection: turn it on.
  4. Code scanning: CodeQL as KTD3 sets out. Write the line for #391's state when the pull request opens. Either way, check that Copilot Autofix is not turned off.
  5. Dependency graph: check it is on.
  6. Dependabot alerts: turn them on.
  7. Dependabot security updates: turn them on.
  8. Dependabot auto-triage: turn on GitHub's preset rules, such as dismissing low-impact alerts for development-scoped dependencies.

  Close with one line saying none of these needs a paid plan on a public repository (R17), and one naming the paid features left off, as the Scope Boundaries list them.
- **Test expectation:** none. Text in a pull request's description.
- **Verification:**
  - The description has one line for each item of R15.
  - No line names a paid feature as something to turn on.
