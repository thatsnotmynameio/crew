## Product Contract

### Summary

Adds the `stacking` key to a rule, to the schema and to the example config, documents stacking in the README, and turns it on for this repository's `development` rule, whose prompt opens its pull request on the run's base and links it into a stack with `gh stack`.

### Context

Every part before this one is dormant: no rule can set `stacking`, so crew takes blocked issues exactly as before. This part ships the switch with the documentation of what it does, so the key never exists on `main` without its behaviour or its README text.

### Key Decisions

- **Stacking is a rule's opt-in, off by default.** Governs R1. (session-settled: user-approved — chosen over stacking in every rule: it changes when an issue starts, so a repository turns it on per rule.)

### Requirements

**Taking a blocked issue**

- R1. A rule takes blocked issues only when its config turns stacking on; a rule without it waits for every blocker to close, exactly as today.

**This repository's rules**

- R11. `development` turns stacking on; `fix` keeps waiting for merges.
- R12. The machine that runs crew's sessions for this repository has the `gh stack` extension installed, and stacked pull requests are enabled on the repository.

### Key Flows

- F1. A split's chain of parts
  - **Trigger:** refinement splits #P into sub-issues #A, #B and #C, where #B is blocked by #A and #C by #B, and moves them to `crew:development:ready`.
  - **Steps:** `development` takes #A from `main`, as today. Its run ends in `crew:development:waiting review` with its pull request open. At the next listing, `development` takes #B with a workspace made from #A's branch, and #B's session opens its pull request on #A's branch and links it into a stack. #C follows the same way once #B's run ends with its pull request open.
  - **Outcome:** the stack is `main ← #A ← #B ← #C`, all in review at once. When the boss merges #A's pull request, GitHub retargets #B's to `main` and rebases #C's.
  - **Covered by:** R2, R3, R5, R7, R8, R10, R12.
- F2. Siblings on one blocker
  - **Trigger:** #B and #C, sub-issues of #P, are both blocked only by #A, whose run ended with its pull request open.
  - **Steps:** `development` takes #B and stacks it on #A. #C is taken too, while #B runs or after, and its workspace is made from #A's branch. Each session opens its pull request on #A's branch and links it into a stack on top of #A's.
  - **Outcome:** two stacks share #A at the bottom, `main ← #A ← #B` and `main ← #A ← #C`. When #A merges, GitHub retargets both to `main`; crew does nothing.
  - **Covered by:** R5, R6, R12.

### Acceptance Examples

- AE1. **Covers R1.** Given a rule without stacking on and an issue blocked only by #A, whose run ended with its pull request open, the rule does not take the issue.

### Success Criteria

- In this repository, every part of a split chain has its pull request open in one GitHub stack without any part waiting for a merge: each part starts at the first listing after the run of the part below it ends with its pull request open.

### Scope Boundaries

- This is the last part; nothing is left to a later part.
- The prompt that opens the pull request on the run's base and links it into a stack is the repository's configuration; this plan sets no wording for it.
- No new lines, cards or chips in the live view or `--plain` output for a stacked issue.
- No restack by crew after a merge, and no rebase when the blocker's pull request gets new commits in review: `gh stack rebase` covers it.
- crew does not guarantee that a stacked issue closes when its code lands in the default branch; a person closes it when GitHub does not.
- crew's label mirror and the stop comments of a `close` keep reaching only the pull requests GitHub's closing references name, so a stacked pull request misses them until it targets the default branch.
- A blocker's pull request closed without merging leaves the issues stacked on it unmergeable; a person unstacks them.

### Dependencies / Assumptions

- GitHub's stacked pull requests: `gh stack link` adds pull requests to a stack bottom to top, GitHub retargets and rebases the remaining ones when one merges, and a pull request can sit at the bottom of more than one stack, so two siblings can each link on top of the same blocker.
- `gh stack` 0.2.1 is installed on the machine that runs this repository's sessions (2026-10-12). Stacked pull requests are enabled on this repository in its settings; no API for that switch was found.

## Planning Contract

### Key Technical Decisions

- KTD1. **The tracker reads stack data during the listing, through an optional port, for the candidates only.** `ListIssues` carries the ready labels of the rules with stacking on. After `Tracker.List`, the engine calls the new optional `port.StackFinder` with the listed issues that are blocked and sit only in one of those labels, and puts the issues it returns into the same `IssuesListed`. The core then decides each take in its own pure code. This follows the shipped pattern of tracker data on the issue (`docs/solutions/integration-issues/blocked-issues-dispatched-by-github-tracker.md`). It was chosen over enriching every blocked issue inside `Tracker.List`, which costs queries in repositories that never stack and changes every tracker, and over a new command and input round trip before the take, which adds a pending-take state to the scheduler. If the read fails, the candidates stay unenriched and wait (R4), and the core publishes a `StacksNotFound` warning, as it does `StatisticNotRecorded`. One unreadable query must not stop crew taking its other issues.
- KTD8. **Sessions read the stack as prompt data and as environment variables. Shell actions and route shell steps read it as environment variables.**
  - **Prompt data:** a session prompt's template data gains `.Base` and `.Stack`. `.Stack` has `Stacked`, `Blocker.Ref`, `Blocker.URL`, `PullRequest.Ref`, `PullRequest.URL` and `Branch`, all empty when the run is unstacked.
  - **Rendering:** `Prompt.Render` takes the run's stack and base next to the issue at every call site, so the render that checks a prompt when the session is asked for and the render that starts it produce the same text. `ParsePrompt` renders both a stacked and an unstacked sample, so a typo inside `{{if .Stack.Stacked}}` fails at config load.
  - **Environment:** `CREW_BASE_BRANCH`, `CREW_BLOCKER_REF`, `CREW_BLOCKER_URL`, `CREW_BLOCKER_PR_REF` and `CREW_BLOCKER_PR_URL`; the last four are empty when the run is unstacked. Codex gets them only through the process environment (`docs/solutions/security-issues/session-environment-values-in-codex-command-line.md`).
  - **Left out:** function parameters and comment templates get neither, since R8 names sessions and shell actions only.
- KTD9. **A rule opts in with `stacking: true`.** It is a field of `crew.Rule`, parsed next to `takes`, and false by default (R1). It has no effect on a rule that takes pull requests, which are never blocked. Config refuses it on a rule without actions, which would move blocked issues on without working them.

### Assumptions

## Implementation Units

### U2. Config: the `stacking` key

- **Goal:** a rule turns stacking on in config.
- **Requirements:** R1; KTD9.
- **Dependencies:** U1.
- **Files:** `internal/config/rules.go`, `internal/config/rules_test.go`, `internal/config/testdata/translation/.crew/config.yaml`, the test that loads the `translation` fixture, `schema/config.schema.json` (a boolean `stacking` property on a rule), `.crew/config.example.yaml` (a commented `stacking` entry). `TestSchemaAndConfigTakeTheSameKeys` and `TestTheExampleSetsEveryKey` fail until both name the key.
- **Approach:** add a `located[bool]` `Stacking` field to `ruleDoc`, set `crew.Rule.Stacking`, extend the `ruleShape` message, and add a `keyError` for a rule without actions.
- **Patterns to follow:** `takes` in `rules.go`; the `checkQuestions` refusal rows in `internal/config/questions_test.go`.
- **Test scenarios:**
  - Covers AE1. A rule without the key has stacking off.
  - `stacking: true` turns it on, and `stacking: false` leaves it off.
  - `stacking: true` on a rule without actions is an error naming the key.
  - A non-boolean value is a shape error.
  - The `translation` fixture sets the key both ways, and its loaded rules carry both values.
- **Verification:** config tests pass, and a config with an unknown key under a rule still fails strictly.

### U9. Docs, this repository's config, and the operational switch

- **Goal:** the README tells users how stacking works, and `development` stacks in this repository.
- **Requirements:** R11, R12, Success Criteria.
- **Dependencies:** U2, U7, U8.
- **Files:** `README.md`, `.crew/config.yaml`, `CONCEPTS.md` (only if it lacks an entry for a stacked take).
- **Approach:**
  - **README:** document `stacking` in the rules section: when a stacked take happens, what one child per pull request means, and sibling sub-issues. Also document the workspace made from the blocker's branch, the prompt fields, the five environment variables, and the `StacksNotFound` warning. Add that a blocker whose pull request merged while it stays open holds its dependents until someone closes it. Make the `blocked` card line say that a stacking rule may still take the issue.
  - **This repository's config:** turn `stacking: true` on for `development` and not for `fix`. Change `development`'s prompt so its pull request targets the run's base and, when stacked, is linked into a stack with `gh stack`. Before it opens the pull request, the session checks that the base branch still exists on origin and the blocker's pull request is still open. When either is gone, it rebases its branch onto the default branch, leaving out the blocker's commits, targets the default branch and links no stack. The wording is the implementer's (Scope Boundaries).
  - **Config test:** run `tools/crew_config_test.sh` by hand after the config change.
- **Test expectation:** none. This unit is docs and this repository's config, which no Go test reads. The config script runs by hand.
- **Verification:** the README describes every new key, field and variable. crew loads this repository's config without an error, and the config script passes.

## Risks & Dependencies

| Risk | Mitigation |
|---|---|
| **A pull request belongs to at most one GitHub stack.** The schema's `PullRequest.stack` and `stackEntry` are singular, which contradicts the brainstorm's assumption that a pull request can sit at the bottom of two stacks (F2). | The crew side of F2 is unaffected: both siblings get worktrees from #A's branch, and their pull requests target it. Linking the second sibling into a stack is the prompt's work (R9). If `gh stack link` refuses it, that pull request stays unlinked. GitHub then retargets it to `main` when #A's merged branch is deleted, but does not rebase it. Conflict call-out for the sibling Key Decision, recorded here for the boss. |
| **The blocker usually merges before the stacked session opens its pull request.** In this repository, crew's pull requests merged 10 to 20 minutes after opening (#426, #435, #436, #438), which is shorter than a development session, and merged branches are deleted. | R10 leaves this to the prompt, and U9's prompt handles a base that is gone. The stacked take still pays off: the session starts on the blocker's code instead of waiting for the merge. |
