# AGENTS.md

Guidance for coding agents working in this repository. Claude Code reads it as `CLAUDE.md`, a symlink to this file.

crew is a Go program that polls a tracker (GitHub) and moves each issue through the rules a repository declares on its labels in `.crew/config.yaml`, running one coding-agent session (Claude Code or Codex) per action in its own git worktree. Its users run it in their own repositories, where it takes the issues their code owners and bots opened.

## Commands

Run every command from the repository root. Go 1.27 (`go.mod`).

```sh
go build ./cmd/crew   # the binary, at the root (ignored by git)
go test -race ./...   # every test; one package: go test -race ./internal/core; one test: add -run TestName
gofmt -l cmd internal tools acceptance # prints the unformatted files; must print nothing
go vet ./...
go run github.com/golangci/golangci-lint/v2/cmd/golangci-lint@v2.14.0 run   # lint + layering (depguard)
go run golang.org/x/vuln/cmd/govulncheck@v1.8.0 ./...
go test -race -covermode=atomic -coverpkg=./... -coverprofile=coverage.out ./...   # coverage profile
go run github.com/vladopajic/go-test-coverage/v2@v2.19.0 --config=.testcoverage.yml   # total >= 90%
git diff -U0 origin/main...HEAD | go run ./tools/diffcover -profile coverage.out   # changed lines >= 90%
go -C acceptance run ./cmd/acceptance   # builds crew with the release config, runs the acceptance suite against it; go test flags pass through
pnpm install          # once: the Codacy CLIs
pnpm exec codacy-analysis analyze --install-dependencies   # Codacy's Lizard, Opengrep, Trivy, Checkov
```

- **golangci-lint:** run it through `go run` at v2.14.0, as CI does. A local install older than v2.13.0 cannot lint a `go 1.27` module.
- **CI:** the `go` job in `.github/workflows/ci.yml` runs gofmt, vet, golangci-lint, `go test -race` with coverage, both coverage floors and govulncheck. Its `acceptance` job builds crew with GoReleaser (a Linux amd64 snapshot), runs vet, golangci-lint and govulncheck in `acceptance/`, then the suite with `CREW_BIN` set; on failure it uploads the tests' artifacts. Its `codacy` job uploads the coverage to Codacy, which analyses the code on its own servers.
- **Code scanning:** `.github/workflows/security.yml` runs the security analyses on every pull request and on each push to `main`, with no secret, and publishes them to GitHub code scanning. The pull request runs every check, and no new check has to run locally first. Its `codeql (go)` and `codeql (actions)` jobs run CodeQL's `security-extended` suite (`.github/codeql/codeql-config.yml`) over both Go modules, tests included, and over the workflows. They fail on a build or analysis error, but not on an alert: an alert only reports until a ruleset blocks on it. CodeQL has no inline suppression: dismiss a false positive in code scanning, with its reason. Its `zizmor` job audits the workflows, the composite actions and `.github/dependabot.yml` with zizmor's online audits and publishes under the category `zizmor`; it fails on an error, such as a malformed `.github/zizmor.yml`, but not on a finding. Suppress a zizmor finding at the finding, `# zizmor: ignore[<id>] <reason>`, or turn a rule off for the whole repository in `.github/zizmor.yml` with a comment giving the reason, which applies to the pull request that does it.
- **Security:** `.github/workflows/security.yml` runs `grype` and `dependency-review` on every pull request and each push to `main`. Both publish to GitHub code scanning, which reports only the alerts a pull request adds to `main`'s analysis. `grype` scans every manifest of the checkout for vulnerable and malicious packages and fails only on a tool error or an empty scan (no package found in one of `go.mod`, `acceptance/go.mod` and `pnpm-lock.yaml`), never on its findings. `dependency-review` fails when a pull request adds a dependency whose license is off the `allow-licenses` list in the workflow, or one with a known vulnerability, and publishes the license findings; on a push it runs no review and uploads an analysis with no result, which each pull request's analysis is compared against. A grype finding is suppressed by an ignore rule in `.grype.yaml`, by vulnerability id and package, with a `reason`; a dependency review finding by exempting the package through `allow-dependencies-licenses` (a purl) or the advisory through `allow-ghsas`, each with a comment giving the reason. A malware match is never suppressed in either: the package is removed instead. `.grype.yaml` holds only ignore rules: a `fail-on-severity` there makes grype exit non-zero on findings, which the job reads as an error.
- **Quality bar:** zero findings, everywhere. `.golangci.yml` turns on every linter except those it lists with a reason; Codacy's tools and limits are in `.codacy/codacy.config.json`.

## Architecture

Ports and adapters with a pure core.

- `cmd/crew`: flags, signals, the repository root, the global config file's path, crew's data folder (`config.DataDir`) and crew's version, read from the environment in one place (`folders`); builds the `git` workspace, the `shell` adapter, the `jsonl` run journal (at `engine.JournalPath`, with the crew process's id) and `app.Options.Bots` (through `internal/bots`) and calls `app.Run`. `crew bots create <name>` is chosen before the flags and runs the `internal/bots` flow instead; `crew sessions <session-id> tasks next|current` is too, and asks `captain.Dumb` for the session's task; so is `crew upgrade [vX.Y.Z]`, which runs the `internal/upgrade` flow with the process's version, build info, path, platform and `CREW_UPGRADE_API_URL`.
- `internal/app`: config, registry, engine, renderer, stop signals, exit codes (0 clean, 1 failure or forced, 2 config or environment). It builds the statistics store `statistics.store` names through the registry, in the data folder, none when it is `off`, hands it and crew's version to the engine, and closes it once the engine's `Run` has returned without an error; a failed engine, a panic included, and a forced exit leave it open.
- `internal/crew`: the domain (states, issues, rules with their labels, queues, actions and routes, actions as sessions with their parsed prompts, shell actions or function calls with their parameter templates, verdicts and where they lead, crew's markers, the open questions a session or a rule asked and the one rule for the answers that count (`marker.go`, `question.go`, `answer.go`), a rule's question (`Ask`) as a question step or action, its delegation and the item's `OpenQuestion` (`ask.go`), the answered rule's check, `CheckReturn`, and its three failure verdicts (`returning.go`), route steps with their comment templates, agents, bots, board columns, outcomes, failure reports, statuses, the records crew keeps in its statistics store (`Statistic`, sealed, with its `Process` variant)) and the rule run aggregate: `RuleRun` with its `ActionRun`s, the facts that reach a run, the run events `Decide` returns for a fact and `Apply` applies, the status and reports a run computes, and `History`, the last run of each issue and rule, folded from its events, which gives a new run its start.
- `internal/config`: the global config file (`~/.config/crew/config.yaml`, or `$XDG_CONFIG_HOME/crew/config.yaml`), then `.crew/config.yaml` and `.crew/config.local.yaml`, each file's top-level keys replacing those of the files before it (`files.go`, which also resolves the global file's path with `GlobalFile` and crew's data folder with `DataDir`, by one rule, and names each error's file): strict decoding, so a key of an older format fails as an unknown key or a wrong shape, engine defaults, one file per section: `actions.go` (the top-level shell actions), `functions.go` (function presets and uses: their parameters, merged key by key and checked, and each use's `FunctionUse`, which the app builds through the registry at startup), `rules.go` and `sequence.go` (a rule and its list of actions), `routes.go` (its routes and their steps), `graph.go` (the checks across a rule's actions and routes and across rules), `agents.go`, `queue.go`, `board.go`, `answering.go` (`answering_apps`), `statistics.go` (`statistics`: the store's name, `sqlite` by default, or `off`, which takes no other key) and `questions.go` (`questions`, the question step and action, and crew's built-in `question` and `answered` rules it adds before the file's rules, with their reserved names and labels); builds `crew.Agent` and `crew.Bot`, resolves each session's agent and bot and each named action to its shell definition, and parses each prompt and comment template once; hands the tracker, the statistics store and each agent's harness its section as a `port.Decode`, and the live view each rule's notify as a map.
- `internal/port`: `Tracker`, `Captain`, `Harness`, `Workspace`, `Shell`, `Function`, `Identity`, `Journal`, `Statistics`, the optional `Preparer`, `StatusReporter`, `PullRequestReporter`, `Acting`, `CodeOwnerFinder`, `LoginFinder`, `RepositoryFinder`, `WriterReporter`, `BoardLister`, `Delegator`, `Narrator`, `Reopener`, `UsageReporter`, `LastMessageReporter` and `PullRequestFinder`, sentinel errors, factory types, among them `FunctionDefinition`, which declares a function's verdicts beside its factory.
- `internal/registry`: name to factory, function name to `port.FunctionDefinition`, and store name to `port.StatisticsFactory`; `default.go` is the production list: the `sqlite` store, and no function yet.
- `internal/core`: the pure reducer, (model, input) to (commands, events). No I/O, no clock. It orchestrates the rule runs, which decide their own changes, in four parts. The scheduler (`scheduler.go`): ticks, listings, takes, slots, queues, the stop and the wind-down. The held runs (`runs.go`): each run input becomes a fact for the run its id names, and each event the run decides becomes commands, published events and, when the core journals, a `Record`; it keeps each live action's session plumbing. The route steps (`steps.go`): a run's shell and function steps and the tracker steps it hands the outbox, one at a time. The prompt's paragraphs (`paragraph.go`, `waiting.go`, `answers.go`): every paragraph crew adds to a session's prompt, the resume, answers, verdict and waiting paragraphs among them, and the read of the issue's comments a session at an action with open questions waits for before it starts. The delegation (`ask.go`): the question rule's read of the issue's comments and the delegation it hands the outbox. The return (`answered.go`): the answered rule's read of the issue's comments, which hands its run only the check's label or verdict. The outbox (`outbox.go`, `status.go`, `pullrequest.go`) delivers every tracker write the rules decide on, through a run, a status and a pull-request lane per issue, and owns retrying, owing and dropping them; a held run only receives a write's outcome. The projections: the handled entries (`handled.go`), the journal's `History`, with each past run whose workspace's name another run opens retired (`claims.go`), and the gone entries (`gone.go`). `view.go` builds the `View` from the runs and projections; `update.go` only dispatches run and scheduler inputs, winds down and reports `Stopped`.
- `internal/engine`: the one loop that owns the core, runs commands through the ports, owns `.crew/logs/`, publishes updates. It writes each rule run's log there, its sessions' and scripts' output, keeps the latest session's prompt and last message beside it, and names the run journal's path (`JournalPath`), which the `jsonl` adapter writes. It journals through `port.Journal`: it loads the journal's events into the core at startup and appends each event the core records, from the loop, in order. It keys each session and shell action by its rule run and action, and each route shell step by its rule run and step. It calls each function action and function step with the function built for its use (`engine.Function`, keyed by the use's key path), and writes into the run's log. With a statistics store, it has the core record the crew process at its start, and writes each record the core asks for through `port.Statistics` on a writer goroutine of its own, in order (`statistics.go`), so a slow store never delays the loop; a failed record goes back to the core, which publishes it as `StatisticNotRecorded`, a warning.
- `internal/proc`: the only way to start a child process (own process group, stop with deadline, kill all; `StartDetached` for the browser opener).
- `internal/fileline`: appends a line of its own to a file crew only appends to (the run journal, a session log's resume marker), ending a line a crash cut short; imports only the standard library.
- `internal/captain`: the captain, which answers a coding-agent session's next task (`port.Captain`); its only one, `Dumb`, hands every session a new task with a placeholder prompt.
- `internal/bots`: `crew bots create`, crew's own GitHub identities (private GitHub Apps): names, manifest, loopback page, GitHub API signed as the bot, the bots' files under `$XDG_CONFIG_HOME`, else `~/.config`, on macOS too (`crew/bots`, and the older `crew/mates` read as a fallback); `Act`, which makes the configured bots act: repository tokens renewed in private gh config directories, and the git environment of the co-author hook.
- `internal/upgrade`: `crew upgrade`, which replaces a release build of crew with the latest release or the one named: reads the version argument (`ParseArgs`), tells a release build from a `go install` or local one (`Classify`), finds the release through GitHub's REST API with the token `gh auth token` gives, downloads its assets by id, checks the archive against `checksums.txt` and renames the extracted crew over the running binary, never with `sudo`. `CREW_UPGRADE_API_URL` points it at a loopback fake GitHub, for the acceptance suite.
- `internal/adapter/{github,claude,codex,git,shell,jsonl,sqlite}`: the adapters; `jsonl` is the run journal's file, one version 3 line per run event, and skips the lines older versions wrote; `sqlite` is the statistics store, `statistics.db` in the data folder it is given, which several crew processes write at once (`modernc.org/sqlite`, pure Go, with `modernc.org/libc` at the version the driver's `go.mod` names, which Dependabot leaves alone), opened and migrated on its first record.
- `internal/ui/lines`, `internal/ui/tui`: the renderers; they only read engine updates.
- `internal/fake`: in-memory tracker, scripted harness, temp-dir workspace, scripted shell, scripted function, in-memory run journal, in-memory statistics store.
- **Layering:** imports point inward, and `depguard` in `.golangci.yml` fails the build otherwise. `crew` imports nothing of crew's; `core` imports only `crew`; `port` imports no `core`, `engine`, `config`, adapter or UI; `engine` imports no adapter or UI; adapters import no `core`, `engine`, `config`, UI or other adapter (their tests may import `config`); only `ui/tui` imports Bubble Tea, Lip Gloss and Bubbles; only tests import `fake`; `bots` imports only the standard library and `proc`, and only `cmd/crew` imports it, and the same holds for `upgrade`; `captain` imports only `crew` and `port` of crew's, and so does each function under `internal/function/` (the `function` rule); `fileline` imports nothing of crew's.
- `acceptance/`: the black-box acceptance suite, a nested Go module outside the layering. It reaches crew only through the built binary and never imports crew's packages (a `depguard` rule denies `internal` and `cmd` there). The root `go test ./...`, lint, coverage floors and `tools/diffcover` stop at its `go.mod`: run its vet, golangci-lint and govulncheck with `go -C acceptance` (`acceptance/README.md`, which documents the doubles without crew's internals).
- **New adapter:** one package under `internal/adapter/` with a `Factory(group)`, plus one entry in `internal/registry/default.go`. Optional capabilities are separate interfaces found by type assertion: never wrap an adapter value, never add "not implemented" stubs.
- **New function:** one package under `internal/function/<name>` that returns a `port.FunctionDefinition`, plus one entry in the functions map of `internal/registry/default.go`.

## Tests

- **Fakes:** `internal/fake`: `NewTracker`, the scripted `NewHarness`, `NewWorkspace(t.TempDir())`, and `TrackerFactory`/`HarnessFactory` to register them; `NewRoutingTracker`, a tracker that also comments, closes and lists comments; the scripted `NewShell` runs shell actions and route shell steps; `NewJournal` holds the events an earlier crew left; `NewFunction` is a scripted function, and `FunctionDefinition` registers it with the verdicts it declares; `NewStatistics` is a statistics store that can fail or hold its records, and `StatisticsFactory` registers it. Tests build their own `registry.New` with the fakes, so they go through the same lookup and validation as real adapters.
- **Domain and core:** table tests, no goroutines, no process, network or filesystem. A rule run's decision is a row: the events given, a fact, and the events `Decide` must return.
- **Time:** the engine loop, and `app` where timing matters, run under `testing/synctest` (fake clock, so `time.Sleep` there costs nothing; leaked goroutines fail).
- **Adapters:** scripted `gh` and `git` runners, and recorded `stream-json` fixtures in `internal/adapter/claude/testdata/`.
- **Real git:** only in temporary repositories (`t.TempDir()`, a local bare `origin`), with `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_NOSYSTEM` set so the user's config cannot leak in.
- **Config fixtures:** no test reads this repository's `.crew/config.yaml`, so it changes without touching crew's tests. A test that needs a full config loads an invented one from `internal/config/testdata/` (`translation` covers every kind of key), never a copy of this repository's rules, labels, prompts, shell actions or skills. `tools/crew_config_test.sh` tests that config's own prompts and shell actions (the refine prompt against `/cw-split-plan` and `/cw-rank-blockers`, the rules running the shell actions after their sessions, and the `session-finished` judge against stub `curl` and `sleep`); it needs `jq` and runs by hand, not in CI, after a change to the config.
- **Golden files:** the TUI's views in `internal/ui/tui/testdata/`, with escape codes stripped; rewrite with `go test ./internal/ui/tui -update` and review the diff.
- **Acceptance:** `acceptance/` runs the binary in `CREW_BIN` (unset fails, never skips) against `gh` and `claude` doubles on `PATH`: the test binary itself, through `harness.Main`, answering from a stateful fake GitHub and scripted sessions. Screen scenarios run crew in a pseudo-terminal and compare masked screens with snapshots. Always `-count=1`: a rebuilt binary keeps its mtime. The pull request that changes how crew calls `gh` or `claude` teaches `acceptance/fakegithub` or `acceptance/fakeclaude` the call. Scenarios (`acceptance/scenarios/`) and their snapshots are the tester's: only the tester rewrites snapshots (`-accept-snapshots`).

## Docs

- **Keep it true:** a change in behaviour, configuration or messages updates the README where it describes them, in the same pull request.
- **Learnings:** `docs/solutions/` holds documented solutions to past problems (bugs, best practices, workflow patterns), by category, with YAML frontmatter (`module`, `tags`, `problem_type`).
- **Capture:** After a solved, verified problem, automatically invoke the `ce-compound` skill with `mode:non-interactive` at the completion checkpoint only when the work produced durable project reasoning that is not readily recoverable from the final code, tests, types, comments, or existing documentation, and losing it would plausibly cause recurrence, material risk, or substantial rediscovery. Apply this counterfactual: if the learning document disappeared, would a future engineer reading the final implementation still be likely to repeat the mistake or redo substantial investigation? If not, do not invoke it. Completion, effort, and diff size alone are not enough. Capture at the checkpoint so a qualifying learning can ship in the PR that produced it, and only where the repository treats captured learnings as tracked, committed knowledge.

## Releases and CI

- **Releases:** the version is `VERSION`, starting at `0.1.0`. A bump pull request changes it and adds the version's section to `CHANGELOG.md`, a `## X.Y.Z` heading with what changed for users. Merging it publishes nothing. The boss then starts the Release workflow by hand on `main`. Its `tools/release check` refuses another branch, a version that already has a tag or a published release, and a version with no section. Its `build` job then has GoReleaser (`.goreleaser.yaml`) build `vX.Y.Z` as a draft GitHub release with crew's binaries for macOS and Linux and `checksums.txt`, with the section as the release text. Its `attest` job, the only one that can mint an OIDC token, attests the archives and the `crew` inside each one with `actions/attest`. Its `publish` job checks that the draft is above every published release and that each archive and its `crew` verify with `gh attestation verify`, with the README's flags, and only then publishes the draft. Nothing is published unless every one built and verified; a failed run leaves a draft, which re-running its failed jobs or a new start finishes. `tools/releaseworkflow` runs the workflow's inline scripts against a fake release. A run that refused is fixed by a new pull request and a new start: re-running it checks the same commit again. Unlike the other workflows, it publishes without the shared release action and uses only its `check` mode. The version must be `MAJOR.MINOR.PATCH` and not below the latest release (CI's `version` check).
- **Shared workflows:** CI, Claude Code and the release call [thatsnotmynameio/.github](https://github.com/thatsnotmynameio/.github), pinned by SHA with the version as a comment; Dependabot bumps them. Change shared behaviour there, not here.
- **CI:** GitHub Actions are pinned by SHA, pnpm packages by hash (`pnpm-lock.yaml`). Use pnpm, never npm: `package.json` pins pnpm itself (`packageManager`). The `checks` ruleset requires `version`, `actionlint / actionlint` and `go`. A new required job goes into it through `bootstrap.sh --checks` (in `.github`); `acceptance` joins it that way once it is on `main`.
- **Codacy:** its jobs are off until the repository variable `CODACY_ENABLED` is `true`. Fix a finding; suppress only a genuine false positive, at the finding, naming the rule and the reason (`//nolint:<linter> // <reason>`). Never exclude crew's own source from analysis. After editing `.codacy.yaml`, run `pnpm exec codacy-analysis update-config` and commit both files. The gates live in Codacy's UI.

## Agents

- `AGENTS.md` and `.agents/` are the source; `CLAUDE.md`, `.claude/agents` and `.claude/skills` are symlinks to `AGENTS.md`, `.agents/agents` and `.agents/skills`. Edit the source.
- `acceptance-tester` (`.agents/agents/acceptance-tester.md`) writes behavior tests from a plan's acceptance examples in its own worktree, without reading the implementation. It is linked into `~/.claude/agents/` to work in any repository.
- `cw-create-issue` (`.agents/skills/cw-create-issue/SKILL.md`) is the `/cw-create-issue` skill: it creates a GitHub issue with the label and filled issue template of one of the issue types its own table lists. The `cw-*` skills are this repository's own aids, not crew defaults: they do not read `.crew/config.yaml`, and their types, labels and prompts, this repository's, live in the skill files. Its directory is linked into `~/.claude/skills/` to work in any repository.
- `cw-update-issue-plan` (`.agents/skills/cw-update-issue-plan/SKILL.md`) is the `/cw-update-issue-plan` skill: it copies the plan file the session's `ce-brainstorm` or `ce-plan` wrote into the body of the issue the session is working on, keeps the old body in a comment, and moves the issue to the label given or, without one, runs the prompt it holds, which moves it from `crew:brainstorm:in progress` to `crew:brainstorm:done`. Linked like `cw-create-issue`.
- `cw-brainstorm` (`.agents/skills/cw-brainstorm/SKILL.md`) is the `/cw-brainstorm` skill: it fills the brainstorm prompt it holds with an issue and runs it in the user's session. Linked like `cw-create-issue`.
- `cw-split-brainstorm` (`.agents/skills/cw-split-brainstorm/SKILL.md`) is the `/cw-split-brainstorm` skill, once `/cw-split-plan`: it reads only the issue it is given, measures its brainstormed plan with its `measure.sh` and, above 10,000 characters or 12 requirements, splits it into small parts that each merge alone, written as lean files in `docs/splitting/brainstorm/issue-N/` (`1.md` to `n.md`, ignored by git) with `issues.json`, which lists each part's id, its title and the ids of the parts it is `blocked_by`. Each part copies its contract (decisions, requirements, flows, examples) verbatim from the plan, writes its own short context, and names what the parts that block it deliver. It creates no issue and changes nothing on GitHub; the refinement prompt in `.crew/config.yaml` and `tools/crew_config_test.sh` still run `/cw-split-plan` and expect the sub-issues, split record and outcomes it wrote before, until they run this skill and read these files. It is not linked into `~/.claude/skills/`: it is written for this repository's refinement rule.
- `cw-split-ce-plan` (`.agents/skills/cw-split-ce-plan/SKILL.md`) is the `/cw-split-ce-plan` skill: the same split for a plan `ce-plan` enriched with implementation units. It reads only the issue it is given, measures its plan with `/cw-split-brainstorm`'s `measure.sh` and, above the same threshold, groups its whole units into small parts that each merge alone, written as lean files in `docs/splitting/plan/issue-N/` with `issues.json`. Each part copies its units, technical decisions and contract verbatim, and a unit's dependency on another part's unit becomes a link between the parts. It changes nothing on GitHub. It is not linked into `~/.claude/skills/`.
- `cw-rank-blockers` (`.agents/skills/cw-rank-blockers/SKILL.md`) is the `/cw-rank-blockers` skill, which the refine prompt in `.crew/config.yaml` runs for each issue it refines, reading in full only the issues it lists, or every candidate when it fails: its `rank.sh` takes an issue, asks Jev (`jev-1.13.0`) about each open issue the logins in `$CREW_CODE_OWNERS` and `$CREW_BOTS` opened, one request per pair, and prints the 5 most likely to block it and the 5 it most likely blocks, or one error line naming why it could not judge every candidate. Its `backtest.sh` replays `rank.sh` against every `blocked_by` link GitHub records, each with the issues and bodies of the moment it was recorded, and prints a report ending with #166's gate (the real dependency in the top 5 for at least 70% of the links). Neither records anything. They need `TYPESAFE_API_KEY`, `gh`, `jq` and `curl`. Their tests, `rank_test.sh` and `backtest_test.sh`, use stub `gh` and `curl` and run by hand, not in CI. It is not linked into `~/.claude/skills/`: it reads crew's session environment.
- `cw-tester` (`.agents/skills/cw-tester/SKILL.md`) is the `/cw-tester` skill: it makes the session crew's black-box tester for the areas it is given. It reads only the README, the two config references the README links, `crew --help` and the acceptance doubles' documentation, never crew's code, writes scenarios under `acceptance/scenarios/<area>/` for the README's promises and the edge cases it judges necessary, keeps a scenario the binary fails red, rewrites a TUI snapshot only when the new screen keeps the README's promises, commits only its own packages and ends with a report of the scenarios that fail and the gaps in the README. It is the tester `acceptance/README.md` names, and the developer never edits its scenarios. It is not linked into `~/.claude/skills/`: it is written for this repository's acceptance suite.
- **Reports:** Write every report, summary, or handoff to the user through the `ce-noslop` skill. This applies when you are the top-level agent writing to the user, not when you are a subagent reporting to its caller. Do not apply it to code, config, verbatim quotes, or text the user asked to post as written.
- **Jev:** when a change needs a judgment on free text (such as classifying, routing, verifying, or ranking), consider TypeSafe's Jev model through the [agent skill](https://docs.typesafe.ai/agent-skill) before using string rules or LLM prompts meant for programmatic parsing. Measure its effectiveness first using real data (e.g., `.crew/logs` and repository issues) using these criteria: one narrow judgment per question, only the necessary text in the state, and thresholds chosen from held-out data. If it is not a fit, explain why. This requires `TYPESAFE_API_KEY`; skip Jev if the key is missing.
